목적지 Address를 기준으로 구분
- **Unicast**
	- 출발지와 목적지가 `1 : 1` 통신
	- 실제 사용하는 대다수의 통신
- **Broadcast**
	- 동일 네트워크에 존재하는 모든 호스트가 목적지
	- 목적지 Address가 네트워크 전체로 표기되어 있는 방식
	- Unicast로 통신하기 전에 상대방의 정확한 위치를 알기 위해 사용
- **Multicast**
	- `1 : 그룹` (multicast를 구독 호스트) 통신
	- 하나의 출발지에서 다수의 특정 목적지로 데이터 전송
	- Multicast 그룹 Address를 이용해 해당 그룹에 속한 다수의 호스트로 패킷을 전송하기 위한 통신 방식
	- IPTV • 사내 방송 • 증권 시세 방송 등 다수에게 동시에 같은 내용을 전달할 때 사용
		- ZOOM 등
- **Anycast**
	- `1 : 1` 통신 (목적지는 동일 그룹 내의 1개 호스트)
	- 다수의 동일 그룹 중 가까운 호스트에서 응답
	- IPv4에서는 일부 기능 구현
	- IPv6에서는 모두 구현 가능
	- Anycast Address가 같은 호스트들 중, 가장 가깝거나 효율적으로 서비스할 수 있는 호스트와 통신함
		- 가장 가까운 DNS 서버 찾을 때 사용

- **최종 통신은 대부분 `1 : 1`로 Unicast 와 Anycast가 동일하나, 통신 가능한 후보자는 서로 다름**
	- Unicast → 출발지 목적지가 모두 하나씩
	- Anycast → 같은 목적지를 가진 서버가 여러대 → 통신 가능한 다수의 후보군 존재

- 현재 주로 사용하는 네트워크 주소 체계는 IPv4
- 일부 모바일 네트워크와 IDC 위주로 새로운 IPv6 기반 주소 체계가 사용되고 있음
- IPv6에는 Broadcast가 없음 → 링크 로컬 Multicast로 대체됨

### 링크 로컬 멀티캐스트
- 같은 물리적 네트워크 안에 있는 특정 그룹의 장치들에게만 데이터 전송
- **Link Local** 
	→ 라우터를 넘어가지 않는 동일한 로컬 네트워크 내의 범위

- **특징**
	- 범위 제한: 데이터가 라우터를 통과 못하므로 오직 같은 스위치나 허브에 연결된 장치들끼리만 통신 가능
	- 네트워크 상의 장치들이 서로를 찾거나 자동으로 설정을 주고 받을 때 사용
	- Broadcast와 달리 해당 데이터를 받기로 설정된 그룹 멤버들에게만 전달되어 불필요한 트래픽을 줄임

- **사용 사례**
	- IPv6 에서는 Broadcast가 존재하지 않음
		→ Link Local Multicast를 이용해 구현
	
	- Address 자동 설정(SLAAC)
		- 장치가 네트워크 접속하자마자 자신의 존재를 알리거나 중복 주소를 확인할 때 사용

	- 인근 장치 탐색 (Neighbor Discovery)
		- IPv4의 ARP 대신 상대방의 MAC Address 를 알아내기 위해 Multicast 메시지를 보냄

### BUM Traffic
- BUM → Broadcast • Unknown Unicast • Multicast
	- 서로 다른 트래픽이지만 네트워크에서의 동작은 유사함
- Unknown Unicast?
	→ 목적지 주소는 명시되어 있으나, 스위치가 목적지 MAC 주소를 학습하지 못한 상태의 유니캐스트 트래픽
	→ 목적지 포트를 알 수 없어 수신 포트를 제외한 모든 포트로 플러딩(Flooding)함.
	→ 동작은 브로드캐스트와 유사하지만 목적지 주소는 유니캐스트임.
- BUM Traffic이 많아지면 네트워크 성능이 저하될 수 있음
- 이더넷 환경에서는 ARP Broadcast를 먼저 보내고 이후 통신을 시작
	→ BUM Traffic 이 많이 발생하지 않음

## 2 ) MAC Address
---
### 개요
- 변경할 수 없도록 하드웨어의 고정돼서 출하되는 주소
- 하드웨어마다 서로 다른 고유의 주소임
- **MAC Address는 일종의 NIC의 주민등록번호** → IP 주소가 택배 주소라면, MAC은 그 주소로 배송된 물건을 받는 **내 집의 실제 위치**로 비유할 수 있음
- **모든 네트워크 장비 업체에서 장비가 출하될 때마다 MAC Address를 할당함**
	→ 매번 Address의 할당 여부 확인 불가
	→ 제조업체 하나에 하나 이상의 주소 풀을 주고, 각 제조업체가 해당 풀 내에서 MAC을 할당함
		(노나먹자)
	→ 풀을 할당하는 것을 제조사 코드라고 하며 IEEE 국제 기구에서 관리함
- **MAC Address는 48 비트**
	- 16진수 12자리로 표현
	- 앞의 24비트 → `OUI` (제조사 코드)
	- 뒤의 24비트 → UAA (각 제조사에서 자체적 할당하여 각 장비를 구분)

- **유일하지 않은 MAC Address도 존재함**
	- UAA가 실수나 의도적으로 중복될 수 있음
	- But, 동일 네트워크에서만 중복되지 않으면 문제 없음
	-  서로 다른 네트워크 간 통신은 라우터를 통해 이루어짐.
	- 라우터는 패킷을 다른 네트워크로 전달할 때 새로운 이더넷 프레임을 생성함.
	- 이 과정에서 출발지 MAC 주소와 목적지 MAC 주소를 다음 홉(Next Hop)에 맞게 변경함.
	- 따라서 MAC 주소는 네트워크를 넘어가도 유지되지 않음.
	- 반면 IP 주소는 최종 목적지까지 변경되지 않음.
	
	> **MAC 주소는 홉(Hop)마다 변경되고, IP 주소는 종단 간(End-to-End) 유지됨.**

### MAC Address 변경도 됨
- 일반적으로 ROM 형태로 고정돼 출하되므로 NIC에 고정된 주소를 변경하기는 어려움
- But, 주소 자체도 메모리에 적재 되어 구동 됨
	- 다양한 방법으로 주소를 변경해 동작시킬 수 있음
		- Windows의 경우 driver 상세에서 변경 기능 제공
		- Linux의 경우 GNU MacChanger 네트워크 설정 파일에 MAC Address 입력 시 변경 가능

### 동작
- 기본 동작 방식
	- NIC는 자신의 MAC 주소를 가짐
	- 전기 신호가 들어오면 2계층에서 데이터 형태로 변환
	- 내용 구분 후 도착지 MAC을 확인
	- 도착지 MAC이 자신의 MAC과 일치하지 않을 시 폐기함
	- 패킷의 목적지 MAC이 자신이거나 Broadcast, Multicast 같은 그룹 Address 면 처리할 주소로 인지
		- 패킷 정보를 상위 계층으로 넘김
	- 도착지 Address가 일치하지 않아 NIC에서 패킷을 자체 폐기하는 경우와 달리
		- Address, Broadcast Address는 NIC 가 아닌 OS나 애플리케이션에서 처리

> **IPv6가 Link Local Multicast를 사용하는 이유**
> - IPv4의 Broadcast는 네트워크의 모든 장치가 수신 여부와 관계없이 패킷을 받아 처리해야 함
> - NIC가 하드웨어 수준에서 처리하지만, 불필요한 패킷이 OS와 Application까지 전달되어 자원 낭비 발생
> - IPv6에서는 Broadcast를 없애고 **Link Local Multicast**로 대체
>   → 필요한 그룹(Multicast Group)에 가입한 장치만 패킷을 수신
>   → 불필요한 트래픽 처리와 자원 낭비를 줄임

- **무차별 모드(Promiscuous Mode)**
	- NIC(Network Interface Card)가 수신한 모든 패킷을 분석할 수 있도록 설정하는 모드임.
	- 기본적으로 NIC는 자신의 MAC 주소나 브로드캐스트 주소의 패킷만 처리함.
	- 네트워크 모니터링, 디버깅, 패킷 분석 시에는 다른 목적지의 패킷도 확인해야 함.
	- 이를 위해 NIC를 무차별 모드로 설정하면 자신의 MAC 주소와 관계없는 패킷도 메모리에 올려 분석할 수 있음.
	- 대표적인 애플리케이션으로 Wireshark가 있음.

- **MAC Address를 여러개 갖는 경우**
	- MAC은 단말이 아닌 NIC에 종속되므로 단말에 여러 개의 NIC를 장착 시 여러 MAC 주소 소유 가능
	- Multi Layer Switch, Router 같은 장비의 경우 NIC가 여러개임

## 2 ) IP Address
---
- OSI 7 계층에서 Address를 갖는 계층은 2 계층과 3 계층
- 3 계층은 논리 Address인 IP Address 사용
- 사용자가 변경 가능한 논리 Address
- 2 부분으로 나뉨
	- Network Address → 그룹을 의미
	- Host Address → 구별 위함

### 주소 체계
- IPv4
	- 32 비트 체계
	- 4개의 옥텟(8비트)로 나뉨
	- 각 옥텟은 `.`으로 구분하여 10진수로 표현
	- Network와 Host 주소로 구분, 크기 설정이 가능함
- IPv6는 128 bit

### IPv4 Classful
- 필요한 호스트 IP 개수에 따라 네트워크 크기를 다르게 할 수 있는 클래스 개념 도입
- `A, B, C, D, E` 5개의 클래스로 구분

1. **A Class: 0.0.0.0 ~ 127.255.255.255**
	- 호스트 개수가 `256 * 256 * 256`
	- 0.0.0.0 / 8
	- 1.0.0.0 / 8

2. **B Class: 128.0.0.0 ~ 191.255.255.255**
	- 호스트 개수가 `256 * 256`
	- 128.0.0.0 / 16
	- 128.1.0.0 / 16

3. **C Class: 192.0.0.0 ~ 223.255.255.255**
	- 호스트 개수가 `256`
	- 192.0.0.0 / 24
	- 192.0.1.0 / 24

4. **D Class: 224.0.0.0 ~ 239.255.255.255**
	- Multicast 용

5. **E Class: 240.0.0.0 ~ 255.255.255.255**
	- 예비

### SubNet Mask
- 네트워크 규모를 나타내기 위한 표현법
- 동일한 주소를 사용하는 영역을 1로 표시 → 비트 수나 IPv4 형태로 표현
- `192.168.0.0/24` 또는 `192.168.0.0 255.255.255.0` 의 형태로 표현
- 위 네트워크의 의미는 `192.168.0`까지 동일하면 같은 네트워크로 간주
	- 이 크기가 주소 대역 별로 고정 돼 있는 방식을 **Classful**이라고 함
- 0과 1을 반대로 치환해 사용하는 것을 **와일드 마스크**라고 함
- 와일드 마스크는 방화벽에서 사용

### IP 주소 부족
- 인터넷 상용화에 따라 연결되는 호스트가 폭발적으로 증가
- 기존 Classful 방식으로는 감당 불가능
- **해결책**
	- **CIDR (Classless Inter Domain Routing)** 기반의 Address 체계
	- **NAT**와 **Private IP** Address
	- **IPv6**

### CIDR
- **등장 배경**
	- IPv4의 주소 고갈 문제를 해결하기 위해 등장
	- Classful을 이용 시 IP 주소가 낭비됨
	- 서브넷 마스크의 크기를 자유롭게 사용
- **서브네팅**과 **슈퍼네팅** (Route Summarization)
	- 서브네팅 → 기본 Classful 방식의 네트워크를 **분할**해서 사용
	- 슈퍼네팅 → 기본 Classful 방식의 네트워크를 **병합**해서 사용
		- 라우터에서 네트워크를 병합하여 광고하기 위해 주로 사용
- 실무에서 고려해야 할 부분
	- **네트워크 사용자 입장**
		- 네트워크에서 사용할 수 있는 IP 범위 파악
		- 기본 게이트웨이와 서브넷 마스크 설정이 제대로 되어 있는지 확인
	- **네트워크 설계자 입장**
		→ 네트워크 설계 시 네트워크 내 필요한 단말을 고려한 네트워크 범위 설계

### Public IP와 Private IP
- 외부와 통신을 하려면 IP Address가 있어야 함
- IP Address는 네트워크 내에서 유일무이해야 함
- 인터넷을 하고자 할 때는 전 세계 네트워크에서 유일무이한 주소를 사용해야 함
	- 인터넷을 사용하지 않는 곳은 세계에서 유일무이한 IP 주소를 가질 필요가 없음
- **Private IP** → 외부 네트워크에서 사용하지 않고 내부 네트워크에서만 사용 가능한 IP
	- Private IP를 사용하면 기본적으로 인터넷에 접속할 수 없지만 **NAT** 장비를 이용하면 접속 가능
	- Private IP 대역
		- `10.0.0.0/8`: `10.0.0.0 ~ 10.255.255.255`
		- `172.16.0.0/12`: `172.16.0.0 ~ 172.31.255.255`
		- `192.168.0.0/16`: `192.168.0.0 ~ 192.168.255.255`
	- IP 공유기에서는 `192.168.0.0/24`를 주로 이용
	- 모바일 디바이스는 `10.` 대역이나 `172.16` 대역을 주로 이용

#### Bogon IP
- IP 주소를 할당하는 최상위 기구인 **IANA**가 여러 목적으로 예약해서 Public IP로 할당되지 않는 IP
- 인터넷에서 동작하는 라우터에 해당 IP 정보가 없음
- Bogon IP로 통신 시도가 있었다면 **IP Spoofing** (IP 주소 변조)했거나 실수로 할당된 IP를 사용한 경우이므로 적절히 필터링하는 것이 좋음

| IP 대역 | 용도 |
| ------- | ---- |
| `0.0.0.0/8` | This Network |
| `10.0.0.0/8` | Private Network |
| `100.64.0.0/10` | 통신 사업자가 Private IP 할당용 |
| `127.0.0.0/8` | Loopback 주소 |
| `127.0.53.53` | 네임 충돌 발생 |
| `169.254.0.0/16` | Link Local |
| `172.16.0.0/12` | Private Network |
| `192.0.0.0/24` | IETF 프로토콜 할당 |
| `192.0.2.0/24` | 테스트 용 |
| `192.168.0.0/16` | Private Network |
| `192.168.0.0/15` | 네트워크 인터커넥트 디바이스 벤치마크 테스트|
| `198.51.100.0/24` | 테스트 용 |
| `203.0.113.0/24` | 테스트 용 |
| `224.0.0.0/4` | 멀티캐스트 용 |
| `240.0.0.0/4` | 예약 |
| `255.255.255.255/32` | 브로드캐스트 |

#### IP 주소 발신지 확인 방법
- IP Address를 보고 발신자의 신원이나 소속된 조직 이름을 확인할 수 있음
- **Whois**나 **KISA**에서 서비스를 제공

## 3) TCP & UDP
---

### 4계층 프로토콜과 서비스 포트
- 4계층에서는 **Sequence Number**, **ACK Number** 등이 사용됨
- 2계층 → 이더 타입 / 3계층 → 프로토콜 번호 / 4계층 → 포트 번호가 상위 프로토콜 지시자
- TCP/IP 스택에서는 **TCP**와 **UDP**가 담당
- 4계층의 목적
	→ 목적지를 찾아가는 주소가 아니라 **애플리케이션에서 사용하는 프로세스를 정확히 찾아가고**
	→ 데이터를 분할한 패킷을 잘 쪼개 보내고 잘 조립하는 것
- 실제 통신 시 목적지와 출발지 모두 포트 번호가 설정됨
	- 일반적으로 이야기하는 포트는 **목적지의 포트 번호**

#### Port Range
- **Well Known Port** (`0 ~ 1023`)
	- HTTP TCP `80`, HTTPS TCP `443`, SMTP TCP `25` 등 IANA에 등록된 잘 알려진 포트
- **Registered Port** (`1024 ~ 49151`)
	- 다양한 애플리케이션에 포트 번호를 할당하기 위한 범위
	- 신청하면 아무 포트 번호나 할당
- **Private / 임시 Port** (`49152 ~ 65535`)
	- 자동 할당되거나 사설 용도로 할당
	- 클라이언트의 임시 포트 번호로 사용
	- 쿠버네티스에서는 `30000 ~ 32767`을 **Node Port**라고 별도 용도로 할당

### TCP 프로토콜
- **연결 지향** 전송 계층 프로토콜
- **신뢰성**이 중요한 대부분의 통신에서 사용
	→ HTTP/HTTPS, SSH, SMTP, FTP, 데이터베이스 연결
- **3-way Handshake로 연결 확립**
	→ 통신 전에 클라이언트와 서버가 SYN, SYN-ACK, ACK 세 단계로 연결을 확인
	→ 마치 악수를 하기 전에 "악수할까요?", "네, 합시다", "좋아요" 라고 확인하는 과정과 유사

#### 패킷 순서 & 응답 번호
- 분할된 패킷을 잘 분할하고 수신 측이 잘 조합하도록 패킷에 순서를 주고 응답 번호를 부여
- 패킷에 순서를 부여하는 것이 **시퀀스 번호**, 응답 번호를 부여하는 것이 **ACK**
- 이 번호를 확인해서 순서가 바뀌거나 중간에 패킷이 손실된 것을 파악 가능

#### 윈도 사이즈와 슬라이딩 윈도우
- TCP에서 패킷을 하나씩 주고받아 검사하면 오버헤드가 크므로 한 번에 여러 개의 패킷을 보내고 ACK를 받는 방법을 선택
- 한 번에 보내는 패킷의 개수 → **윈도 사이즈**
- 여러 개의 데이터를 한꺼번에 전송하는 방식 → **슬라이딩 윈도우**
- 슬라이딩 윈도우 구현 방식
	- 정적으로 크기를 정하는 방식
	- 에러 발생 여부에 따라 동적으로 크기를 변경하는 방식

### UDP 프로토콜
- 4계층 프로토콜이 가져야 하는 특징이 거의 없음
- TCP와 달리 **신뢰성 있는 통신을 위한 기능이 없음**
	- 연결 확립 절차 없음 (3방향 핸드셰이크 불필요)
	- 시퀀스 번호, ACK 번호, 윈도우 사이즈, 플래그 없음
	- 데이터 유실 발생이나 순서 변경 시 복구 불가
- **제한된 용도로만 사용**
	- 음성 데이터나 실시간 스트리밍 같이 시간에 민감한 프로토콜이나 애플리케이션
	- 사내 방송이나 증권 시세 데이터 전송에 사용되는 멀티캐스트처럼 단방향으로 다수의 단말과 통신해서 응답을 받기 어려운 환경
	- 중간에 데이터가 몇 개쯤 유실되는 것보다 재전송을 위해 잠시 멈추는 것이 더 큰 문제가 되는 서비스
- *하지만* 동영상 전송 방식 중 **넷플릭스나 유튜브**와 같이 시간에 민감하지 않은 단일 시청자를 위한 연결은 **TCP**를 사용
	→ 원활한 시청을 위해 수 초~수 분의 동영상 데이터를 미리 캐시에 저장

### TCP와 UDP 비교

| | TCP | UDP |
| ----- | --- | --- |
| 연결 방식 | 연결 지향형 | 비연결형 |
| 오류 제어 | 수행함 | 수행하지 않음 |
| 흐름 제어 | 수행함 (속도 조절) | 수행하지 않음 |
| 전송 방식 | 유니캐스트 | 유니캐스트, 멀티캐스트, 브로드캐스트 |
| 통신 방식 | Full Duplex (동시에 주고받기 가능) | Half Duplex (어느 순간에는 한쪽만 전송) |
| 사용처 | 일반적인 데이터 전송 | 실시간 트래픽 전송 |

## 4) ARP (Address Resolution Protocol)
---

### 개요
- OSI 7계층 중 **2계층(MAC)** 과 **3계층(IP)** 이 주소를 가지고 있으나 두 주소 사이에는 아무런 관계가 없음
- MAC Address는 하드웨어 생산업체가 임의적으로 할당한 주소로 NIC에 종속
- IP 주소는 직접 할당하거나 **DHCP**를 이용해 자동 할당
- 일반적으로 통신은 IP 주소 기반으로 일어나지만 실제 데이터 전송을 위해 상대방의 **MAC 주소**를 알아내야 함
- 상대방의 MAC 주소를 알아내기 위해 사용되는 프로토콜 → **ARP (Address Resolution Protocol)**
	→ 비유하자면, IP 주소는 "서울시 강남구 123번지"라는 주소이고, MAC 주소는 "그 건물 안의 특정 호실"
	→ ARP는 "강남구 123번지 사는 분, 몇 호실이세요?"라고 **네트워크 전체에 방송**하는 것과 같음
- ARP는 TCP/IP 프로토콜 스택만을 위해서 동작하는 것은 아님

### ARP 동작 방식
- 통신을 시도할 때 출발지와 목적지 **IP 주소**는 알고 있어 캡슐화 가능
- *하지만* 상대방의 **MAC 주소**를 알 수 없어 2계층 캡슐화를 할 수 없음
- 상대방의 MAC 주소를 알아내려면 **ARP 브로드캐스트**를 이용해 네트워크 전체에 질의
- 브로드캐스트를 받은 목적지들은 ARP 프로토콜을 이용해 자신의 MAC 주소를 응답
- 이 작업이 완료되면 캡슐화를 진행해서 데이터를 전송

### ARP 테이블
- 패킷 네트워크에서는 큰 데이터를 잘라 여러 개의 패킷을 전송
- 매 패킷마다 ARP 브로드캐스트를 수행하면 효율성 저하
- 메모리에 ARP 정보를 **테이블 형태**로 저장해두고 재사용
- `arp -a` 명령으로 ARP 테이블 정보 확인 가능
- 성능 유지를 위해 ARP 테이블을 오래 유지하는 것이 좋음
- *하지만* 논리 주소는 언제든지 바뀔 수 있으므로 일정 시간 통신이 없으면 테이블 삭제
- 네트워크 장비에서는 ARP 요청을 CPU에서 직접 수행 → 짧은 시간에 많은 요청이 오면 큰 부하
	- 해커들이 ARP를 이용한 공격을 많이 수행
	- 장비는 ARP 저장 기간을 PC보다 길게 설정하고 많은 요청을 필터링하거나 천천히 처리
	- 일부 장비는 ARP 테이블을 수동으로만 갱신하도록 설정

### GARP (Gratuitous ARP)
- ARP의 대상자 IP 필드에 **자신의 IP 주소**를 채워서 ARP 요청을 보내는 것
- 자신의 IP 주소와 MAC Address를 알리는 것이 목적
- **용도**
	- IP 주소 충돌 감지
	- 상대방의 ARP 테이블 갱신
	- **HA (고가용성)** 용도의 클러스터링

### RARP (Reverse ARP)
- **Reverse ARP**
- 자신의 MAC 주소는 알지만 IP 주소가 없어 서버에게 IP 할당을 요청할 때 사용
- 과거에 네트워크 호스트의 주소 할당에 사용되었지만 제한된 기능으로 인해 **BOOTP**와 **DHCP**로 대체
- 현재는 거의 사용되지 않음

## 5) Subnet & Gateway
---

### 게이트웨이 (Gateway)
- 원격 네트워크 통신은 네트워크를 넘어 전달할 수 없는 **브로드캐스트**의 성질 때문에 네트워크 장비의 도움이 필요
- 이 장비를 **Gateway**라고 함
	→ 게이트웨이는 **네트워크의 출입문** 역할
	→ 비유: 아파트 단지 정문 — 같은 단지 내에서는 자유롭게 다닐 수 있지만, 다른 단지로 가려면 반드시 정문(Gateway)을 거쳐야 함
- 게이트웨이에 대한 정보를 PC나 네트워크 장비에 설정하는 항목 → **Default Gateway**

### Proxy ARP
- ARP를 대행해주는 기능
- 기본 게이트웨이에 **Proxy ARP**를 활성화하면 원격지 통신이더라도 로컬에 ARP 브로드캐스트를 보내서 통신 가능
- 라우터에 기본으로 활성화되어 있어 사용자 몰래 동작하는 경우가 많음

### Subnet
- 현재 통신이 **로컬 통신**인지 **원격 통신**인지를 알 수 있도록 해주는 것
