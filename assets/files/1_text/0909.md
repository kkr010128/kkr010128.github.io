푸시 에러

ImageRegistry는 기본적으로 HTTPS 통신 만을 허용

- HTTP를 사용할 수 있도록 설정 변경
Docker의 설정 파일은 daemon.json 파일에 HTTP를 사용할 수 있도록 설정을 추가
이 파일의 위치는 linux의 경우는 /etc/docker에 위치
"insecure-registries" ["IP:포트번호"]

{
"insecure-registries":["192.168.0.100:5000"]
}

- 도커를 재시작: sudo systemctl restart docker

- 레지스트리를 다시 시작
docker start registry
docker start registry-web

- 이미지를 다시 push: docker push 192.168.0.100:5000/pythonapp:v1

- kubernetes에서 사용하고자 하면 모든 노드 컴퓨터에 이 이미지 저장소를 사용할 수 있도록 설정을 해야 합니다.
/etc/containerd/config.toml 파일에 내용을 추가

[plugins."io.containerd.grpc.v1.cri".registry.mirrors."192.168.0.100:5000"]
endpoint=["http://192.168.0.100:5000"]

- containerd 재시작
sudo systemctl restart containerd

- 다시 배포

- 노드에 추가 작업
sudo mkdir -p /etc/containerd/certs.d/192.168.0.100:5000

sudo nano -p /etc/containerd/certs.d/192.168.0.100:5000/hosts.toml
작성

server = "http://192.168.0.100:5000"
[host."http://192.168.0.100:5000"]
  capabilities = ["pull", "resolve"]
  skip_verify = true

-/etc/containerd/config.toml 파일의 내용을 수정

[plugins."io.containerd.grpc.v1.cri".registry]
ig_path = "/etc/containerd/certs.d"

- containerd 재시작
sudo systemctl restart containerd

- 워커 노드에서 테스트 하고자 하는 경우
sudo crictl pull 이미지경로

**Git
1.버전 관리 시스템
1)개요
=>파일의 변화를 시간에 따라 기록한 후 과거 특정 시점의 버전을 다시 불러올 수 있는 시스템
=>모든 컴퓨터 파일이 버전 관리의 대상

2)종류
=>로컬 버전 관리 시스템
- 직접 백업하지 않고 로컬 데이터베이스에 변경 사항을 기록해 두는 방식
- 각 리비전들 간의 patch set이라고 하는 데이터의 차이점을 특수한 형태의 파일에 보관하는 방식으로 특정 시점의 파일 내용을 확인하고자 하는 경우는 원본 파일에 patch set을 전부 더해서 파일을 만들어내는 방식
- Mac OS X 에서는 개발 도구를 설치하면 RCS가 자동으로 설치되는데 RCS가 대표적인 로컬 버전 관리 시스템 
- 협업에는 이용할 수 없음

=>중앙 집중식 버전 관리 시스템(클라이언트-서버 모델)
- 하나의 서버에 변경 내역을 전부 기록해두고 여러 클라이언트가 접속해서 변경 내용을 적용하는 방식
- 서버에 장애가 발생하면 모든 것이 잘못됨
- CVS, Subversion, Perforce 가 대표적인 도구

=>분산 버전 관리 시스템
- 저장소를 통째로 복사해서 서버 와 클라이언트 모두 가지고 있는 방식
- 체크아웃을 할 때 마다 전체 백업이 수행
- Git(리눅스 커널 개발을 위해 Linus Torvals 가 처음 개발), Mecurial(구글이 파이썬으로 개발), Bazaar, Darcs 등이 대표적인 도구

5)기본 개념
=>작업 영역
- Working Directory
이력 관리 대상(tracked) 파일들이 위치하는 영역
저장소 디렉토리에서 .git 디렉토리를 제외한 공간
작업 중인 파일이나 코드가 저장되는 공간
Work Tree 라고도 함
.git 디렉토리를 제외한 모든 공간

- Staging Area
이력을 기록할 대상 파일들이 위치하는 영역
Index라고도 함
.git 디렉토리 하위에 파일 형태로 존재

- Local Repository
이력이 기록된 파일들이 위치하는 영역
.git 디렉토리에 이력 관리를 위한 모든 정보가 저장되고 관리됨

- 명령어
Working Directory에서 Staging Area로 이동시키는 명령: git add
Staging Area에서 Local Repository로 이동시키는 명령: git commit
Local Repository에서 Remote Repository로 복사하는 명령: git push

=>Commit
- 파일 및 디렉토리의 추가/변경 사항을 로컬 저장소에 기록하는 것이 Commit
- Commit을 수행하면 이전 Commit 부터 현재 상태까지의 변경 이력이 기록된 Revision이 생성됨
- 순서대로 저장되므로 최근 Commit 부터 올라가면 과거 변경 이력과 내용을 알 수 있음
- Revision은 40자리의 고유한 이름을 가지고 있는데 화면에 보여질 때는 짧게 보여지고 이 짧은 이름을 가지고 작업이 가능
- Commit을 할 때는 메시지를 작성해야 하는데 권장 사항
첫번째 줄은 Commit 내의 변경 내용을 요약
두번째 줄은 빈 줄
세번째 줄은 변경한 이유

=>Working 디렉토리에서 관리되는 파일의 상태
- Modified: 관리 중인 파일에 수정 사항이 감지되었지만 커밋이 되지 않은 상태
- Staged: 감지된 파일의 수정 사항이 Staging Area로 이동한 상태
- Commited: 파일의 수정 사항에 대한 이력을 저장한 상태
- Untracked: 저장소에서 관리하지 않는 파일
