**클라우드의 이해
1. 클라우드
1)On Premise & Cloud Computing
=>On-Premise
- 클라우드가 도입되기 이전에는 대부분의 기업이 자체 데이터 및 솔루션 등을 저장하기 위해 데이터 센터를 구축해서 IT 서비스를 수행하는 방식 - 전산실
- 하드웨어를 포함한 모든 자원(CPU, 메모리, 디스크, OS, 네트워크, 라이선스 등)에 대한 초기 투자 비용과 탄력적이지 않은 제한된 용량으로 인해 지속적 관리 비용이 증가하는 단점이 있지만 기업에 내재화된 서비스를 통해 품질 및 보안에 대한 신뢰도는 높음
- 많은 기업들이 On-Premise 방식에서 벗어나 Cloud 서비스로 전환하는데 그 이유 중 하나는 높은 초기 도입 비용과 운용에 따른 추가 비용 때문
- On-Premise 방식으로 설계 시 자원 사용량은 가급적 최대 사용량을 근거로 하고 네트워크 트래픽 또한 최대 순간 트래픽을 가정하기 때문에 고사양의 설계를 하게되고 증설에 따른 시간적, 인적 비용도 무시할 수 없음
- Cloud가 무조건 On-Premise 보다 비용이 낮은 것은 아닌데 동일 사양으로 일정기간 이내에서는 클라우드가 유리할 수 있지만 어느 시점 부터는 Cloud 비용이 더 커질 수 있습니다.
- 관리 비용의 문제

=>Cloud
- 자원을 직접 소유하지 않고 인터넷 너머에 존재하는 Cloud 사업자의 컴퓨터에서 처리하는 형태
- IT 자산을 소유하지 않고 서비스로 이용하는 모델
- 서비스 제공자의 최소한의 관리나 개입만으로 신속하게 생성/제거/구성 할 수 있는 공유 공간의 컴퓨팅 자원들을 어디서든 필요할 때 편리하게 네트워크에 접속할 수 있게해 주는 모델

=>Cloud 등장 배경
- Cloud 등장하기 까지의 흐름
MainFrame: 모든 처리를 메인 프레임 한 곳에서 처리 - 단말은 입출력 기능만 수행

분산형 클라이언트 서버: 클라이언트 단말기에도 처리 기능을 부여

사내 시스템을 네트워크 환경 위에 구축해서 사용

2010 년 대 전 세계에 분산 배치된 서버 리소스를 필요할 때 필요한 만큼 사용하는 Cloud Computing이 등장

- 보급된 배경
다양한 기술의 발전
	CPU의 처리 속도 고속화
	가상화 기술과 분산 처리 기술 등의 발전
	모바일의 융성
	빨라지고 저렴해진 네트워크
	거대해진 데이터센터에 의한 규모의 경제(스케일 메리트)

기업 사용자와 Cloud 사업자 모두에게 Cloud를 받아들일 환경 조성


2)Cloud 정의 와 특징
=>클라우드 정의: 공유 구성이 가능한 컴퓨팅 리소스를 통합을 해서 어디서나 간편하게 요청에 따라 네트워크를 통해 접근하는 것을 가능하게 하는 모델이며 최소한의 절차 도는 서비스 공급자의 상호 작용을 통해 신속히 할당되어 제공되는 것

=>특징
- On-Demand Self-Service: 주문형 셀프 서비스, 사용자가 별도의 기술 습득없이 필요할 때 즉시 사용

- Broad Network Access: any time, any place, any device - 언제 어디서든 네트워크를 통해 리소스 접근

- Resource Poling: Multi-Tenancy - 다중 임대 모델을 통한 자원 할당

- Rapid Elasticity: 비지니스 상황에 따른 컴퓨팅 자원의 탄력적 사용(Flexibility, Scalability)

- Measured Service: 측정 가능한 서비스, Pay-Per-Use 나 Pay as you go - 사용량을 명확하게 기록하고 서비스를 사용한 만큼 지불

=>Cloud 설계 시 고려할 사항
- Fault Tolerance(내결함성)
시스템에 어떤 문제가 발생하더라도 전체 서비스가 중단되지 않고 동작을 계속할 수 있는 능력

하나의 서버나 네트워크 장비가 고장나더라도 다른 자원이 그 역할을 대신해서 사용자는 아무 이상없이 서비스를 이용할 수 있도록 하는 구조

- High Availability(고가용성)
시스템이 가능한 오랫동안 끊김없이 동작하는 것

고가용성을 확보하려면 단순히 서버를 하나 더 놓는 것 만으로는 부족하고 구성 요소 전체를 이중화하고 네트워크 스토리지까지도 장애에 대비한 설계를 갖추어야 함

- Scalabilty(확장성, 유연성)
컴퓨팅 리소스를 필요할 때 필요한 만큼 확장하고 많은 리소스가 필요하지 않을 때는 축소하는 등 유연한 활용이 용이

시스템의 처리 능력을 수평 또는 수직으로 확장할 수 있는 능력

- Redundancy or Resilience(중복성 또는 탄력성)
수요 변화에 따라 자원을 자동으로 늘리거나 줄일 수 있는 능력

자동 확장

=>장점
- 경제성
- 자동화: 업데이트, 보안 패치 백업 등을 직접 수행하지 않아도 됨
- 이동성: 웹을 지원할 수 있는 모든 장치에서 사용 가능
- 자원 공유
- 빠른 구축 속도

=>한계
- Internet Access(No Internet = No Cloud)
- Security
- Privacy
- Vendor Lock-In: 특정 벤더에만 존재하는 서비스는 다른 벤더에서 사용할 수 없다.

3)Cloud Service 종류
=>IaaS: Infrastructure as a Service
- 서버, 스토리지, 네트워크, 방화벽, 로드밸런서 같은 인프라 하드웨어 자원을 가상화하여 사용자 요구에 따라 인프라 자원을 사용할 수 있게 제공하는 Cloud 서비스 방식
- 장점은 자유도가 높고 세밀한 설정이 가능
- 인프라에 사용되는 각각의 자원의 특징에 대한 지식이 유지 관리 차원에서 필요
- 대표적인 서비스가 AWS의 EC2
- All CSPs are providing IaaS to the public

=>PassS: Platform as a Service
- 애플리케이션을 개발하고 실행하고 관리할 수 있는 플랫폼 또는 프레임워크를 제공하는 서비스
- 세일즈 포즈 나 GCP의 Service Now 등

=>SaaS: Software as a Service
- 응용 프로그램을 제공해주는 서비스
- MS Office 365 서비스 가 가장 대표적

=>DaaS: Desktop as Service
- 서비스로서의 데스크탑을 의미하는데 인터넷만 연결되면 언제, 어디서나, 기업 내부망에 접속할 수 있는 Cloud 서비스의 일종
- 모든 정보가 중앙 서버에 저장되기 때문에 직원의 개별 PC가 바이러스에 노출되거나 파손, 분실되어도 정보 유출의 위험이 적고 외부에서 기업망에 접근하는 가장 안전한 기술

5)Cloud & On-Premise(Public Cloud & Private Cloud)
=>비용 비교
- 단기간 사용이면 Cloud 가 장기간 사용이면 On-Premise가 유리
- CapEx에서 OpEx
CapEx: 장비의 가격
OpEx: 운영에 필요한 가격(장비의 비용 + 인적 자원에 대한 비용)

=>확장성 비교
- 클라우드를 사용하면 막대한 IT 투자가 어려운 중소기업의 경우에도 대기업에 필적하는 규모의 서비스로 확장 가능

=>안정성 과 신뢰성
- 클라우드의 리스크
IaaS의 리스크로는 Cloud 사업자의 하드웨어 장애로 인한 데이터 손실이나 서비스 중단 등을 들 수 있고 네트워크 리스크로는 통신 도청, 중간자 공격, 스푸핑 같은 통신 위협과 네트워크 관리 미비에 따른 시스템 다운 위협 등을 꼽을 수 있음
사용자가 할 수 있는 것은 장애에 대비해서 가상 서버를 백업하거나 템플릿을 만들어 두는 것

- Cloud 보안 거버넌스
Cloud를 이용하면 기업 사용자는 자사가 보유한 정보의 관리와 처리를 Cloud 사업자에게 맡겨 버리기 때문에 보안 등의 리스크를 모두 통제할 수 없다는 문제가 발생
Cloud 서비스의 Incident 와 서비스 복구와 같은 사항들은 제어가 어렵고 Cloud 사업자의 갑작스런 파산이나 서비스 중단과 같은 Cloud 서비스의 연속성 리스크 또한 존재

6)클라우드에 필요한 기술
=>가상화
- 개요
서버, 스토리지, 네트워크 및 기타 물리적 시스템에 대한 가상 표현을 생성하는데 사용하는(추상화) 기술

하나의 물리적인 컴퓨터를 여러 대의 독립된 컴퓨터처럼 사용하는 기술

가상화 소프트웨어는 물리적 하드웨어 기능을 모방하여 하나의 물리적인 컴퓨터에서 여러 가상 시스템을 동시에 실행

기업은 가상화를 사용해 하드웨어 리소스를 효율적으로 사용하여 투자 대비 이익을 더 많이 얻을 수 있고 클라우드 컴퓨팅 서비스를 지원하여 조직의 인프라를 더욱 효율적으로 관리할 수 있음

가상화에 대한 접근은 OS, Server, Storage, Network에서도 동일한 모습으로 실행되며 개별 하드웨어 관련 노하우가 소프트웨어로 점차 도입되고 있음

DevOps 지원 기술에서는 인프라의 전문성을 배제하는 개발 측면에서 인프라 구성에 접근할 수 있도록 가상화의 흐름을 맞이하고 있음

- 가상화 이점
리소스를 효율적으로 사용

자동화된 IT 관리

신속한 재해 복구

- 가상화 서비스
운영체제 가상화
	하나의 OS위에서 서로 다른 애플리케이션을 서비스하고 싶다는 생각에서 시작

	초창기에는 파일 시스템 분리가 가능한 chroot를 이용

	Jail라는 이용해서 CPU 시간과 메모리 및 네트워크 등 자원을 분할하여 여러 개의 Linux 가상 서버를 작동

	개별 프로세스 단위로 네임스페이스(Namespace)에 의한 자원 분리를 실시함으로써 가상화를 실현하는 컨테이너라는 개념 이용

	도커가 등장
	
	DevOps에서 개발과 운영의 긴밀한 연계를 위해 인프라 구성을 소프트웨어로 끌어모아 관리를 일원하거나 구성을 변경할 때 사용하는 Infrastruture as Coded에서도 많이 사용하는 기술

서버 가상화
	PC 위에 PC를 만드는 컨셉
	
	VMWare에서 출발했는데 모든 물리적 하드웨어를 소프트웨어로 표현하고 OS 위에서 완전히 다른 OS를 구동시키는 것
	
	가상화된 하드웨어를 가상 머신이라고 하고 가상 머신을 탑재한 원래의 OS를 가상화 호스트라고 부르는데 Hypervison 라고도 부름
	
	Linux 나 Windows 같은 OS를 설치한 후에 Hypervisor 소프트웨어를 넣는 방법과 물리 하드웨어 위에 Hypervisor를 넣는 BareMetal Hypervisor 방법이 있음

스토리지 가상화
	하나의 물리 스토리지에 논리 스토리지를 여러 개 생성하거나 정책에 기반하여 동작하는 내용을 배포 및 결정할 수 있는 스토리지 기기를 SDS(Software Defined Storage)라고 부름

	EMC 아 NetApp 등 스토리지 기업에서 많은 스토리지용 OS가 소프트웨어로 제어할 수 있도록 API를 두고 있어 보다 소프트웨어에 가까워지고 있음

	스토리지는 전문 엔지니어가 각 서비스에 대한 용량을 계산하고 데이터 배치를 결정하거나 디스크 증설 계획은 세우는 등 개발 부문에서는 인프라 담당자가 무엇을 하는지 전혀 모르는 상태였지만 SDS로 가상화된 스토리지를 소프트웨어로 제어할 수 있게 되어 보다 개발과 운영이 긴밀하게 연계될 수 있는 환경이 됨

네트워크 가상화
	네트워크 가상화의 수단으로 가장 많이 알려진 것은 VLAN인데 하나의 물리 스위치를 여러 개의 논리적인 스위치로 나누기 위한 기술

	대규모 네트워크의 유연한 변경에 대한 수요가 커지면서 이 문제를 해결하기 위한 수단으로써 SDN(Software Defined Network)이 제창됨

	개발 부문은 낮은 학습 비용으로 소프트웨어 지식을 구사하면서 네트워크 설정을 변경할 수 있음

	Firewall 이나 Load Balancer도 예전에는 전문 엔지니어만 만질 수 있었지만 소프트웨어에 의한 제어로 이동함에 따라 인프라 담당자 뿐 아니라 개발 부문에서도 내용을 파악하거나 변경할 수 있게 되었음

애플리케이션 가상화

데스크톱 가상화
	Virtual Desktop Infrastructure는 내 컴퓨터의 화면을 멀리잇는 기업의 서버에서 통째로 뛰워서 사용하는 기술

	사용자는 눈앞에 있는 모니터, 키보드, 마우스를 이용하지만 실제로 모든 프로그램이 실행되고 데이터가 있는 곳은 중앙 서버

	서버 가상화는 서비스 제공이 목적이고 테스크톱 가상화는 사용자 작업 환경을 위한 것이 목적

- Hypervisor 가상화 구현 방식
	구현 방식
		Type 1: Native/Bare-Metal Hypervison
			하드웨어 위에 중간 운영체제 없이 Hypervison가 직접 설치되는 방식
			하드웨어 바로 위에 설치된다고 하여 Bare Metal 이라고 부름
			특징
				중간에 거치는 운영체제가 없기 때문에 자원 낭비가 적고 성능이 매우 뛰어남
				하드웨어를 직접 제어하므로 안정성과 보안성이 높아 기업용 서버 환경에서 주로 사용
				자체적으로 머신에 대한 관리 기능이 없기 때문에 관리를 위한 컴퓨터나 콘솔이 필요
			대표적인 종류
				VMware ESXi: 기업형 가상화 시장에서 가장 많이 사용
				Microsoft Hyper-V: 윈도우 서버 환경에 최적화
				KVM(Kernel-based Virtual Machine): 리눅스 커널을 Hypervisor로 변환하여 사용하는 오픈 소스 기술로 AWS 등 대형 클라우드 서비스의 기반
				Oracle VM Server
				Citrix Hypervison(Zen Server): 오픈 소스 기반의 강력한 엔터프라이즈 가상화 솔루션 
  
		Type 2: Host Hypervison
			물리적 하드웨어 위에 설치된 호스트 운영체제 위에 가상화 소프트웨어와 가상 머신에 설치된 운영체제를 움직이는 방식
			특징
				일반 앱처럼 쉽게 설치하고 지울 수 있어서 사용법이 매우 직관적이고 편리
				하드웨어 자원을 사용할려고 하면 타입 1에 비해 오버헤드가 발생(가상머신 -> Hypervison -> 기존 운영체제 -> 하드웨어)
				개발자 테스트용이나 개인 실습으로 주로 사용
				호스트 운영체제에 크게 제약 사항이 없음
			가상화 소프트웨어
				VMware Workstation
				Oracle VirtualBox
				Microsoft의 Hyper-V Client
				Parallels Deektop
				QEMU
				UTM

	구성 요소
		CPU: 물리 CPU 자원을 여러 가상 CPU라고 부르는 vCPU로 나누어서 할당하는데 Core 단위로 할당
		
		Memory: 실제 메모리를 일정 크기만큼 잘라서 할당, 실제로는 모두 같은 물리 메모리를 사용하지만 서로 간섭하지 않도록 격리되어 있음
		
		Disk: 하나의 파일로 구성하는데 하나의 파일에 운영체제를 설치하고 애플리케이션 과 데이터도 저장한 후 Hypervisor가 이 파일을 하나의 하드디스크처럼 인식하도록 도와줌
			
		Network Adapter: 가상 머신마다 독립된 네트워크 어댑터를 만들어주고 이를 통해 다른 가상 머신이나 외부 네트워크 와 통신할 수 있도록 해줍니다. 
		
	Snapshot
		가상 머신에서 컴퓨터 상태를 그대로 저장해 두는 파일
		저장하는 것
			가상 디스크 상태
			Memory 상태: 현재 켜져 있는 프로그램, 작업 중 이던 창 등
			하드웨어 설정: CPU 개수, 메모리 크기, 네트워크 설정 등
		동작 원리
			스냅샷은 가상 머신의 전체 디스크를 매번 통째로 복사하는 것이 아니고 차이점만 기록하는 방식(Copy-on-Write)으로 작동
			기본 상태(Base): 원래 가상 머신의 가상 디스크 파일
			스냅샷 생성: 기존 디스크 파일은 읽기 전용으로 잠기고 그 위에 새롭게 변경되는 데이터만 저장하는 차동 디스크 파일이 만들어 짐
			이후 작업: 스냅샷 이후에 사용자가 파일을 지우거나 설치하는 모든 작업은 차동 디스크 파일에 수행됨
			Rollback: 새로 만들어진 차동 디스크 파일을 날려버리고 기존 디스크만 파일을 가져와서 복구

		사용해야 하는 경우
			위험한 작업 전 필수: 운영체제 업데이트, 프로그램 테스트, 시스템 설정 변경 전에 
			개발 및 테스트: 악성 코드 분석가들이 악성 코드를 실행하기 전에
			여러 분기 테스트: 여러 버전의 프로그램을 나누어 테스트 할 때
			
		주의할 점
			스냅샷은 백업용이 아님
			원본 디스스 파일에 의존하기 때문에 원본 디스크 파일이 깨지거나 물리 하드웨어가 고장나면 스냅샷도 사용할 수 없음
			오래 방치하면 성능 저하: 스냅샷을 찍은 상태로 가상 머신을 계속 쓰면 변경 사항(차동 파일)이 점점 커지게 되서 스냅샷이 누적되면 디스크 읽기/쓰기 속도가 느려지고 컴퓨터 용량을 많이 소모
			용무가 끝나면 삭제하던가 병합을 수행


=>Container
- 개념
애플리케이션 과 그 애플리케이션을 실행하기 위해 필요한 의존성 요소(실행 환경, 라이브러리, 설정 파일 등)을 한데 묶은 독립적인 실행 단위

가상 머신은 물리적인 하드웨어 위에 운영체제 전체를 가상화한 다음 그  위에 애플리케이션을 올리는 구조이지만 컨테이너는 호스트 운영체제 와 직접 연결되며 게스트 운영체제같은 추가 레이어가 없기 때문에 성능이 향상되고 리소스도 낭비되지 않음

Container의 경우는 호스트 운영체제의 프로세스 수준에서 격리하고 의존성 요소를 공유하지 않음

Docker 엔진에서는 Container용 Linux 네임스페이스와 컨트롤 그룹을 생성해 이를 처리하는데 Docker의 보안이 Linux 커널 프로세스 격리를 기반으로 하는 이유이기도 한데 운영체제 기반 격리보다는 덜 안전하다고 여겨지기도 함

장점
	Hypervisor 와 Guest OS가 없기 때문에 가벼움
	경량이기 때문에 만들어진 Image 복제, 이관, 배포가 쉬움
	게스트 운영체제를 부팅하지 않기 때문에 애플리케이션 시작 시간이 빠름
	가상 머신보다 경량이라서 더 많은 애플리케이션을 실행할 수 있음

단점: 다양한 운영체제를 사용할 수 없고(Linux 만 사용 가능) 보안적으로 격리되지 않음

- Container Runtime: 컨테이너를 생성하고 실행할 수 있도록 도와주는 소프트웨어
Containerd
	컨테이너 실행을 관리하는 오픈 소스 런타임
	Docker 및 Kubernetes 같은 컨테이너 오케스트레이션 시스템에서 컨테이너 실행을 처리
	Container 전체 수명 주기를 관리하는 기능을 제공

Docker
	Containerd 위에 설치되는 데몬
	Container를 생성하고 관리하는데 필요한 모든 기능을 제고

CRI-O
	RedHat, Intel, SUSE, IBM 등 관리자 및 커뮤니티를 중심으로 개발된 오픈 소스 런타임
	Docker를 대체하기 위해 개발

- Container Orchestration
개요
	여러 개의 Container를 유기적으로 연결 및 실행하고 상태를 추적하고 보존하는 등 Container를 안정적으로 사용할 수 있게 만들어주는 솔루션
	여러 시스템에 Container를 분산해서 배치하거나 문제가 발생한 Container를 교체하는 등의 작업을 수행

종류
	Docker Swarm
		간단하게 설치하고 사용하기도 용이
		기능이 다양하지 않아서 대규모 환경에 적용하려면 사용자 환경을 변경해야 함
		소규모 환경에서는 유용하지만 대규모 환경에서는 잘 사용하지 않음

	Mesos

		Twitter, Apple, AirBnB, Uber 등 다양한 곳에서 검증된 솔루션
		기능을 충분히 활용할려면 분산 관리 시스템과 연동해야 하기 때문에 여러가지 솔루션을 유기적으로 구성해야 하는 부담이 있음

	Nomad

		HashiCorpdml Consul 이나 Vault(암호화 저장소) 와 연동이 원할하므로 이런 도구에 대한 사용 성숙도가 높은 조직이라면 고려할만 한 오케스트레이션 도구

	Kubernetes
		구글이 내부적으로 사용하던 Borg 시스템에서 발전한 기술로 현재는 Cloud Native Computing Foundation(CNCF)에서 관리

=>Serverless Computing 과 Event Driven Architecture
- Serverless
개요
	개발자가 서버를 직접 관리하거나 프로비저닝할 필요없이 애플리케이션을 빌드하고 실행할 수 있는 클라우드 컴퓨팅 모델
	서버가 없다라는 의미가 아니고 개발자 관점에서 신경써야 할 서버가 없다라는 의미
	서버의 운영, 관리, 확장 등은 모두 클라우드 제공업체가 대신 처리해주는 형태

특징
	서버 관리 불필요
	자동 확장
	실제 사용량 기반 과금: 코드가 실행된 시간에 대해서만 비용을 청구

FaaS(Function as Service)
	애플리케이션을 거대한 하나의 프로그램이 아니라 특정 이벤트가 발생했을 때 만 실행되는 작은 함수 단위로 쪼개어 등록하는 방식

구현된 서비스
	AWS 의 Lambda
	Google Cloud Functions
	Microsoft Azure Functions

장점
	인프라 비용 절감
	빠른 출시
	
단점
	Cold Start: 오랫동안 실행되지 않으면 처음 호출될 때 서버를 켜는 준비 시간이 걸려 약간의 Delay가 발생
	플랫폼 종속성: AWS 용으로 만든 서버리스 코드를 Google Cloud로 옮기기 까다로울 수 있음 
	장기 실행 시 비용 증가: 24시간 내내 동작해야 하는 것이라면 EC2 같은 인스턴스를 이용하는 것이 더 저렴할 수 있음

- Event Driven Architecture
소프트웨어 아키텍쳐 패턴 중 하나로 시스템 내외부에서 발생한 의미있는 상태의 변화인 이벤트를 생상하고 감지하여 소비하는 방식으로 동작하는 시스템 구조

구독 과 게시 패턴 이라고도 함

핵심 구성 요소
	Producer(생산자)
		상태 변화를 감지하고 이를 표준화된 메시지 형태로 만들어 발행
	Event Broker(Message Broker)
		생산자가 보낸 이벤트를 수집하고 이를 필요로 하는 소비자들에게 안전하게 전달하는 중간 중재자 역할을 수행
		Apache Kafka, RabbitMQ 가 있고 각 Cloud 서비스에는 이들을 활용할 수 있는 서비스가 제공
	Consumer(소비자)
		Event Broker로 부터 이벤트가 들어오면 자신의 비지니스 로직을 수행 		

가장 큰 특징
	Loose Coupling(느슨한 결합): 하나의 수정이나 결함이 다른 서비스에 영향을 최소로 주는 것

장점
	높은 유연성과 확장성: 새로운 기능을 추가하고자(소비자) 할 때 기존 코드를 수정할 필요없이 Event Broker에게 연결만 시키면 됩니다.
	장애 격리(Fault Tolerance): 특정 서비스에 장애가 발생하더라도 브로커가 이벤트를 보관해 주므로 시스템 전체가 마비되지 않고 장애가 복구된 후 이어서 처리 가능
	실시간 성 응답: 대용량 트래픽 처리나 트래픽 스파이크가 발생했을 때 브로커가 완충재 역할을 해서 시스템이 안정적으로 유지됨
 
단점
	시스템 복잡도 증가
	데이터 일관성 문제: 실시간으로 모든 DB가 동시에 업데이트되는 것이 아니라 시간이 지나면서 점진적으로 일관성이 맞춰지므로 정밀한 트랜잭션 관리가 필요
	중복 처리 고려 필요: 네트워크 문제 등으로 동일한 이벤트가 두 번 전달될 수 있으므로 소비자가 이를 중복처리하지 않도록 설계

=>스토리지 와 데이터 구조
- 종류
객체 스토리지
블록 스토리지
파일 스토리지

- 클라우드 스토리지를 잘 활용할려면 단순히 저장공간이 얼만큼 필요하다는 생각을 넘어서 이 데이터를 어떤 방식으로 사용하고 얼마나 자주 그리고 얼마나 빨리 접근해야 하는지를 고려해야 함

- 객체 스토리지
데이터 본문(파일), 그에 대한 속성(메타 데이터로 파일에 대한 정보), 고유한 이름 이나 주소를 합친 것이 객체

계층 구조가 아니라 평면 구조

트리 구조 처럼 보이도록 만들 수 있지만 실제로는 이름을 만들기 위한 과정일 뿐

객체 스토리지는 Web 기반 API로 접근할 수 있게 설계되어 있어서 프로그램이나 서비스에서 사용하는 것이 쉬움

클라우드에서 데이터를 저장하는 방식 중 가장 많이 사용

구조가 단순하고 대용량 데이터를 오래 보관할 수 있어서 많은 서비스에서 기본 스토리지로 활용

- 블록 스토리지
전통적인 하드디스크를 사용하는 방식

데이터를 작은 블록 단위로 나누어서 저장하고 운영체제가 관리하는 방식

가상 머신을 만들 때 자주 사용

읽기 와 쓰기가 빠르고 정교하게 제어가 가능하다는 강점

파일 전체를 변경하지 않고 일부분만 수정하는 것도 가능

블록 스토리지는 복잡한 설정이 추가되고 운영체제가 포맷을 해야하고 사용자가 직접 파일 시스템을 관리

- 파일 스토리지
네트워크 드라이브와 같이 공유하기 위한 스토리지

여러 클라이언트가 동시에 접근해서 읽고 쓰기가 가능

디렉토리-파일 구조를 그대로 적용

협업에 적합

웹 서버에서 이미지 파일이나 정적 리소스를 공유하고자 할 때 유용

많은 양의 데이터를 동시에 빠르게 읽고 쓰는 경우 병목이 생기기 쉬움

편의성, 동시 접근성, 사용자 친화적 인터페이스라는 면에서 강점이 있음
