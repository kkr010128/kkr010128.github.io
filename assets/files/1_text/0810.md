- 기술

Dedicated Line(전용선)

- VPN
가상의 전용 네트워크를 만들어서 사설망처럼 안전하게 데이터를 주고 받을 수 있게 해주는 기술

실제로는 인터넷을 이용하지만 외부에서 볼 수 없도록 데이터를 암호화해서 전송

Public Cloud에서는 이 VPN을 구성할 수 있는 기능이 기본적으로 제공됨

사용자는 클라우드 상에 VPN 게이트웨이를 만들어서 VPN 클라이언트와 연결하면 됩니다.

VPN은 인터넷을 기반으로 하기 때문에 품질은 인터넷 연결 상태에 따라 달라짐

화상회의처럼 대용량 데이터를 전송하는 경우에는 VPN이 부적합

- 전용선
회사 내부 네트워크와 클라우드 간을 직접 물리적으로 연결

일반 인터넷을 거치지 않기 때문에 속도도 빠르고 안전성도 높아집니다.

데이터베이스를 연결하거나 화상회의 같은 실시간 처리가 중요한 서비스에서 거의 필수

=>로드 밸런서 와 서비스 엔드 포인트
- 서비스 엔드 포인트: 네트워크 상에서 클라이언트가 특정 서비스나 애플리케이션 기능에 접근할 수 있도록 노드나 자원에 노출해 놓은 접점을 의미

- 장점
캡슐화 및 추상화: 내부 시스템 구조가 바뀌어도 외부 사용자는 동일한 엔드 포인트 주소만 참조하면 됨

보안 제어: 특정 엔드포인트 단위로 인증/인가, 방화벽 규칙, 트래픽 제한 등을 적용할 수 있음

로드 밸런싱

=>클라우드 네이티브 네이밍 서비스
- DNS는 도메인 이름을 이용해서 네트워크 통신을 쉽게 해줌

- 클라우드에서 더 복잡한 요구가 발생

- 클라우드에서는 서버 나 컨테이너의 수가 고정이 아니기 때문에 고정 IP를 사용하는 것이 어렵고 비효율적

- DNS와 유사한 역할을 해주는 새로운 네이밍 서비스가 필요

- 클라우드에서는 시스템이 자동으로 이름을 붙이고 그에 해당하는 IP 나 엔드 포인트를 실시간으로 연결해 줌

- 이러한 네이밍 서비스는 컨테이너 오케스트레이션 환경에서 많이 사용

- 쿠버네티스에서 서비스가 생기면 자동으로 네임서버에 등록되고 다른 서비스가 그 이름으로 접근할 수 있게 해줍니다.

- 장점
유연성이 높음

자동화가 가능: 직접 도메인 이름을 등록하거나 IP를 확인하지 않아도 시스템이 알아서 이름과 위치를 연결해 줌

서비스가 통신이 쉬움: 클라우드 내부에서 마이크로 서비스들이 통신할 때 서비스 이름만 알면 통신이 가능

IP 주소를 기억하고 관리하는 시대를 넘어서 이름 기반의 네트워크 설계가 가능

- 최근에는 Private DNS 나 내부 전용 네이밍 서비스도 함께 제공해서 외부에 노출되지 않는 안전한 네트워크 내에서 내부 서비스들끼리 효율적으로 통신할 수 있음

=>클라우드 가상 네트워크 구조
- 클라우드에서 서버를 만들고자 하는 경우 가상 네트워크라는 단위부터 생성을 해야 하는데 이것을 VPC(Virtual Private Cloud) 또는 Vnet(Virtual Network)이라고 부름

- 생성 과정
VPC 생성

IP 주소 범위를 설정하고 서브넷 설정

서버 생성 - Private IP를 설정하고 외부로 연결해야 하는 경우에는 Public IP 나 NAT Gateway를 설정

라우팅 테이블로 흐름을 설정: NAT Gateway로 갈지 아니면 온프레미스로 갈지 결정

보안 그룹 과 네트워크 ACL을 이용해서 방화벽 기능을 구현

=>보안과 접근 제어
- 공유 책임 모델
클라우드의 보안은 클라우드 기업이 전적으로 책임져 주지 않음

일정 부분 사용자도 함께 책임 져야 함

클라우드 기업은 물리적인 기반 인프라에 대해서는 전적으로 책임을 지지만 그 위에 올려 사용하는 소프트웨어에 대해서는 무엇을 올려서 어떻게 사용하는가에 따라 사용자에게도 책임이 있다는 의미

책임의 경계
	IaaS: 운영체제 부터 네트워크 설정을 포함한 거의 대부분을 사용자가 관리

	PaaS: 플랫폼의 기본 구성과 일부 보안 설정은 클라우드가 책임지고 사용자는 애플리케이션 단의 보안을 담당

	SaaS: 거의 모든 인프라 보안은 클라우드가 담당하고 사용자 계정 과 데이터 접근 권한 설정만 사용자가 담당

- IAM(Identity and Access Management)
적절한 사용자가 적절한 시점에 적절한 시스템 자원에 접근할 수 있도록 통제하고 관리하는 보안체계이자 프레임워크

핵심 구성 요소
	식별(Identification): 누가 접근하고 있는지를 명확히 구분하는 것으로 사용자는 사람일 수 도 있지만 서버나 프로그램 같은 시스템일 수 도 있음
	
	인증(Authentication): 사용자가 주장하는 신원이 맞는지 확인(ID/비밀번호, MFA 2단계 인증, 소셜 로그인 등)

	인가(Authorization): 인증된 사용자가 자원에 접근할 권한이 있는 지 확인(읽기 전용 권한, 관리자 권한 부여 등)

	계정 관리): 신규 사용자의 계정 생성부터 권한 변경, 계정 삭제 및 비활성화까지의 수명 주기 관리

각자에게 필요한 권한만 설정 - policy

클라우드 보안의 기초이자 가장 강력한 통제 도구

개요		사용자의 직책/역할에 따라 권한 부여			사용자, 환경, 자원의 속성/조건에 따라 권한 부여
특징		구조가 단순하고 관리가 쉬움				세밀한 보안 정책 가능

IAM이 필요한 이유
	최소 권한의 원칙 적용: 사용자에게 업무에 필요한 최소한의 권한만 부여하여 보안 사고 발생 시 피해 범위를 최소화

	중앙 집중식 관리: 클라우드 및 기업 내 수 많은 시스템의 계정과 권한을 한 곳에서 통합 제어

	규정 준수 및 감사: 누가, 언제, 어떤 데이터에 접근하고 변경했는지에 대한 상세 기록(Audit Log)을 남겨서 법적/보안 규제를 충족 

대표적인 IAM 솔루션 및 서비스
	클라우드 IAM: AWS IAM, Google Cloud IAM, Microsoft Azure Entra ID
	기업용 IAM/SSO 솔루션: Okta, Ping Identity, Keycloak

- 최소 권한의 원칙
정보 보안의 가장 핵심적인 규칙 중 하나로 사용자, 프로세스, 프로그램에 주어진 업무나 임무를 수행하는데 필요한 최소한의 접근 권한 만을 부여해야 한다는 원칙

필요이상의 권한을 주지 말고 알 필요가 있는 정보 와 할 필요가 있는 행동에 대해서만 딱 맞게 허용하는 방식(Need-to-Know, Need-to-Do)

필요한 이유
	보안 사고 피해 최소화

	내부자 위협 방지

	실수 및 오류로 인한 데이터 손실 방지

	규정 준수

일상 및 IT 환경에서의 적용 예시
	루트 계정 사용 자체: 평소에는 일반 계정으로 작업하고 필요한 순간에만 권한 상승 명령어(sudo 등)를 사용

	AWS IAM 정책: 개발자에게 DB 접근 권한 전체(*)을 주는 대신 특정 테이블의 읽기 권한 만 부여

	스마트폰 앱 권한 요청

	DB 계정 분리: 계정을 이용해서 데이터베이스 또는 테이블 단위로 권한 설정을 해서 사용

최소 권한 원칙 이행 방법
	기본 거부(Default Deny)

	역할 기반 접근 제어(RBAC)

	적시 권한 부여(Just-In-Time Access): 필요할 때만 짧은 시간 동안 승인받아 사용

	정기적인 권한 감사(Access Review)

- 비밀번호나 키 관리 와 암호화
많은 개발자들이 실수하는 부분 중 하나가 비밀번호나 API키를 코드에 직접 적는 것인데 이 문제를 방지할려면 먼저 비밀정보를 코드와 분리해서 관리해야 함

환경 변수나 외부 설정 파일을 이용해서 비밀번호나 키를 별도로 관리

클라우드 서비스 제공자는 비밀 관리 서비스를 별도로 제공
	민감 정보를 암호화된 형태로 안전하게 저장

- 인증 토큰
사용자가 시스템에 신원(아이디/비밀번호)을 한 번 증명한 뒤 이후 요청에서 매번 비밀번호를 입력하지 않고 자격증명을 대신하기 위해 서버가 발급해주는 암호화된 인증성

가장 대표적인 인증 토큰이 JWT(JSON Web Token)

토큰 유형
	Access Token
		리소스에 접근하기 위한 실질적인 인증 권한을 담은 토큰
		유효기간을 짧게 설정해서 탈취 시 피해를 줄임

	Refresh Token
		Access Token이 만료되었을 때 Access Token을 재발급받기 위한 토큰
		유효기간을 길게 주고 서버 DB 나 저장소에 저장해서 관리

토큰 인증 방식의 장점 및 단점
	장점
		Stateless: 서버가 세션 상태를 저장하지 않아서 확장성이 뛰어남
		모바일/다중 플랫폼에 적합: CORS 문제 해결 및 REST API 와 완벽 호환
	단점
		탈취 위험: 클라이언트에 저장되므로 XSS/CSRF 공격 대비 필요
				XSS(Cross Site Scripting): 악성 스크립트를 웹 페이지에 삽입하는 공격
				CSRF(Cross-Site Request Forgery): 사용자가 로그인한 상태를 악용해서 사용자가 원하지 않는 요청을 보내게 만드는 공격
		강제 폐기 불가: 발급된 토큰은 만료전까지 서버에서 삭제하기가 어려움
	
- MFA
사용자가 로그인 하거나 시스템에 접근할 때 둘 이상의 서로 다른 인증 요소를 조합하여 신원을 검증하는 보안 방식

- 고가용성 구성
시스템, 서버, 네트워크 등이 장애가 발생하더라도 중단없이(또는 아주 짧은 시간) 서비스를 지속적으로 제공할 수 있는 능력

24시간 365일 멈추지 않고 계속 잘 작동하는 성질

가용성 지표: 가용성은 주로 몇 퍼센트의 시간동안 시스템이 정상 작동했는가로 측정을 하고 9의 개수로 보안 및 가동 수준을 표현
	99.9%: 연간 누적 장애 시간이 약 8.76 시간
	99.99%: 연간 누적 장애 시간 약 52.6분(일반적인 기업 기준)
	99.999%: 연간 누적 장애 시간 약 5.26분(금융, 통신, 의료 등의 핵심 인프라)

고가용성을 구현하는 3가지 핵심 원칙
	단일 장애점 제거(No Single Point of Failure): 시스템의 어느 한 부분이 고장나더라도 전체 서비스가 멈추지 않도록 설계

	이중화 및 이중 구성(Redundancy)
		서버, DB, 네트워크 장비, 전원 공급 장치 등을 최소 2개 이상 배치
		Active-Active: 여러 대가 동시에 처리하다가 하나가 죽으면 나머지가 부담
		Active-Standby: 하나는 일하고 하나는 대기하다가 장애가 발생하면 대기 중인 시스템이 즉시 전환되서 작업을 수행(Failover)

	장애 감지 및 자동 복구(Failover & Monitoring): 시스템 상태를 실시간으로 감시(Health Check)하다가 문제 발생 시 사람의 개입없이 자동으로 상시 대기 중인 시스템으로 전환

	서버 이중화
		Master-Slave 구조 또는 Read-Replica 구조
		Multi-Region Deployment: 지리적 이중화
	Load Balancer
		Health Check

	Disaster Recovery
		문제가 발생하면 서버를 자동으로 교체

재해복구 목표수립
	RPO(복구 시점 목표)
		장애 발생 시 허용할 수 있는 최대 데이터 손실 기준
		질문 기준: 어느 시점의 데이터 백업본으로 돌아갈 것인가? 데이터를 얼마나 잃어도 비지니스에 지장이 없는가?
		RPO=24시간: 하루에 한 번 백업	
		RPO=0: 실시간 동기 복제를 통해 장애 순간에도 데이터 손실이 0인 상태

	RTO(복구 시간 목표)
		장애 발생 시점부터 시스템이 정상 가동될 때 까지 허용되는 최대 복구 시간
		질문 기준: 서비스가 멈춘 후 다시 켜질 때 까지 얼마나 걸리는가? 다운타임을 얼마나 버틸 수 있는가?
		RTO = 4시간: 장애 발생 후 복구 작업, 서버 재부팅, 네트워크 전환 등을 마치고 4시간 이내에 정상화해야 함을 의미
		RTO = 0: 장애 즉시 대기 시스템으로 자동 전환되어 사용자가 장애를 인식하지 못하는 수준

IT 인프라 운영관리 de facto(사실 상의 표준)로 전 세계 IT 서비스 기업의 운영 방법론으로 자리잡음

2019년 ITIL v4 부터 Agile, Lean, DevOps 등의 방법론 과의 연계성을 강화한 Service Value System 개념으로 전체 체계 변화

- DevOps 개요
IT 서비스 설계, SW 개발, 릴리즈 및 운영에 이르기까지 전체 서비스 수명 주기에 함께 참여하는 IT 서비스 운영 및 개발 엔지니어의 업무 방식

하나의 팀이 애플리케이션 개발에서 프로덕션 운영에 이르는 전체 프로세스를 소유하는 방법론

일련의 기술 구현을 넘어서 문화 와 프로세스의 완전한 변화를 요구

DevOps는 전체 기능이 아닌 작은 구성 요소에서 작업하는 엔지니어 그룹을 요구하여 오류 소스인 핸드 오프를 줄임

DevOps는 Development 와 Opertions 의 합성어로서 소프트웨어 개발자와 정보 기술 전문가 간의 소통, 협업 및 통합을 강조하는 개발 환경이나 문화
 
소프트웨어 제품과 서비스를 빠른 시간에 개발 및 배포하는 것이 목적

- Tool Chain
Plan - 목적을 수행하기 앞서 방법이나 절차 등을 미리 생각하여 계획

Code - 코드 개발 및 검토, 버전 관리 도구, 코드 병합

Build - 지속적 통합 도구, 빌드 상태

Test

Package - 배포할 애플리케이션을 생성

Release(Deploy) - 변경 사항 관리, 릴리스 승인, 릴리스 자동화

Operate - 운영

Monitoring - 애플리케이션 성능 모니터링, 최종 사용자 경험

- DevOps로의 변화

Service Orientied Architecture(SOA) 	-> Microservices				-> Functional Microservices

Agile Teams 				-> Mode 2, DevOps, Agile Mindset	-> Enterprise DevOps

Cloud Infra Automation			-> CI/CD					-> DevOps Automation

- DevOps 이점
속도(Agile) - Time to Market, Microservices
신속한 배포 - CI/CD
안정성 - 모니터링 과 로깅
확장 - IaC
협업 강화 - CLAMS
보안 - Policy as Code, 코드형 정책

- DevOps 생태계
Code & Build: git(GitHub, GitLab), JACOCO, docker, kubernetes

CI/CD: github action, git lab ci, Jenkins, Argo CD

Test: 단위 테스트(JUnit, pytest), API 테스트(Postman), 웹 UI 테스트(Selenium), 성능/부하테스트(JMeter, k6), 모바일 테스트(Appium), 통합 테스트(Testcontainers), 테스트 관리(Jira + Xray), 정적 코드 분석(Sonarqube), 코드 커버리지 도구(JaCoCo)

Operate: Jira, mantis

Deploy: Docker, Kubernetes
