2)Pod
=>개요
- Kubernetes의 기본 배포 단위로 다수의 컨테이너가 모인 집합체
- 하나의 Pod는 한 개 이상의 컨테이너로 구성되며 하나의 파드에 여러 개의 컨테이너를 포함시킬 수 있는데 이러한 구조를 사이드카 패턴이라고 합니다.
- 하나 이상의 컨테이너로 애플리케이션을 구축하다 보면 nginx 와 go application 처럼 서로 강한 결합을 유지하는 쪽이 더 나은 경우가 있는데 쿠버네티스에서는 이렇게 결합이 강한 컨테이너를 하나로 묶어서 배포
- 동일한 파드에 포함된 컨테이너끼리는 네트워크적으로 격리되어 있지 않고 IP 주소를 공유
- 동일한 파드에 포함된 컨테이너끼리는 localhost로 통신이 가능

=>파드의 디자인 패턴
- Sidecar Pattern
메인 컨테이너 외에 보조적인 기능을 추가하는 서브 컨테이너를 포함하는 패턴
데이터 영역을 공유할 수 있기 때문에 대부분 데이터 와 설정에 관련된 패턴

- Ambassador Pattern
메인 컨테이너가 외부 시스템과 접속할 때 대리로 중계해주는 서브 컨테이너(앰버서더)를 포함한 패턴
메인 컨테이너가 목적지로 localhost를 지정해서 앰버서더 컨테이너에 접속 하는 형태
메인 컨테이너가 데이터베이스 하나를 선택해서 접속을 하게되면 메인 컨테이너는 데이터베이스와 결합도가 강해짐

- Adapter Pattern
데이터 형식을 변경해주는 컨테이너(어댑터)를 포함하는 패턴
메트릭을 수집하는 컨테이너들은 특별한 형태의 데이터를 수집하는데 이 형식에 맞추어 주는 별도의 컨테이너를 갖는 방식
예전 웹 프로그래밍에서 많이 사용
예전 웹 프로그래밍에서는 주로 XML 형식의 데이터를 반환했는데 지금은 JSON 형식의 데이터를 많이 사용

=>파드 생성

kind: Pod
metadata:
  name: 이름
spec:
  containers:
  옵션

- 파드 생성을 위한 yaml 파일 생성:sample-pod.yaml

=>컨테이너 실행과 관리
- 쿠버네티스가 직접 컨테이너를 실행하지 않음
- 컨테이너를 생성할 책임을 해당 노드에 설치된 컨테이너 런타임에 맡기는 형태
- 컨테이너 런타임은 containerd 나 docker가 될 수 있음
- 파드는 쿠버네티스가 관리하는 리소스고 컨테이너는 쿠버네티스 외부에서 관리하는 형태

=>stateless & stateful
- stateless는 사용자가 애플리케이션을 사용할 때 상태나 세션을 저장해 둘 필요가 없는 애플리케이션에서 사용
- stateful은 사용자가 애플리케이션을 사용할 상태나 세션을 별도의 데이터베이스에 저장해야 하는 애플리케이션에서 사용

=>ENTRYPOINT 와 CMD
- 도커 파일로 이미지를 생성할 때는 ENTRYPOINT 명령과 CMD 명령을 사용해서 컨테이너 실행 시 명령어를 정의하는데 쿠버네티스에서는 도커용 용어와 다르게 ENTRYPOINT를 command 로 CMD를 args라고 부름
-컨테이너를 실행할 때 도커 이미지의 ENTRYPOINT 와 CMD를 덮어쓰기를 하려면 파드 정의 내용 중 spec.containers[ ].command 와 spec.containers[].args를 지정

- 매니페스트 파일: sample-entrypoint.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-entrypoint
spec:
  containers:
  - name: nginx-container
    image: nginx
    command: ["/bin/sleep"]
    args: ["3600"]

- 배포: kubectl apply -f sample-entrypoint.yaml

- 파드에 접속: kubectl exec -it sample-entrypoint -- /bin/sh

- 프로세스 실행 확인
apt update

apt -y install procps

ps aux

- 이용 가능한 문자는 영문 소문자와 숫자
- 이용 가능한 기호는 - 와 .
- 시작과 끝은 영문 소문자

=>호스트의 네트워크를 사용하는 파드 생성
- 파드에 할당된 IP는 쿠버네티스 노드의 호스트 IP와 범위가 달라서 외부에서 볼 수 없는 IP 주소가 할당됨
- spec.hostNetwork를 활성화하면 호스트 상에서 프로세스를 기동하는 것과 같은 네트워크 구성으로 파드를 기동시킬 수 있음
- 포트 충돌이 발생할 수 있으므로 주의

=>작업 디렉토리 설정
- Dockerfile에서는 WORKDIR로 설정했는데 spec.containers[].workingDir로 덮어슬 수 있음

2)ReplicaSet
=>개요
- ReplicaSet은 일정한 개수의 Pod가 항상 실행되도록 관리하는데 이러한 기능이 필요한 이유는 서비스의 지속성 때문
- 노드의 하드웨어에서 발생하는 장애 등의 이유로 Pod를 사용할 수 없을 때 다른 노드에서 Pod를 다시 생성해서 사용자에게 중단없는 서비스를 제공할 수 있음
- 원래 파드의 레플리카를 생성하는 리소스의 이름은 ReplicationController 였는데 레플리카셋을 추가하고 일부 기능을 추가
- 최근에는 ReplicaSet을 권장

=>생성
- 매니페스트 파일 생성: sample-rs.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: sample-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx

- 배포: kubectl apply -f sample-rs.yaml

- 확인
kubectl get pods
kubectl get replicasets

- 레플리카 셋이 만드는 파드의 이름 레플리카이름-임의의문자열

=>레플리카 셋에서는 노드나 파드에 장애가 발생했을 때 지정한 파드 수를 유지하기 위해서 다른 노드에서 파드를 기동시켜 줍니다.

=>증감 이력 확인: kubectl describe replicaset sample-rs

=>레플리카셋과 레이블
- 레플리카셋은 쿠버네티스가 파드를 모니터링해서 파드 수를 조정
- 모니터링은 특정 레이블을 가진 파드 수를 계산하는 형태로 이루어 짐
- 레플리카 수가 부족한 경우 매니페스트에 기술된 spec.template 으로 파드를 생성하고 레플리카 수가 많을 경우 레이블이 일치하는 파드 중 하나를 삭제
- 2개의 레이블을 다르게 생성: sample-rs-fail.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: sample-rs-fail
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app-fail
    spec:
      containers:
      - name: nginx-container
        image: nginx
- 배포: kubectl apply -f sample-rs-fail.yaml
- 에러
The ReplicaSet "sample-rs-fail" is invalid: spec.template.metadata.labels: Invalid value: map[string]string{"app":"sample-app-fail"}: `selector` does not match template `labels`

- 레플리카 셋과 동일한 레이블을 가진 파드를 생성
매니페스트 파일: sample-rs-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-rs-pod
  labels:
    app: sample-app
spec:
  containers:
  - name: nginx-container
    image: nginx

배포: kubectl apply -f sample-rs-pod.yaml

배포는 성공했다고 메시지는 출력되지만 실제로 만들어지지는 않습니다.
동일한 레이블로 시작하기 때문에 레플리카셋은 이미 3개가 있으므로 더 이상 생성하지 않습니다.

=>스케일링 조정
- 매니페스트를 수정해서 다시 배포
- kubectl scale 명령어를 사용

3)Deployment
=>개요
- 여러 레플리카셋을 관리하여 롤링 업데이트나 롤백을 구현하는 리소스
- Deployment가 레플리카셋을 관리하고 레플리카셋이 파드를 관리하는 관계
- Deployment는 ReplicaSet의 상위 개념으로서 Pod의 개수를 유지할 뿐 아니라 배포 작업을 좀 더 세분화해 관리할 수 있음
- Deployment를 사용하면 신규 레플리카 셋에 컨테이너가 기동되었는지 와 헬스 체크는 통과했는지를 확인하면서 전환 작업이 진행되며 레플리카셋의 이행과정에서 파드 수에 대한 상세한 지정도 가능
- 쿠버네티스에서 가장 권장하는 컨테이너 기동 방법
- 하나의 파드를 기동만 하는 경우라도 파드로만 배포한 경우에는 장애가 발생하면 자동으로 파드가 다시 생성되지 않으면 레플리카 셋으로 배포한 경우에는 롤링 업데이트의 기능을 사용할 수 없음

=>Deployment 배포
- 매니페스트 파일 생성: sample-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx

- 배포: kubectl apply -f sample-deployment.yaml

=>이미지 업데이트
kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record

=>레플리카 셋이 생성되는 조건
- 레플리카의 수의 변경은 새로운 레플리카 셋이 만들어지지 않음
- 파드의 내용이 변경이 되야 새로운 레플리카 셋이 만들어지고 롤링 업데이트를 수행
- 수작업으로 이미지를 이전 버전으로 재변경하면 새로운 레플리카 셋을 만들지 않고 기존 레플리카 셋을 사용

=>파드의 삭제 및 복구 과정
Deployment를 배포하면 레플리카 셋을 감시
파드의 수의 차이가 발견되면 상태를 변경(파드를 추가하거나 삭제)
변경 완료 후 감시

=>변경 롤백
- Deployment에는 롤백 기능이 있음
- 롤백은 레플리카 셋의 전환
- 이전에 있던 레플리카 셋의 레플리카 수가 0인 상태로 남아있는데 이 수를 변경시켜서 다시 사용할 수 있는 상태로 만듬
- 변경 이력을 확인할 때는 kubectl rollout history 명령을 사용
kubectl rollout history deployment sample-deployment
- 버전에 대한 상세 이력 확인
kubectl rollout history deployment sample-deployment --revision 넘버
- 버전 번호를 이용해서 롤백
kubectl rollout undo deployment sample-deployment --to-revision 넘버
- 바로 이전 버전으로 롤백
kubectl rollout undo deployment sample-deployment

=>변경 일시 중지
- kubectl rollout pause deployment sample-deployment

- 이미지 변경(실제로는 수행되지 않음): kubectl set image deployment sample-deployment nginx-container=nginx:1.17 

- 이전 버전으로 되돌리기(에러): kubectl rollout status deployment sample-deployment

- 일시 정지 해제: kubectl rollout resume deployment sample-deployment

=>스케일링
- 매니페스트 파일의 replicas를 변경을 해서 kubectl apply로 적용해도 되고 kubectl scale을 이용하는 것도 가능
kubectl scale deployment sample-deployment --replicas=5

=>deployment를 매니페스트를 이용하지 않고 생성
kubectl create deployment sample-deployment-by-cli --image nginx

4)DaemonSet
=>개요
- ReplicaSet의 특수한 형태
- 모든 노드에 Pod를 생성
- ReplicaSet이 특정 개수의 Pod를 유지하기 위해서 사용하는 반면 모든 노드에 1개씩 배치되는 Pod를 배포할 때 사용
- 레플리카 수를 지정할 수 없고 하나의 노드의 두 개의 파드를 배치할 수 도 없음
- 파드를 배치하고 싶지 않은 노드가 있을 경우 nodeselector나 노드 안티어피니티를 사용한 스케쥴링으로 예외 처리
- 노드를 늘렸을 때 자동으로 늘어난 노드에서 기동
- Fluentd 같은 로그 수집 도구나 노드 상태를 모니터링하는 Datadog이나 Prometheus 등에 사용
=>생성
- 매니페스트 작성: sample-daemonsets.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: prometheus-daemonset
spec:
  selector:
    matchLabels:
      tier: monitoring
      name: prometheus-exporter
  template:
    metadata:
      labels:
        tier: monitoring
        name: prometheus-exporter
    spec:
      containers:
      - name: prometheus
        image: prom/node-exporter
        ports:
        - containerPort: 80

- 배포: kubectl apply -f sample-daemonsets.yaml

5)StatefulSet
=>StatefulSet도 DaemonSet과 마찬가리로 레플리카셋의 특수한 형태라고 할 수 있는 리소스
=>데이터베이스 등 과 같은 stateful한 워크 로드에 사용하기 위한 리소스
=>ReplicaSet 과 차이점
- 생성되는 파드명의 접미사는 숫자 인덱스가 부여됨
- 파드명이 바뀌지 않음
- 데이터를 영구적으로 저장하기 위한 구조
- spec.volumeClaimTemplates을 이용해서 영구 볼륨 클레임을 설정할 수 있고 영구 볼륨 클레임을 사용하면 클러스터 외부의 네트워크를 통해 제공되는 영구 볼륨을 파드에 연결할 수 있기 때문에 파드를 재기동할 때나 다른 노드로 이동할 때 같은 데이터를 보유한 상태로 컨테이너가 다시 생성되고 영구 볼륨은 하나의 파드가 소유할 수 도 있고 영구 볼륨 종류에 따라 여러 파드에서 공유할 수 도 있음
=>생성
- 매니페스트 파일: sample-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: sample-statefulset
spec:
  serviceName: sample-statefulset
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx.html
  volumeClaimTemplates:
    - metadata:
        name: www
      spec:
        accessModes:
        - ReadWriteOnce
        resources:
          requests:
            storage: 1G

- 리소스 배포: kubectl apply -f sample-statefulset.yaml

- 확인: kubectl get statefulsets

- 스케일을 변경하면 일련번호 순서대로 생성되고 제거해야 하는 경우는 일련번호가 높은 것 부터 제거

=>라이프사이클
- spec.podManagementPolicy를 Parallel로 설정하면 레플리카셋 등과 병렬로 동시에 파드를 기동시킬 수 있음
- 기본값은 OrderedReady로 순차적으로 생성됩니다.
=>병렬로 생성하는 StatefulSet: sample-stateful-parallel.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: sample-statefulset-parallel
spec:
  podManagementPolicy: Parallel
  serviceName: sample-statefulset-parallel
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx
