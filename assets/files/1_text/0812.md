=>소스 애플리케이션 과 타깃 애플리케이션을 연결하는 파이프라인의 개수가 많아지면서 소스 코드 및 버전 관리에서 이슈가 생겼고 타깃 애플리케이션에 장애가 발생할 경우 그 영향이 소스 애플리케이션에 그대로 전달됨

=>큐에 데이터를 전송하는 것이 프로듀서이고 큐에서 데이터를 가져가는 것이 컨슈머

=>Big Data 나 Data Pipeline 구축하는 곳에서는 거의 필수 요소

from kafka import KafkaProducer
import json


#프로듀서 클래스
class MessageProducer:
    #프로듀서 초기화
    #broker는 브로커 위치
    #topic은 토픽 이름
    def __init__(self, broker, topic):
        self.broker = broker
        self.topic = topic
        self.producer = KafkaProducer(
            bootstrap_servers = self.broker,
            value_serializer = lambda x:json.dumps(x).encode("utf-8"),
            acks=0,
            api_version=(2, 5, 0),
            key_serializer=str.encode,
            retries=3
        )

    def send_message(self, msg, auto_close=True):
        try:
            #send는 버퍼에 전송
            future = self.producer.send(self.topic, value=msg, key="key")
            #실제 전송은 버퍼가 가득차거나 flush를 호출해야 전송됩니다.
            self.producer.flush()
            if auto_close:
                self.producer.close()
            future.get(timeout=2)
            return {"status_code":200, "error":None}
        except Exception as exc:
            raise exc

#브로커와 토픽명을 지정

2.MySQL, Mongo DB, Spring Boot, Kafka를 이용한 CQRS 구현    
0)CQRS
=>개요
- Command and Query Responsibility Segregation의 약자로 데이터 저장소로부터 읽기 와 업데이트 작업을 분리하는 패턴
- 애플리케이션의 퍼포먼스, 확장성, 보안성을 극대화 할 수 있고 여러 요청으로부터 들어온 복수의 업데이트 명령에 대한 충돌도 방지할 수 있음

=>전통적인 방식의 문제점
- 전통적인 아키텍쳐에서는 데이터베이스에서 데이터를 조회하고 업데이트하는데 같은 데이터 모델을 사용
- 복잡한 애플리케이션에서 이러한 접근 방식은 유지보수를 어렵게 만들 수 있는데 데이터를 조회할 때 사용하는 데이터의 형태가 다르다면 각기 다른 형태의 DTO(Data Transfer Object - 데이터를 이동할 때 사용하는 클래스)를 반환하는 매우 다양한 쿼리들을 수행할 수 있는데 각각 다른 DTO 들에 매핑을 하는 것은 복잡해 질 수 있고 데이터를 쓰거나 업데이트를 할 때는 복잡한 유효성 검사와 비즈니스 로직도 수행해야 하는데 이 모든 걸 하나의 데이터 모델이 한다면 너무 많은 것을 수행하는 복잡한 모델이 되는 것
- 읽기 와 쓰기의 부하는 일반적으로 동일하지 않기 때문에 각각에 대해 다른 성능이 요구됨
- 읽기 와 쓰기의 작업에서 사용되는 데이터 표현들이 서로 일치하지 않는 경우가 많은데 그로 인해 일부 작업에서는 필요하지 않은 추가적인 컬럼이나 속성의 업데이트가 이루어져야 하는 경우가 있음
- 동일한 데이터 세트에 대해 병렬로 작업이 수행될 때 데이터 경합이 발생
- 정보 조회를 위해 요구되는 복잡한 쿼리로 인해 성능에 부정적인 영향을 줄 수 있음

=>해결책
- 읽기와 쓰기를 각각 다른 모델로 분리하는데 Command를 이용해서 데이터를 수정하고 Query를 이용해서 데이터를 조회
- Command는 데이터 중심적이 아니라 작업 중심이 되어야 함
- Command는 동기적으로 처리되기보다는 비동기적으로 큐에 쌓인 후 진행
- Query는 절대로 데이터베이스를 수정하지 않고 어떠 도메인 로직도 캡슐화하지 않은 DTO만을 반환
- CQRS를 이용하는 경우 ORM 툴을 통해서 DB 스키마로부터 자동으로 생성되도록 할 수 없다는 단점이 있음
- 작업에 특화된 데이터베이스를 사용하는 것이 가능

=>장점
- 독립적인 스케쥴링
- 최적화된 데이터 스키마를 사용: 읽기 저장소는 쿼리에 최적화된 스키마를 사용할 수 있고 쓰기 저장소는 쓰기에 최적화된 스키마를 사용할 수 있음
- 보안
- 관심사 분리: 대부분의 복잡한 비즈니스 로직은 쓰기 모델에 들어가고 읽기 모델은 상대적으로 간단한 조회 로직만 포함
- 간단한 쿼리: 읽기 저장소의 materialized view를 통해 복잡한 조인문을 사용하지 않을 수 있음

=>구현 이슈
- 복잡성: 아이디어는 간단하지만 이 패턴은 이벤트 소싱 패턴을 포함할 경우 복잡해 질 수 있음
- 메세징: 명령을 수행하고 업데이트 이벤트를 발행하는 것이 보편적인 사용법인데 이 경우 애플리케이션은 반드시 메시지 실패나 중복 메시지 처리를 해야 함
- 데이터 일관성

=>구현해야 하는 경우
- 많은 사용자가 동일한 데이터에 병렬로 엑세스 하는 경우
- 복잡한 프로세스나 도메인 모델을 통해 가이드 되는 작업 기반 사용자 인터페이스
- 데이터의 읽기의 성능이 데이터 쓰기의 성능과 별도로 조정이 가능해야 할 때
- 쓰기 와 읽기를 분리해서 구현하고자 할 때 
- 하나의 시스템이 장기간 여러 버전을 가질 수 있고 정기적으로 수정되는 경우
- 다른 시스템과 통합할 때

=>서비스 클래스를 생성: BookService
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

import java.text.SimpleDateFormat;
import java.util.Date;
import java.util.Locale;

@Service
@RequiredArgsConstructor
public class BookService {
    private final BookRepository bookRepository;

    public void saveBook(BookDTO bookDTO){
        try {
            SimpleDateFormat formatter = new SimpleDateFormat(
                    "yyyy-MM-dd", Locale.ENGLISH);
            Date published_date = formatter.parse(bookDTO.getPublished_date());
            Book book = Book.builder()
                    .title(bookDTO.getTitle())
                    .author(bookDTO.getAuthor())
                    .category(bookDTO.getCategory())
                    .pages(bookDTO.getPages())
                    .price(bookDTO.getPrice())
                    .published_date(published_date)
                    .description(bookDTO.getDescription())
                    .build();
            bookRepository.save(book);
        }
        catch(Exception e){
            System.out.println(e.getMessage());
        }
    }
}

import com.mongodb.client.*;
import lombok.RequiredArgsConstructor;
import org.bson.Document;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import java.util.ArrayList;
import java.util.List;

@RestController
@RequiredArgsConstructor
public class BookController {
    @GetMapping("/cqrs/book")
    public ResponseEntity<List> getBooks(){
        MongoClient mongoClient = MongoClients.create("mongodb://localhost:27017");
        MongoDatabase database = mongoClient.getDatabase("mymongo");
        MongoCollection<Document> mongo_books =
                database.getCollection("books");
        List<Document> list = new ArrayList<Document>();
        
        try{
            try(MongoCursor<Document> cur = mongo_books.find().iterator()){
                while(cur.hasNext()){
                    Document doc = cur.next();
                    list.add(doc);
                }
            }
        }catch(Exception e){
            e.printStackTrace();
        }
        finally{
            mongoClient.close();
        }
        return ResponseEntity.status(HttpStatus.OK).body(list);
    }
}
