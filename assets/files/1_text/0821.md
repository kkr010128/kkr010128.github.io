8)Load Balancer
=>개요
- 서버에 가해지는 부하를 분산해주는 장치 또는 기술
- 클라이언트 와 서버 풀(server poll) 사이에 위치하며 한 대의 서버로 부하가 집중되지 않도록 트래픽을 관리해서 각각의 서버가 최적의 퍼포먼스를 보일 수 있도록 해주는 기술
- 리소스 활용도를 최적화하고 처리량을 최대화하면 지연 시간을 줄이고 내결함성 구성을 보장하기 때문에 안정적인 시스템 운영에 도움이 됨
- docker는 HaProxy, Nginx/Apache Load Balancer 등 외부 서비스와 컨테이너를 결합한 Load Balancing 구현이 가능

=>LoadBalancing 알고리즘
- Round Robin: 클라이언트의 요청을 번갈아가면서 순서대로 처리하는 알고리즘인데 서버 가중치 설정이 가능

- Least Connetions: 현재 연결된 클라이언트 수가 가장 적은 서버로 요청 전달

- IP Hash: 해시키를 이용해서 IP별 INDEX를 설정해서 동일한 IP는 동일 서버로 경로를 보장하는 알고리즘, 해당 서버 장애 시 주소가 변경되고 균등 배분 보장 안됨

- General Hash: 사용자가 정의한 키(Port, URI 문자열 등)를 이용해서 서버를 지정

- Least Time: 요청에 대한 낮은 지연시간을 이용
header: 서버의 첫번째 바이트를 받는 시간 기준
last_byte: 서버에서 전체 응답을 받는 시간 기준
last_byte_inflight: 실패한 요청을 고려한 응답을 받는 시간 기준

- Random

=>nginx Load Balancing 관련 파라미터
- weight: 가중치로 기본값은 1
- max_connes, queue: 최대 클라이언트 연결 수 지정과 대기열 생성
- max_fails: 최대 실패 횟수를 지정하는 것으로 설정한 횟수 이상 실패하면 서버를 분배 대상에서 제외
- backup: 평소에는 동작하지 않고 모든 서버가 동작하지 않을 때 사용 
- down: down 키워드가 있는 서버는 사용하지 않지만 ip_hash 인 경우 사용

10.Docker Swarm
1)개요
=>여러 도커 호스트를 클러스터로 묶어주는 오케스트레이션 도구
=>컨테이너 오케스트레이션 도구 없이는 도커 호스트 여러 대를 사용하는 확장성있는 애플리케이션을 만들기가 어려움
=>어느 도커 호스트에 어떤 컨테이너를 배치해야 하는지 서로 다른 호스트에 위치한 컨테이너 간의 통신은 어떻게 제어해야 할 지를 조율하는 것은 쉽지 않은 일

=>용어
- docker-compose: 여러 컨테이너로 구성된 도커 애플리케이션을 관리하는 것으로 주로 단일 호스트
- docker swarm: 클러스터 구축 및 관리로 멀티 호스트에서 사용
- docker service: 스웜에서 클러스터 안의 서비스
- docker stack: 스웜에서 여러 개의 서비스를 합한 전체 애플리케이션

=>주요 기능
- 역할이 분리된 분산 설계
역할 종류
	manager node
	leader node
	worker node

단일 관리자 환경이라면 manager node 와 worker node로 분리해서 manager node가 전문적 관리를 수행하고 worker node가 도커 호스트의 역할을 수행

manager node가 여러 개라면 manager node는 중 하나를 리더 매니저 노드로 구성해서 관리

manager node가 클러스터의 관리 역할을 수행하는데 컨테이너 스케쥴링 및 상태 유지 등을 제공하고 작업자 노드는 컨테이너를 실행하는 역할만 수행

쿠버네티스와 비교해보면 쿠버네티스의 매니저 노드인 마스터 노드는 컨테이너 서비스를 제공하지 않지만 도커 스웜의 매니저 노드는 작업자 노드의 역할을 수행할 수 있음

관리 역할을 수행하는 노드의 부하를 고려해서 각 역할은 분리해서 사용하기를 권장하는데 서비스를 생성 시 --constraint node_role!=manager 옵션을 사용하면 manager 노드에서는 서비스 컨테이너를 수행하지 않도록 합니다.

- 도커 엔진과 통합된 다중 서버 클러스터 환경 구성: 별도의 오케스트레이션 도구를 설치할 필요가 없음

- 서비스 확장과 원하는 상태 조정
Replicas Option을 이용해서 중복된 서비스 배포 가능

초기 구성 후 스웜 관리자를 이용해서 애플리케이션의 가용성에 영향을 주지 않고 서비스 확장 및 축소를 수행할 수 있음

배포된 서비스는 매니저 노드를 통해서 지속적으로 모니터링

사용자가 요청한 상태와 다르게 서비스 장애가 생길 경우 장애가 발생한 서비스를 대체할 새로운 복제본을 자동으로 생성해서 사용자 요구를 지속하게 되는데 이것이 요구 상태 관리(desire state management)

대부분의 오케스트레이션 도구의 목적이 요구 상태 관리

- 서비스 스케쥴링
서비스 컨테이너를 배포하는 작업

노드 선택 전략은 swarm manage --strategy 옵션 을 이용해서 설정
	spread: 모든 작업자 노드에게 균등하게 분산
	binpack: 작업자 노드의 자원 사용량을 고려하여 할당하는 자원대비 전략
	random: 무작위

도커 스웜 모드는 단일 옵션으로 고가용성 분산 알고리즘을 사용하느네 생성되는 서비스의 복제본을 분산 배포하기 위해서 현재 복제본이 가장 적은 작업 노드 중에서 이미 스케쥴링된 다른 서비스 컨테이너 수가 가장 작은 작업자 노드를 우선 선택

- 로드 밸런싱
도커 스웜 모드를 초기화 하면 자동으로 생성되는 네트워크 드라이버 중 하나가 Ingress Network

Ingress Network는 서비스의 노드 간 load balancing 과 외부에 서비스를 노출하기 위한 overlay network

도커 스웜 모드는 서비스 컨테이너에 publishedport를 자동으로 할당(30000~32767)하거나 수동 노출할 포트를 구성할 수 있고 서비스 컨테이너가 포트를 오픈하면 동시에 모든 노드에 있는 동일한 포트가 오픈되고 이로 인해서 클러스터에 합류되어 있는 어떤 노드에 요청을 전달해도 실행 중인 서비스 컨테이너에 자동 전달되는데 모든 노드가 스웜 모드의 routing mesh에 참여하기 때문

worker node 1 과 worker node 2 두 개의 워커노드가 있고 컨테이너를 복제하지 않고 1개만 배포를 한 경우 worker node 1에 배치되어 있다고 가정을 하고 요청을 worker node 1에게 보내면 처리가 되는 것이 당연한데 오케스트레이션 도구에서는 worker node 2에게 요청을 해도 처리가 됩니다.

- 서비스 검색
도커 스웜 모드에서는 서비스 검색을 위해 자체 DNS 서버를 통한 서비스 검색 기능을 제공

도커 스웜 매니저 노드는 클러스터에 합류된 모든 노드의 서비스에 고유한 DNS 이름을 부여하고 할당된 DNS 이름은 도커 스웜 모드 안에서 내장된 DNS 서버를 통해서 해석이 되는데 이를 service discovery 라고 합니다.

- Rolling Update
도커 스웜은 현재 실행 중인 서비스 컨테이너를 업데이트하는 경우 노드 단위로 점진적으로 적용할 수 있는 Rolling Update를 제공

업데이트를 하는 경우 새로운 서비스 컨테이너를 먼저 생성해서 헬스 체크를 하고 서비스가 정상적으로 구동이 되면 이전 서비스 컨테이너를 삭제하는 방식으로 동작하는 업데이트

기본적으로 하나를 먼저 만들고 하나를 삭제하는 구조지만 여러 개를 한꺼번에 만들 수 도 있고 삭제를 먼저 할 수 도 있습니다.

업데이트를 실패하면 자동적으로 이전 정상적인 상태로 롤백이 됩니다.

=>쿠버네티스와의 차이
- 기능이 간단한 컨테이너 오케스트레이션 도구로 설계
- 네트워크 와 서비스의 개념을 도커 컴포즈에서 차용해 오케스트레이션 도구로서 도커 엔진에 안정적으로 동작
- 쿠버네티스는 주요 클라우드 서비스에서 매니저드 서비스 형태로 많이 제공
- 쿠버네티스는 확장성이 뛰어나서 클라우드 사업자가 로드밸런서, 스토리지 등과 같은 애플리케이션 배포를 지원하는 자사 프로덕트와 통합하기에 유리
- 현재까지 도커 스웜을 매니지드 서비스로 제공하는 클라우드 업체는 없음
- 클라우드 환경에서 도커 스웜을 사용하고자 하면 클러스터를 직접 구축해야 함
- 쿠버네티스 보다 쉽다.
