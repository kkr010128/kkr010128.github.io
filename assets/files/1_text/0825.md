1)Container Runtime
- 개요
일반적인 가상화 소프트웨어는 하드웨어 수준에서 가상화를 하지만 Container 가상화는 운영체제 차원에서 가상화
Container는 운영체제의 커널을 공유하기 때문에 상대적으로 가볍고 유연하게 운영 가능
가상머신과 비교하면 자원을 더 적게 사용해서 하나의 시스템에서 더 많은 애플리케이션을 구동할 수 있음
런타임은 프로그래밍 언어가 구동되는 환경을 의미하는데 자바스크립트가 브라우저에서 실행되면 런타임은 브라우저
Container를 생성하고 실행할 수 있도록 해주는 것이 Container Runtime

- 종류
Containerd
	컨테이너  실행을 관리하는 오픈 소스 런타임
	Docker 및 Kubernetes 와 컨테이너 오케스트레이션 시스템에서 컨테이너 실행을 처리하는데 사용
	Container 이미지를 다운로드 받아 압축을 푸는 과정부터 Container를 실행하고 감독하는 과정까지 Container의 전체 수명 주기를 관리하는 기능을 제공

Docker
	Containerd 위에 설치되는 데몬
	Container를 생성하고 관리하는데 필요한 모든 기능을 제공
	Docker는 컨테이너의 전체 라이프사이클(빌드, 배포, 실행)을 관리하는 반면 Containerd는 컨테이너 실행과 이미지 관리를 담당하는 핵심 컴포넌트로 Docker는 내부적으로 Containerd를 사용하며 Kubernetes도 Containerd를 기본 런타임으로 지원 

CRI-O
	RedHat, Intel, SUSE, IBM 등의 관리자 및 커뮤니티를 중심으로 개발된 오픈 소스 런타임
	CRI-O는 Docker를 대체하기 위한 툴로 개발

2)Container Orchestration

- Container를 효과적으로 관리할 수 있도록 도와주는 것이 Container Orchestration
- 여러 시스템에 컨테이너를 분산해서 배치하거나 문제가 생긴 컨테이너를 교체하는 등 여러 역할을 수행

- 무중단 서비스: 
- 효율적인 자원 사용: 컨테이너 별로 리소스 설정이 가능하고 트래픽 라우팅은 Service 와 Ingress가 담당

5)쿠버네티스 아키텍쳐
=>Pod
- 하나의 애플리케이션을 생성하기 위해서 하나 이상의 Pod가 필요한데 Pod는 Kubernetes에서 생성할 수 있는 가장 작은 배포단위이면서 단일 혹은 다수의 Container를 포함
- Pod 외에 Service, Volume, Namespace 등을 묶어서 Object 라고 하고 Object는 Kubernetes에서 상태 관리가 필요한 대상
- Pod 와 Container
Pod는 쿠버네티스에서 가장 기본적인 배포 단위이면서 하나 이상의 Container를 포함
Kubernetes는 컨테이너를 개별적으로 하나씩 배포하는 것이 아니고 유사한 역할을 수행하는 Container들을 Pod라는 단위로 묶어서 배포
웹 사이트를 만들고자 하면 사용자가 데이터를 검색하고 수정하는 애플리케이션과 데이터를 저장하는 데이터베이스가 있는데 이 둘은 서로 유기적인 관계를 갖기 때문에 별도의 Container지만 하나의 Pod로 묶어서 배포

=>Kubernetes 구조
- Cluster: 여러 리소스를 관리하기 위한 집합체로 Master Node 와 Worker Node를 이용해서 하나의 Cluster를 구성
- Node
컨테이너가 배치되는 대상
쿠버네티스 클러스터에서는 하나 이상의 Master가 존재해야 합니다.
클러스터는 Master 와 노드의 그룹으로 구성
클러스터 안에 마스터 노드와 워커 노드를 두고 별도의 영역에 영구 스토리지(Persistent Storage)를 가지는 형태로 구성

- Master Node
쿠버네티스 클러스터 전체를 관리하는 시스템으로 Control Plane 이라고도 함
이 컴퓨터에는 kubectl을 설치하는데 이를 이용해서 초기 설정을 진행하거나 추후 조정을 수행

- Persistent Storage
Pod는 휘발성이라서 삭제되면 모든 데이터가 같이 삭제되기 때문에 중요한 데이터는 Pod 외부에 있는 저장소에 저장해 두어야 하며 CSI(Container Storage Interface)로 외부 저장소를 Pod에 연결할 수 있음

- Worker Node
Container Runtime이 설치된 환경으로 Pod가 실제로 생성되고 유지되는 Node

7)Kubenetes Component
=>Master Node에는 etcd, API Server, Controller Manager, Scheduler 등이 존재하고 Worker Node에는 Proxy, kubelet, Container Runtime 등이 존재

=>kubectl
- 쿠버네티스에 명령을 내리는 역할 수행
- 다른 구성 요소들과 달리 바로 실행되는 명령 형태인 binary로 배포되기 때문에 마스터 노드에 있을 필요는 없음 
- API Server와 통신을 하기 때문에 마스터 노드에 구성하는 것이 일반적

=>API Server
- Kubernetes Cluster의 API를 사용할 수 있게 해주는 프로세스
- Cluster로 요청이 전달되면 그 요청이 유효한지 검증
- kubectl로 명령을 전달하면 API Server가 명령을 받아서 검증하고 워커 노드의 Kubelet에게 전달하고 kubelet은 container runtime을 이용해서 명령을 수행

=>etcd
- Cluster에 필요한 리소스들의 상태 정보가 저장된 데이터베이스
- API Server는 Pod를 만든다는 사실을 etcd에게 알려서 상태를 저장하고 사용자에게 pod가 생성되었음을 알림
- 실제로 pod 생성여부는 알 수 없음: 문법에 맞으면 etcd에게 알리고 파드를 생성

=>scheduler
- pod를 어떤 노드에 할당해야 할지를 결정하는데 Worker Node의 리소스 사용량이나 레이블 그리고 노드의 상태 등을 참조해 결정

=>Controller Manager
- 클러스터의 상태를 지속적으로 감시하고 선언된 상태와 실제 상태를 일치시키기 위해서 다양한 컨트롤러들을 실행하는 컴포넌트
- 역할
클러스터 내 리소스를 지속적으로 모니터링
선언된 상태와 실제 상태를 비교해서 필요한 변경 수행
컨트롤러들을 관리하고 실행
장애가 발생하면 자동으로 복구 작업 수행

=>kubelet
- API Server는 Pod가 생성될 Worker Node에 있는 kubelet에 Pod 생성 정보를 전달
- kubelet은 전달된 정보를 가지고 pod를 생성하는데 kubelet은 Cluster의 각 노드에서 실행되는 에이전트로 pod에서 Container의 동작을 관리
- pod를 생성하고나면 kubelet은 API Server에 생성된 pod 정보를 전달하고 API Server는 다시 etcd에 업데이트해서 최종적으로 어떤 Worker Node에 어떤 pod가 생성되었는지 etcd에 저장합니다.

=>kube-proxy
- kubernetes 클러스터 내에서 네트워크 프록시 역할을 하는 컴포넌트로 서비스와 파드 간의 트래픽을 라우팅하는 역할을 수행
- 역할
클러스터 네트워크 트래픽 관리
	서비스 개념을 구현하기 위해 각 노드에서 실행됨
	클러스터 내부에서 서비스와 파드 간 트래픽을 적절히 분배

서비스 IP 와 포트 포워딩
	Kubernetes 서비스가  가상 ip를 사용해도 실제 파드로 트래픽이 전달되도록 설정
	iptables, ipvs 또는 userspace 모드를 활용해서 트래픽을 제어
- 실행 방식
모든 노드에서 데몬셋으로 실행됨
kubectl get pods -n kube-system

=>Kubernetes Controller
- Pod를 관리하는 역할

- ReplicaSet
몇 개의 파드를 유지할 지 결정하는 Controller
ReplicaSet이 관리하는 동일한 구성의 Pod를 Replica라고 부름

- Deployment
stateless 애플리케이션을 배포할 때 사용하는 가장 기본적인 Controller
ReplicaSet의 상위 개념

- DaemonSet
Deployment는 실행해야 할 Pod의 개수와 배포 전략을 세분화해서 조작을 하는데 DaemonSet은 모든 Node에 Pod를 배포하고 관리하는 Controller
노드마다 배포되어야 하는 성능 수집 및 로그 수집 같은 작업에 사용 

- StatefulSet
애플리케이션의 상태를 저장할 수 있는데 사용되는 Controller
Pod 집합의 Deployment 와 Scaling을 관리하며 Pod들의 순서 및 고유성을 보장
스케쥴링이 다시 되더라도 지속적으로 유지되는 식별자를 가짐

- Job
하나 이상의 pod를 지정해서 지정된 수의 pod가 성공적으로 실행될 수 있도록 해주는 Controller

- CronJob
특정 시간에 특정 Pod를 실행시키는 것과 같이 지정한 일정에 따라서 Job을 실행시킬 때 사용

=>Kubernetes Service
- 개요
Pod는 클러스터 안에서 옮겨 다니는 특성이 있어서 Pod가 실행 중인 Worker Node에 문제가 생기면 다른 Worker Node에서 Pod가 다시 생성될 수 있고 Pod IP가 변경되기도 합니다.

동적으로 변하는 Pod에 고정된 방법으로 접근하기 위해서 사용하는 것이 Service

Service를 사용하면 Pod가 Cluster 내의 어디에 떠 있든지 고정된 주소를 이용햇 접근할 수 있으며 Cluster 외부에서 Pod에 접근 할 수 도 있음

하나의 Service가 관리하는 Pod를 모두 동일한 구성을 갖는데 구성이 다른 Pod는 별도의 서비스로 관리

여러 개의 Worker Node에 걸쳐 실행이 되더라도 동일한 구성의 Pod는 하나의 Service가 관리 가능

서비스의 역할은 Load Balancer로 각 서비스는 자동적으로 고정된 IP 주소를 설정해서 이 주소로 들어오는 통신을 처리하는 객체

내부적으로 여러 개의 Pod가 있어도 밖에서는 하나의 IP 주소만 볼 수 있으며 이 주소로 접근하면 서비스가 통신을 적절히 분배해주는 구조

서비스가 분배하는 통신은 한 Worker Node 안으로 국한되며 여러 Worker Node 간의 분배는 Load Balancer 또는 Ingress가 담당하는데 이들은 Master Node도 Worker Node도 아닌 별도의 노드에서 동작하거나 물리적 전용 하드웨어 

- 종류
ClusterIP: Kubernetes 클러스터 내의 Pod들은 기본적으로 외부에서 접근할 수 있는 IP를 할당받지 않지만 동일한 클러스터 안에서 통신을 하고자 하는 경우 Cluster IP를 이용해서 통신이 가능

NodePort: 서비스를 외부로 노출할 때 사용하는 것으로 Worker Node의 IP 와 포트를 이용하는 서비스

Load Balancer: 외부에 있는 Load Balancer에 연결하고자 할 때 사용되는 것으로 사용자는 LoadBalancer의 외부 IP를 이용해서 접근

Ingress: URI, Hostname, Path 등 과 같은 웹 개념을 이해하는 프로토콜로 인지형 설정 메커니즘을 이용해서 HTTP Nework 서비스를 사용가능하게 해주는 것 

External Name: 외부의 특정 FQDN(Fully Qualified Domain Name)에 대한 CNAME(Canonical Name) 매핑을 제공하는 것으로 Pod CName을 이용해서 특정 FQDN 과 통신이 가능

=>kubernetes에서 통신을 할 때 나타나는 특징
- Pod가 사용하는 네트워크와 호스트(노드)가 사용하는 network는 다름
노드 내의 Pod들은 가상의 네트워크를 사용하고 호스트는 물리 네트워크를 사용합니다.

- 쿠버네티스는 하나의 파드에 2개 이상의 컨테이너를 배치하는 것이 가능
하나의 파드에 존재하는 컨테이너들은 IP가 동일
하나의 파드에 2개 이상의 컨테이너들이 존재하는 경우 포트번호는 달라야합니다.
localhost:포트번호 로 통신을 수행

- 동일한 노드에 존재하는 파드끼리는 통신할 수 있음
다른 노드에 존재하는 파드와는 기본적으로 통신이 불가능
단일 노드에 존재하는 Pod들은 172.10으로 시작하는 IP 대역을 사용
IP를 이용해서 통신은 가능하지만 파드가 계속해서 동일한 노드에 존재한다는 보장을 할 수 없기 때문에 실질적으로는 의미가 없음

=>다른 노드에 있는 파드와의 통신
- 다른 노드에 있는 파드와 통신하고자 할 때는 CNI가 필요
- CNI 플러그인은 Container들의 Network를 연결하거나 삭제하며 삭제할 때 할당된 자원을 제거
- 서로 다른 워커 노드에 존재하는 Pod의 IP가 동일하게 할당되는 문제가 발생하는데 이 문제를 해결할 수 있는 방법이 Overlay Network
- Overlay Network란 노드에서 사용하는 물리적인 Network 위에 가상의 Network를 구성하는 것 
- Kubernetes에서는 기본적으로 kubenet 이라는 기본적이고 간단한 Network Plugin을 제공하지만 다수의 노드에 떠 있는 Pod 간의 통신이나 Network 정책 설정 같은 고급 기능은 제공하지 않기 때문에 CNI의 스펙을 준수하는 Network Plugin을 사용해야 함
- CNI를 통해서 서로 다른 워커 노드의 파드끼리 통신 가능합니다.
