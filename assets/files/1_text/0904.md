**Kubernetes
7.AutoScaling
5)Horizontal Pod Autoscaler
=>개요
- HPA는 디플로이먼트/레플리카셋/레플리케이션컨트롤러의 레플리카 수를 CPU 부하 등에 따라 자동으로 스케일하는 리소스
- 부하가 높아지면 스케일 아웃하고 부하가 낮아지면 스케일 인 됨
- 파드에 resource requets가 설정되어 있지 않을 경우에는 동작하지 않음
- HPA는 30초에 한 번 꼴로 오토 스케일 여부를 확인
- 필요한 레플리카수 = ceil(sum(파드의 현재의  CPU 사용률) / targetAverageUtilization)
현재 2개의 파드가 배포 중인데 100% 와 90% CPU를 사용하고 있고 50%까지만 사용하도록 허락
- HPA는 스케일 조건과 최저 레플리카 수 그리고 최고 레플리카 수를 지정

=>작성 방법
kind: HorizontalPodAutoScler
spec:
  scaleTargetRef"
    kind: Deployment
    name: 실제 이름
  minReplicas: 개수
  maxReplicas: 개수

  - type: Resource

      name: cpu 나 memory

=>HorizontalPodAutoscaler에서 사용 가능한 메트릭의 종류

- Object: Kubernetes Object Metric(Ingerss hits/s)

=>다중 지표 지원: CPU 와 Memory를 동시에 감시할 수 있는데 이 경우 둘 중 하나만 임계치를 넘어도 스케일 아웃이 발생
=>target.type
Utilization: 백분율
AverageValue: 값(500Mi)
=>spec.behavior 속성에 한꺼번에 몇 개 씩 늘릴지 설정 가능
apiVersion: autoscaling/v2beta2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-hpa
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 500Mi
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: percent
        value: 100
        periodSeconds: 15
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: percent
        value: 100
        periodSeconds: 15
      - type: Pods
        value: 4
        periodSeconds: 15
      selectPolicy: Max

- 내용
ScaleDown 과 ScaleUP에 대해서 각각 설정
증감 가능한 레플리카 수 제한에는 percent 와 pods로 설정이 가능
스케일 아웃에는 15초 동안 100% 증가와 15초 동안 4개의 파드 추가라는 정책을 설정
selectPolicy는 두개의 정책이 있는 경우 어떤 정책을 따를 것인지 설정
spec.behavior.scaleDaown.selectPolicy를 disable로 설정하면 ScaleDown은 발생하지 않음
stabilizationWindowSeconds는 레플리카 수가 너무 빈번하게 증감하는 것을 방지하기 위해서 일정 시간 동안 지켜보는 것

6)Vertical Pod Autoscaler
=>개요
- 파드에 할당하는 CPU/Memory의 requests는 실제로 성능을 측정하며 적절한 값을 설정해야 하므로 서비스 환경에 배포하지 않으면 조절이 어려울 수 있는데 이 requests는 적절한 범위로 조절을 해두지 않으면 실제로 사용되는 리소스 양과 할당된 리소스 양에 차이가 생겨 리소스 부족으로 인해 동작이 불안정해지거나 반대로 리소스 과잉으로 인해 낭비가 생시기도 하는데 이를 조절하기 위한 VPA
- VPA는 컨테이너에 할당하는 CPU/Memory 리소스의 할당을 자동으로 스케일하는 기능
- HPA가 Scale Out 이고 VPA가 Scale Up

=>VPA는 기본 기능이 아니어서 설치
- 다운로드: git clone https://github.com/kubernetes/autoscaler.git
- 다운로드가 안되면 git config --global http.sslVerify false
- 디렉토리 이동 cd autoscaler/vertical-pod-autoscaler
- 설치 스크립트 실행: ./hack/vpa-up.sh
- 확인: kubectl get crd | grep verticallodautoscalers

- VPA 매니페스트: nginx-vpa-autoscaler.yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: nginx-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-vpa
  updatePolicy:
    updateMode: "Auto"

- 2개의 파일을 배포하고 일정 시간을 대기

- vpa를 확인: kubectl describe vpa nginx-vpa
LowerBound는 그 컨테이너에 최소한으로 필요한 리소스 양으로 이 양을 밑도는 경우 성능에 큰 영향을 미칠 수 있지만 UpperBound는 그 컨테이너가 사용하는 리소스의 최대치로 이 양을 초과하는 경우 리소스가 낭비될 가능성이 있음

Target은 그 컨테이너가 가장 효율적으로 리소스를 사용할 수 있는 추천값으로 컨테이너의 requests를 변경할 때 이 값이 사용되는데 유사한 항목으로 Uncapped Target이 있지만 이것은 할당 가능한 리소스 제약을 고려하지 않고 실제 리소스 사용양 만을 기준으로 계산된 추천값으로만 표시하고  requests 변경에는 사용되지 않음 


- UpdateMode
Off: Pod의 리소스를 자동으로 변경하지 않고 추천 값만 제공
Initial: 새로운 파드가 생성될 때 만  Resource를 적용하고 기존 Pod는 변경하지 않음
Auto: VPA가 필요한 경우 기존 Pod를 재생성하여 새로운 Resource를 적용할 수 있는데 Deployment의 Replica가 여러 개라면 영향은 줄어듬

운영환경에서는 대부분 off로 설정해서 추천값만 확인

=>주의할 점
- VPA 와 HPA를 함께 사용하는 경우
동일한 리소스에 설정하면 문제가 발생할 가능성이 있음
VPA가 성능을 변경하면 HPA의 판단에 영향을 미치기 때문

HPA -> CPU 기준
VPA -> CPU 자동 조절

일반적인 구성
HPA -> CPU 기준
VPA -> Memory만 조절

HPA -> 외부 Metric(Request 수 나 Queue의 길이)
VPA -> CPU/Memory

8.Health Check
1)Health Check 방법
=>Liveness Probe
- 파드 내부의 컨테이너가 정상 동작 중인지 확인하는 것으로 실패한 경우 컨테이너를 재기동
- 프로세스에 버그 등이 있을 경우 장기간 실행되고 있으면 Memory Leak(메모리 누수) 등에 의해 응답하지 않게 되는 경우가 있는데 이런 경우 컨테이너를 재시작할 수 있도록 해주는 헬스 체크
- 헬스 체크에 한 번 실패하면 재시작없이는 복구가 어려운 컨테이너에 사용

=>Readiness Probe
- 파드가 요청을 받아들일 수 있는지 확인하는 것으로 실패한 경우 트래픽을 차단하는데 파드를 재기동하지 않음
- 백엔드 데이터베이스에 정상적으로 접속되는지, 캐시에 로드는 끝났는지 기동 시간이 오래 걸리는 프로세스가 기동을 완료했는지 등을 체크
- 정상적으로 요청을 처리하는 수를 제어하기 위해서 Readness Probe를 실패시키는 방법도 사용할 수 있음 

=>로드 밸런서의 헬스 체크
- 로드밸런서를 생성하면 쿠버네티스 노드의 헬스 체크는 ICMP를 통한 단순한 체크만 하므로 위 2개의 헬스체크가 필요

=>Startup Probe
- 파드의 첫번째 기동이 완료되었는지 확인하는 것으로 실패하면 다른  Probe를 실행하지 않음
- 처음 기동하는데 시간이 걸리는 경우 Liveness Probe를 사용하려면 첫번째 체크 시작 시간을 연장하거나 실패라고 판단할 때 까지 시간을 연장하여 사용해야 하는데 이 설정을 변경하지 않으면 컨테이너는 재시작만하고 실제 기동은 하지 못할 수 있음
이 문제를 해결하기 위해서 판단할 때 까지 시간을 늘리면 되지만 일반적인 장애가 발생했을 때 바로 실패하고 판단하지 않는 문제가 발생
- startup probe를 설정하면 끝날때까지 Liveness 나 Readiness Probe를 실행하지 않고 파드가 서비스되거나 정지되지 않음

2)헬스 체크 방식
=>헬스 체크는 컨테이너 별로 이루어지고 어느 하나의 컨테이너라도 실패하면 전체 파드가 실패한 것으로 간주
=>방식 종류
- exec 방식
명령어를 실행하고 종료 코드가 0이 아니면 실패
livenessProbe:
  exec:
    command: ["test", "-e", "/ok.txt"]

- httpGet
httpGET 요청의 status code로 확인
200~399 사이가 아니면 실패

livenessProbe:
  httpGet:
    path: /health
    port: 80
    scheme: HTTP
    host: web.example.com
    httpHeaders:
    - name: Authorization
      value: Bearer TOKEN

- TCP Socket 
TCP 세션 활성화를 검증하여 확인
판단 조건
	성공: TCP 세션 활성화 가능
	실패: TCP 세션 활성화 불강

livenessProbe:
  tcpSocket:
    port: 80


3)Health Check 간격
=>설정 항목 
- initialDelaySeconds: 첫번째 헬스 체크 까지의 지연
- periodSeconds: 헬스 체크 간격
- timeoutSeconds: 타임 아웃까지 시간
- successThreshold: 몇 번 성공하면 성공이라고 판단할 지 개수
- failureThreshold: 몇 번 실패하면 실패라고 판단할 지 개수

=>Liveness Probe에서는 실패했을 때 파드가 재시작하기 때문에 실패라고 판단하기 까지의 체크 횟수를 환경에 맞게 설정해야 함

=>successThreshold는 1이상이어야 하고 Liveness Probe 와 Startup Probe에서는 반드시 1로 해야 함

=>initialDelaySeconds를 사용하는 것보다는 Startup Probe를 병용해서 사용하는 것을 권장

7)Container 정지 시 동작
=>컨테이너 정지 시 동작 설정은 spec.restartPolicy에 설정
=>값
Always: 파드가 정지하면 항상 재가동
OnFailure: 예상치 못하게 파드가 정지한 경우(종료 코드가 0인 경우 제외) 파드 재가동
Never: 파드가 정지해도 파드를 재기동하지 않음
=>워크로드 리소스 중에서 잡은 파드 1개 당 1회 명령어 실행을 성공시키는 것이 목적이라서 Always는 선택 불가
=>매니페스트: sample-restart-always.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-startup
spec:
  restartPolicy: Always
  containers:
  - name: tools-container
    image: nginx
    command: ["sh", "-c", "exit 0"]
