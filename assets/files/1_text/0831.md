5)LoadBalancer
=>MetalLB
- 개요
Baremetal LoadBalancer의 약자로 온프레미스 환경에서도 퍼블릭 클라우드의 LoadBalancer 처럼 사용할 수 있는 서비스

Public Cloud에서는 LoadBalancer 타입의 서비스를 사용할 때 클라우드 제공자의 Application Load Balancer(ALB)가 자동으로 할당되지만 온프레미스 환경에서는 이러한 LoadBalancer가 기본적으로 제공되지 않아서 MetalLB를 이용해서 클러스터 외부로 서비스를 노출할 수 있음

MetalLB는 AWS 나 GCP 같은 대부분의 퍼블릭 클라우드 환경에서는 사용할 없음

MetalLB는 로컬 클러스터 환경에서 사용 가능한 LoadBalancer

kubeadm 클러스터에 적합
VMWare, VirtualBox, UTM, Proxmox 등의 가상환경에서도 많이 사용

- 특징
DaemonSet으로 Speacker 파드를 생성하여 External IP를 전파
서비스의 External IP 전파를 위해서 표준 프로토콜 ARP, NDP, BGP를 이용
ARP 와 NDP는 L2 mode ARP를 위해서 존재하는데 동일한 서브넷에서 각 IP를 광고
BGP(Border Gateway Protocol)는 외부 네트워크 라우터와 경로 정보를 동적으로 공유

- 사용 절차
MetalLB를 쿠버네티스 클러스터에 설치(Manifest 방식)

LoadBalancer에 할당할 IP 주소 범위를 설정

서비스에서 type:LoadBalancer로 서비스를 생성하면 자동으로 외부 IP가 부여됨

- 설치
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.13.10/config/manifests/metallb-native.yaml

matallb-system이라는 별도의 namespace를 만들어서 설치

확인: kubectl get all -n metallb-system

IP 대역 설정
cat <<EOF | kubectl apply -f -
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: my-ippool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.0.150-192.168.0.199
EOF

IP 대역을 가지고 Layer2 모드로 LoadBalancer IP 사용 허용

cat <<EOF | kubectl apply -f -
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: my-l2-advertise
  namespace: metallb-system
spec:
  ipAddressPools:
  - my-ippool
EOF

확인: kubectl get l2advertisements -n metallb-system

6)Session Affinity
=>개요
- ClusterIP 서비스에서 활성화한 경우 파드에서 ClusterIP로 보내진 트래픽은 서비스에 연결된 어느 하나의 파드에 전송된 후 다음 트래픽도 계속 같은 파드에 보내짐
- 서비스에 대한 설정은 spec.sessionAffinity 와 spec.sessionAffinityConfig를 사용
- 최대 세션 고정 시간을 설정할 수 있음
- sessionAffinity의 기본 값은 None

=>실습
- 매니페스트 파일 생성: sample-session-affinity.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-session-affinity

  type: ClusterIP
  selector:
    app: sample-app
  ports:
  - name: http-port
    protocol: TCP
    port: 8080
    targetPort: 80

- 웹 테스트 용 파드 1개 생성: sample-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  hostNetwork: true
  containers:
  - name: tools-container
    image: amsy810/tools:v2.0

- 서비스 확인: kubectl get service

- 샘플 파드 안으로 접속: kubectl exec -it sample-pod -- /bin/bash

- 여러 번 요청을 보내보면 파드의 이름이 변경되는 것을 확인할 수 있음


- 매니페스트 파일 수정: sample-session-affinity.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-session-affinity
spec:
  selector:
    app: sample-app
  ports:
  - name: http-port
    protocol: TCP
    port: 8080
    targetPort: 80
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10000

7)노드 간 통신 제외와 발신 측 IP 주소 유지
=>NodePort 서비스와 LoadBalancer 서비스에서 쿠버네티스 노드에 도착한 요청은 노드를 통해 파드에도 LoadBalancing을 하게 되어 있어서 실제로는 불필요한 2단계 LoadBalancing이 이루어지는데 LoadBalancer 서비스에서는 LoadBalancer가 LoadBalancing하여 노드에 도착한 요청은 노드를 통해 파드에도 LoadBalancing을 하는 형태
=>2단계 로드밸런싱은 균일하게 요청을 분산하기 쉽지만 불필요한 레이턴시 오버헤드가 발생하거나 밸런싱을 수행할 때 네트워크 주소 변환(NAT)이 이루어져 발신 측 IP 주소가 유실될 수 도 있음
=>파드가 가동 중인 노드와 IP 주소 확인
kubectl get pods -o custom-columns="NAME:{metadata.name},Node:{spec.nodeName},NodeIP:{status.hostIP}"
=>데몬셋은 하나의 노드에 하나의 파드가 배치되기 때문에 굳이 다른 노드의 파드에 전송하지 않고 같은 노드에만 통신하고자 하는 경우가 있을 수 있는데 spec.externalTrafficPolicy를 사용할 수 있는데 ClusterIP에서는 사용할 수 없음
- 설정값
Cluster(기본값): 노드에 트래픽이 도착한 후 다른 노드에 있는 파드를 포함해서 다시 LoadBalancing을 하는 구조

Local: 노드에 트래픽이 도착한 후 노드 간 LoadBalancing을 하지 않음

- 매니페스트 생성: sample-nodeport-local.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-nodeport-local
spec:
  type: NodePort
  externalTrafficPolicy: Local
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
    nodePort: 30082
  selector:
    app: sample-app

=>배포하고 curl -s http://노드IP:30082 으로 요청을 하면 동일한 파드가 응답합니다.

=>NodePort의 경우 해당 노드 상에 파드가 없으면 요청에 응답할 수 없지만 LoadBalancer 서비스의 경우에는 별도로 헬스 체크용 NodePort가 할당되기 때문에 파드가 존재하지 않는 노드에는 LoadBalancer에서 요청이 전달되지 않음
=>헬스 체크용 NodePort의 포트 번호는 spec.healthCheckNodePort에서 설정
지정하지 않으면 임의의 포트번호가 할당되고 할당되고 healthCheckNodePort는 LoadBalancer 서비스 와 externalTrafficPolicy가 Local 인 경우만 설정 가능

8)토폴리지는 고려한 서비스 전송
=>일반적으로 서비스 전송 대상은 region 이나 AZ(가용 영역) 등 의 토폴리지를 고려하지 않고 전송되는데 노드가 같은 리전이나 가용영역에 있으면  레이턴시는 별로 높지 않지만 멀리 떨어져 있는 경우 성능이 저하되고 노드 수가 너무 많으면 East-West 트래픽이 증가되어 결과적으로 성능이 저하되는데 이러한 문제를 해결하는 것이 Topology-aware Service Routing  

9)Headless Service(None)
=>개요
- 대상이 되는 개별 파드의 IP 주소가 직접 반환되는 서비스
- 다른 서비스에서 부하 분산을 위해 제공되는 EndPoint는 가상 IP로 LoadBalancing 동작을 하기 위해 여러 파드로 전송되는 IP EndPoint
- 헤드리스 서비스는 LoadBalancing 하기 위한 IP 주소는 제공하지 않고 DNS RoundRobin을 사용한 EndPoint를 제공
- 스테이트풀셋이 헤드리스 서비스를 사용하는 경우에만 파드명으로 IP주소를 디스커버리 할 수 있는데 sample-statefulset-0 등의 파드명으로 IP 주소를 가져올 수 있음

=>생성
- 만족해야 하는 조건
서비스의 타입이 ClusterIP 일 것
서비스의 spec.ClusterIP가 None 일 것
옵션
서비스의 metadata.name이 스테이트풀셋의 spec.serviceName과 같아야 함

=>Headless 실습

    protocol: "TCP"
    port: 80
    targetPort: 80
  selector:
    app: sample-app

        app: sample-app

10)ExternalName Service
=>개요
- 쿠버네티스는 거의 모든 서버용 소프트웨어를 실행할 수 있는데 모든 서버용 소프트웨어를 꼭 쿠버네티스에서 실행하는 것은 아님
- 데이터베이스 같은 스토리지 컴포넌트 등이 대표적으로 쿠버네티스 외부에서 동작하는 소프트웨어
- 매니지드 데이터베이스 서비스를 활용하거나 쿠버네티스와 통합되지 않은 시스템과 연동할 필요가 있을 수 도 있음
- ExternalName 서비스는 도메인 네임에 대한 별명
- ExternalName 서비스는 애플리케이션 파드에서 로컬 네임을 사용하고 쿠버네티스 DNS 서버에 이 로컬 네임을 조회하면 외부 도메인으로 변경해주는 방식
- 외부 도메인에 별명을 만들어서 내부에서 통신하는 것 처럼 사용

=>서비스를 위한 yaml 파일: sample-externalname.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-externalname
  namespace: default
spec:
  type: ExternalName
  externalName: external.example.com

=>서비스 생성: kubectl apply -f sample-externalname.yaml

=>서비스 확인: kubectl get services

=>느슨한 결합
- 클러스터 내부에서는 파드와 통신에 서비스 이름 해석을 사용하여 느슨한 결합을 유지하고 있고 SaaS 나 IaaS 등 외부에 있는 서비스를 사용할 때도 가능하면 느슨한 결합으로 구성해야 함
- 애플리케이션 등에 외부의 EndPoint를 등록해두면 목적지가 변경되었을 때 애플리케이션 측의 설정 변경이 필요한데 ExternalName을 등록해두면 목적지가 변경되어도 ExternalName 서비스만 변경하는 것으로 가능
- 목적지 변경에 대한 대응을 쿠버네티스 내에서 끝낼 수 있으므로 외부 서비스와 느슨한 결합을 유지할 수 있음
- ExternalName을 사용하면 외부 서비스와의 느슨한 결합을 확보하고 외부 서비스와 쿠버네티스 클러스터에 배포된 내부 서비스와의 전환도 유연하게 할 수 있음
- 애플리케이션 측은 서비스의 FQDN을 지정해두고 이름 해석이 되면 ExternalName의 CNAME 레코드 또는 ClusterIP의 A 레코드가 반환되는 형태가 되어 애플리케이션 측은 변경없이 내부 서비스 와 외부 서비스를 전환할 수 있음
- ClusterIP 서비스에서 ExternalName 서비스로 전환할 경우 spec.clusterIP를 명시적으로 공란으로 만들어두어야 함

11)None-Selector Service
=>개요
- ExternalName 서비스에서는 서비스명으로 이름 해석을 하면 외부 도메인에 전송되는데 반해 None-Selector 서비스에서는 서비스명으로 이름 해석을 하면 자신이 설정한 멤버에 대해 LoadBalancing을 수행
- 쿠버네티스 내에 원하는 목적지로 LoadBalancer를 생성할 수 있는 기능
- 클라이언트 사이드 LoadBalancing 용 EndPoint를 제공하는 서비스라고 할 수 있음
- 쿠버네티스 클러스터 외부의 애플리케이션 서버에 대해 요청을 분산하고자 할 때 쿠버네티스 서비스를 사용할 수 있음
- 외부로 요청을 보내기 위한 서비스로 ExternalName 서비스와 거의 비슷하지만 ExternalName 서비스는 CNAME이 반환되는 반면 None-Selector는 ClusterIP의 A 레코드가 반환되기 때문에 쿠버네티스 서비스를 사용하는 것 처럼 외부용 LoadBalancing을 할 수 있음

12)Ingress
=>개요
- 서비스는 외부에서 들어오는 트래픽을 쿠버네티스 안으로 인도하는 역할
- 애플리케이션에 외부 사용자가 접근할 수 있도록 LoadBalancer 서비스를 사용했는데 이 방법은 애플리케이션마다 IP 주소를 따로 부여하고 부여된 주소와 애플리케이션 관계를 DNS 서버에서 제공해야 하기 때문에 문제가 발생하기 쉬움
- 인입되는 트래픽을 올바른 애플리케이션으로 연결하는 일은 라우팅과 관련된 문제이지만 인그레스를 사용하면 이를 쿠버네티스 안에서도 다룰 수 있음
- 인그레스는 일련의 규칙에 따라 도메인 네임과 애플리케이션의 요청 경로를 매칭해주는 역할을 수행
- 도메인 네임을 이용한 라우팅과 관련된 문제를 reverse proxy로 거의 해결할 수 있는데 쿠버네티스의 인그레스는 플러그인이 가능한 아키텍쳐가 적용되어 있음
- 라우팅 규칙을 일반적인 쿠버네티스 리소스로 정의하고 리버스 프록시로 사용할 컴포넌트에 이 규칙에 따라 트래픽을 처리하도록 하는 구조

=>Rosource 와 Controller
- 쿠버네티스는 분산 시스템이고 매니페스트로 정의한 리소스를 쿠버네티스에 등록하는 것으로 시작되는데 등록만으로는 아무런 처리가 이루어지지 않으며 실제 처리를 하는 컨트롤러라는 시스템 구성 요소가 필요
- 디플로이먼트에서는 레플리카셋을 생성하거나 레플리카 수를 변경해가면서 롤링 업데이트를 하는 디플로이먼트 컨트롤러라고 하는 시스템 구성 요소가 클러스터 안에서 동작

=>인그레스 컨트롤러를 이용한 배포
- 디플로이먼트 작성: deploy-test.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: service-test
spec:
  replicas: 3
  selector:
    matchLabels:
      app: service_test_pod
  template:
    metadata:
      labels:
        app: service_test_pod
    spec:
      containers:
      - name: simple-http
        image: python:2.7
        imagePullPolicy: IfNotPresent
        command: ["/bin/bash"]
        args: ["-c", "echo '<p>Hello from $(hostname) </p>' > index.html; python -m SimpleHTTPServer 8080"]
        ports:
        - name: http
          containerPort: 8080

- 서비스 작성(svc-test.yaml)
apiVersion: v1
kind: Service
metadata:
  name: service-test
spec:
  selector:
    app: service_test_pod
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080

- 인그레스 생성(ingress-test.yaml)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-nginx
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    kubernetes.io/ingress.class: "nginx"
spec:
  rules:
  - host: "ingress.test.com"
    http:
      paths:
      - pathType: Prefix
        path: /test
        backend:
          service:
            name: service-test
            port:
              number: 80

- 배포
kubectl apply -f deploy-test.yaml

kubectl apply -f service-test.yaml

kubectl apply -f ingress-test.yaml
