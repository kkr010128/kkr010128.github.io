5)네트워크 트래픽 관리
=>컴포넌트는 도메인 네임으로 서로를 식별하며 Docker DNS Server 가 만들어져서 도메인 네임을 조회해서 IP 주소를 알려주면 이 IP 주소로 트래픽을 전달
=>스웜 모드에서는 Overlay Network가 만들어지는데 클러스터에 속한 모든 노드를 연결하는 가상 네트워크
=>오버레이 네트워크에 연결된 서비스는 서비스 이름을 도메인 네임 삼아 다른 서비스와 통신할 수 있음
=>서비스를 배포하면 각 서비스마다 IP 주소가 할당이 되도 이 IP 주소를 서비스에 속하는 모든 레플리카가 공유하는 주소
=>서비스의 스케일링 규모와 상관없이 DNS 조회 결과에는 IP 주소가 하나만 조회되는데 클라이언트가 이 IP 주소로 요청을 보내면 운영체제의 네트워크 계층에서 이 IP 주소의 종착점이 여러 곳임을 파악하고 그 중 하나를 결정
=>스웜 서비스 형태로 실행되는 애플리케이션도 DNS 이름을 그대로 사용하기 때문에 오버레이 네트워크는 애플리케이션 관점에서는 전혀 겉으로 드러나지 않음
=>스웜은 Ingress Networking을 이용
=>모든 노드가 같은 포트를 감시하며 외부 트래픽을 받고 이렇게 노드에 도달한 트래픽에 대한 내부적인 로드밸런싱을 도커가 담당
=>서비스의 포트를 공개함녀 인그레스 네트워크가 적용
=>도커 컴포즈는 여러 컨테이너가 같은 포트를 감시하도록 할 수 없지만  도커 스웜에서는 인그레스 네트워크를 사용해서 서비스 하나가 포트 하나를 사용하도록 합니다.

=> 롤링 업데이트
- 첫번째 작업 대상을 Shutdown 한 뒤 새로운 작업을 준비하는 구조인데 ready 와 running을 반복
- 작업을 교체하는 형태
- 추가 기능
--update-parallelism: 동시에 업데이트할 컨테이너 개수로 기본값은 1

--update-delay: 한 그룹의 업데이트가 끝난 뒤 다음 그룹을 업데이트하기까지 대기 시간(10s, 1m 등), health check 등이 있다면 이 시간이 지난 뒤 업데이트하라고 하는 것이 좋습니다.

--update-order: 업데이트 순서
start-first: 새로운 컨테이너를 만들고 기존 것을 삭제, 중단 시간 최소화를 위해서 설정, 기본값
stop-first: 기존의 컨테이너를 삭제하고 새로운 컨테이너를 생성, 리소스 용량이 부족한 경우 설정 

--update-failure-action: 업데이트 실패 시 동작
pause: 업데이트 중지
rollback: 이전 버전으로 되돌림
continue: 오류를 무시하고 진행

--update-max-failure-ratio: 업데이트 중 허용할 수 있는 실패율, 20%로 설정하면 20이상 실패한 경우 실패로 간주

- 리소스 및 설정 변경을 실시간으로 수행할 수 있음
리소스 변경: --limit-cpu 값 또는 --limit-memory 값과단위
cpu는 코어의 개수
--limit-cpu 0.5: 0.5코어
--limit-memory 512mb

7)docker compose 배포
=>개요
- 스웜 모드에서는 애플리케이션을 배포할 때 스택을 생성
- 스택은 서비스, 네트워크, 볼륨 등 여러 개의 리소스를 묶어서 만든 것입니다.
=>배포
- 네트워크 생성: docker network create --driver overlay dailylog-net 
- 디렉토리를 생성하고 이동: mkdir dailylog && cd $_
- docker-compose 파일 생성
version: '3.9'
services:
  mongodb:
    image: dbgurum.dailylog:db_1.0
    ports:
      - "27017:27017"
    networks:
      - dailylog-net
    deploy:
      placement:
        constraints: [node.role != manager]
      restart_policy:
        condition: on-failure
        max_attempts: 3
        delay: 10s
        window: 120s
  backend:
    depends_on:
      - mongodb
    image: dbgurum/dailylog:back_1.0
    ports:
      - "8000:8000"
    networks:
      - dailylog-net
    environment:
      - MONGO_URL=mongodb://mongodb:27017
    deploy:
      replicas: 2
      placement:
        constraints: [node_role != manager]
      restart_policy:
        condition: on-failure
        max_attempts: 3
        delay: 10s
        window: 120s

  frontend:
    image: dbgurum/dailylog:front_1.0
    depends_on:
      - backend
    ports:
      - "3000:8000"
    networks:
      - dailylog-net
    environment:
      - PORT=8000
      - DAILYLOG_API_ADDR=backend:8000
    deploy:
      replicas: 2
      placement:
        constraints: [node.role != manager]
      restart_policy:
        condition: on-failure
        max_attempts: 3
        delay: 10s
        window: 120s
networks:
  dailylog-net:
    external: true

- 배포: docker stack deploy --compose-file docker-compose.yaml dailylog

- 확인: docker stack ls

- 삭제: docker stack rm dailylog

11.기타
1)Health Check
=>개요
- 도커는 컨테이너를 시작할 때 마다 애플리케이션의 기본적인 상태를 확인
- 컨테이너를 실행하면 내부에서 애플리케이션 실행 파일이나 자바 혹은 닷넷 런타임 또는 쉘 스크립트 같은 특정한 프로세스가 실행되는데 도커가 확인하는 것은 이 프로세스의 실행 상태인데 만약 이 프로세스가 종료되었다면 컨테이너도 종료 상태가 되는데 이것만으로도 환경과 관계없이 기본적인 헬스체크는 가능
- 해당 프로세스가 비정상 종료되었거나 컨테이너가 종료되었다면 개발자도 애플리케이션의 상태가 비정상임을 알 수 있음
- 클러스터 환경에서는 플랫폼이 종료된 컨테이너를 재시작하거나 새 컨테이너로 교체하는 작업을 대신 수행
- 웹 애플리케이션을 실행 중인 컨테이너에서 처리 용량을 뛰어넘는 수의 요청이 들어오는 순간 웹 애플리케이션은 503 Service Unavailable 오류를 발생하지만 컨테이너의 프로세스는 여전히 정상적으로 실행 중인 상태
-애플리케이션이 동작을 멈췄어도 도커는 컨테이너를 정상이라고 판단.
- Dockerfile에 HEALTHCHECK 옵션을 사용할 수 있음
	--interval: 헬스 체크 실행 간격
	--timeout: 검사 제한 시간
	--start-period: 컨테이너 시작 후 유예시간
	--retries: 연속 실패 횟수
	CMD: 실제 상태 확인 명령로 필수

=>실습
- 헬스체크를 위한 웹 애플리케이션 생성: app.py
from flask import Flask
app = Flask(__name__)

@app.route("/")
def hello():
  return "Hello Docker"


@app.route("/health")
def health_check():
  return "OK", 200

if __name__ == '__main__':
  app.run(host='0.0.0.0', port=8080)

- 이미지 생성을 위한 Dockerfile
FROM python:3.9-slim

RUN apt update && apt install -y curl && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY app.py .
RUN pip install flask

HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 CMD curl -f http://localhost:8080/health >

EXPOSE 8080
CMD ["python", "app.py"]

- 이미지 빌드: docker build -t my-healthcheck-app .

- 컨테이너 생성: docker run -d --name healthcheck my-healthcheck-app

- docker ps 로 확인
STATUS 
	starting: 컨테이너가 막 실행되서 헬스 체크를 기다리는 중
	healthy: 정상적인 동작 중
	unhealthy: 설정된 횟수만큼 헬스 체크 실패

=>health 체크가 중요한 이유
- 자동 복구: Docker Swarm 이나 kubernetes 같은 오케스트레이션 도구는 unhealthy 상태의 컨테이너를 자동으로 재시작하거나 교체
- 무중단 배포: 로드밸런서와 연동할 때 새 컨테이너가 healthy가 될 때 까지 트래픽을 보내지 않도록 제어할 수 있음

=>docker compose에서의 헬스 체크
- service 하위 항목에 healthcheck 옵션을 추가하면 됩니다.
- Dockerfile 과 docker-compose 파일에 헬스체크가 모두 작성되어 있는 경우 docker-compose에 작성한 내용이 우선순위를 가짐 
- docker-compose.yaml 파일 
version: "3.9"
services:
  web:
    image: my-healthcheck-app
    ports:
      - "8080:8080"
    healthcheck:
      test: ["CMD", "-f", "http://localhost:8080/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 5s

=>데이터베이스의 헬스 체크가 끝나면 웹 서버 구동하는 docker-compose
version: "3.9"
services:
  db:
    image: postgre:15
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: mydb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydb"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - my-network
  web:
    build: .
    ports:
      - "8080:8080"
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks:
      - my-network
networks:
  my-network

2)config 객체
=>개요
- 도커에서는 설정 값을 저장하기 위해 config 객체를 사용
- config 객체는 컨테이너가 설정 값을 클러스터에서 읽어올 수 있게 해주는 리소스로 애플리케이션 배포와 설정 관리를 분리할 수 있도록 함

=>MySQL 관리자 비밀번호를 Config 객체로 생성
- MySQL은 환경변수 뒤에 _FILE이라는 접미사를 붙이면 해당 환경 변수에 지정된 파일 경로의 내용을 읽어서 비밀번호로 설정하는 것이 가능
- 비밀번호 작성 파일 생성: echo -n "MyStrongPassword123!" > mysql_root_pw.txt
- 도커 컨피그 객체 생성: docker config create mysql_root_password ./mysql_root_pw.txt
- 확인: docker config ls
- 주입
docker service create --name mysql-server --publish 3306:3306 --config source=mysql_root_password,target=/etc/mysql-config/root-pw -e MYSQL_ROOT_PASSWORD_FILE=/etc/mysql-config/root-pw mysql:8.0

- 서비스 확인
docker service ps mysql-server

- 확인된 컴퓨터에서 수행
CONTAINER_ID=$(docker ps -q -f name=mysql-server)


docker exec -it $CONTAINER_ID mysql -u root -pMyStrongPassword123! -e "SHOW DATABASES;"


- docker-compose 파일로 config 객체 불러오기
version: "3.9"

services:
  db:
    image: mysql:8.0
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD_FILE: /etc/mysql-config/root-pw
      MYSQL_DATABASE: myapp_db
    configs:
      - source: db_root_pw
        target: /etc/mysql-config/root-pw
        mode: 0400
configs
  db_root_pw:
    file: ./mysql_root_pw.txt

3)secret 설정
=>환경 변수를 이용하는 방법은 컨테이너 설정이나 docker inspect 등을 통해 노출될 수 있음
=>기본 구조
Secret 생성 -> Docker Secret Store -> 서비스에 Secret을 연결 -> 컨테이너 내부에 저장(/run/secrets/시크릿 이름)
=>실습
secrets:
  db_root_pw:
    file: ./mysql_root_pw.txt

=>시크릿 객체 직접 생성
echo "initial_db_password_111" | docker secret create db_password_v1 - 

=>배포할 때 주입
docker service create --name myservice --secret source=db_password_v1,target=db_password alpine:latest sh -c "while true; do echo \"[$(date + %T)] Secret content:$(cat /run/secrets/db_password)\"; sleep 5; done"
