3.Workload API
6)Job
=>개요
- 컨테이너를 사용해서 한 번만 실행하는 리소스
- 여러 개의 작업을 병렬로 실행하면서 지정한 횟수의 컨테이너 실행을 보장하는 리소스
- Run-to-Completion 이라고 부르기도 함
- ReplicaSet 과 다른 점은 정지되는 것을 전제로 만들어지는 것
- ReplicaSet은 정상 종료되는 횟수를 세지 못하기 때문에 배치 처리를 할 수 없음

=>파이를 2천자리까지 계산해주는 잡을 생성
- 매니페스트 파일: sample-job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: hello-job
spec:
  template:
    spec:
      containers:
      - name: hello
        image: busybox:1.36
        command:
          - sh
          - -c
          - |
            echo "Job 시작"
            sleep 10
            echo "Job 완료"
      restartPolicy: Never
  backoffLimit: 4
- 매니페스트 적용: kubectl apply -f sample-job.yaml

- 잡을 확인: kubectl get jobs

=>restartPolicy
- Job에서는 spec.template.spec.restartPolicy에 OnFailure 이나 Never 중 하나를 지정해야 하는데 Never를 지정하면 장애가 발생하면 새로운 파드를 만들고 OnFailure 지정하면 동일한 파드를 이용해서 잡을 다시 시작
- 실패하는 JOB을 만들어서 확인
apiVersion: batch/v1

kind: Job

metadata:
  name: errorjob

spec:
  template:
    spec:
      containers:
      - name: errorjob
        image: busybox:1.36
        command:
          - ls
          - unvalid path
      restartPolicy: Never
  backoffLimit: 4

=>태스크 와 작업 큐 병렬 실행
- 성공 횟수를 지정하는 completions 와 병렬성을 지정하는 parallelism 설정들의 기본값은 1이기 때문에 명시적으로 지정하지 않아도 동작은 변하지 않음
- 2개의 파라미터는 잡을 병렬화하여 실행할 때 사용하는 옵션
- backoffLimit는 실패를 허용하는 횟수
- 1회만 실행하는 태스크의 경우는 completions 와 parallelism은 1로 설정하고 backoffLimit는 0으로 설정하는 경우가 많은
- 여러개를 병렬로 설정할 때는 parallelism 값을 조정하고 backoffLimit를 설정하는 것을 권장
- 여러 개의 잡을 순서대로 실행하고자 할 때는 completions를 지정하지 않고 parallelism을 1로 설정

=>일정 시간 후에 잡을 삭제
- spec.ttlSecondsAfterFinished를 설정하면 됩니다.
kind: Job
metadata:
  name: samplejob
spec:
  ttlSecondsAfterFinished: 30
  template:
    spec:
      containers:
      - name: samplejob
        image: busybox:1.36
        command:
          - sh
          - -c
          - |
            echo "Job 시작"
            sleep 10
            echo "Job 완료"
      restartPolicy: OnFailure
  backoffLimit: 4

=>매니페스트를 이용하지 않고 job을 생성: kubectl create job my-job --image=busybox -- date

7)CronJob
=>일정한 시간 간격을 가지고 작업을 수행하는 워크로드
=>spec.schedule에 스케쥴을 지정합니다.
=>작업은 spec.jobTemplate.spec.template에 지정
=>1분마다 명령을 수행하는 크론잡을 생성
- 매니페스트: sample-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "*/1 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: hello
            image: busybox
            imagePullPolicy: IfNotPresent
            command:
            - /bin/sh
            - -c
            - date; echo Hello from the Kubernetes cluster
          restartPolicy: OnFailure

=>크론잡을 일시 정지: kubectl patch cronjob hello -p '{"spec":{"suspend":true}}

=>동시 실행 제어
- spec.concurrencypolicy에 설정
Allow: 기본값으로 동시 실행에 대한 제한을 하지 않음

Forbid: 이전 잡이 종료되지 않았을 경우 다음 잡은 실행되지 않음

Replace: 이전 잡을 취소하고 잡을 시작


=>일시적으로 작업이 밀리는 경우 어느 정도 시간 여유를 줄것인 지 설정 가능
- spec.startingDeadlineSeconds 에 시간을 설정
- 매시간 작업을 수행하는 크론잡이 있을 때 저 값을 300으로 설정하면 00분에 05분이 될 때가지만 작업을 수행
5분이 넘으면 작업을 수행하지 않음

=>성공한 잡의 개수 나 실패한 잡을 저장하는 개수를 지정할 수 있음
spec.successfulJobsHistoryLimit 와 spec.faildOobsHistoryLimit에 설정
- 성공과 실패한 잡의 로그를 확인할 수 있음

7)노드 자원 보호
=>개요
- 근래에 몇 차례 문제가 발생한 노드에 파드를 할당하면 문제가 발생할 가능성이 높아짐
- 이런 경우에는 특정 노드에는 더 이상 파드를 배치하지 않도록 설정가능한데 그 기능이 cordon
- cordon을 설정하면 더 이상 파드가 배치되지 않음
- 이 설정이 없으면 쿠버네티스는 노드에 파드를 균등하게 배치할려고 합니다.

=>실습
- 매니페스트 생성: sample-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx

- 배포: kubectl apply -f sample-deployment.yaml

- 어떤 노드에 배치되어 있는지 확인: kubectl get pods -o wide

- 파드 개수 늘리기: kubectl scale deployment sample-deployment --replicas=4

- 어떤 노드에 배치되어 있는지 확인: kubectl get pods -o wide
worker1 과 worker2에 균등하게 2개씩 배치

- 파드 개수 복원: kubectl scale deployment sample-deployment --replicas=2

- 어떤 노드에 배치되어 있는지 확인: kubectl get pods -o wide
worker1 과 worker2에 균등하게 1개씩 배치

- worker1의 상태 보존: kubectl cordon worker1

- 파드 개수 늘리기: kubectl scale deployment sample-deployment --replicas=4

- 어떤 노드에 배치되어 있는지 확인: kubectl get pods -o wide
새로운 파드는 worker2에만 배치됨

=>워커 노드의 모든 파드를 일시적으로 다른 곳으로 이동: drain
kubectl drain worker1 --ignore-daemonsets

- 해제: kubectl uncordon worker1

3)쿠버네티스에서의 통신
=>동일한 파드에 존재하는 컨테이너끼리는 localhost를 이용해서 통신이 가능
컨테이너들은 포트를 구분해야 합니다.
=>동일한 노드에 존재하는 다른 파드의 컨테이너와는 파드의 IP를 이용해서 통신이 가능?
=>쿠버네티스 클러스터의 내부 네트워크
- 쿠버네티스 클러스터는 클러스터를 생성하면 노드 상에 파드를 위한 내부 네트워크가 자동으로 구성됨
- 내부 네트워크의 구성은 사용하는 CNI 모듈 구현에 따라 다르지만 기본적으로 노드 별로 다른 네트워크 세그먼트를 구성하고 노드 간의 트래픽은 VXLAN이나 L2 Routing 등의 기술을 사용하여 전송함으로써 노드 간 통신이 가능하게 구성
- 노드 별 네트워크 세그먼트는 쿠버네티스 전체에 할당된 네트워크 세그먼트를 자동으로 분할해 할당하므로 사용자가 설정하지 않아도 됨
- 파드 간의 통신은 서비스를 사용하지 않고 IP를 가지고 가능하지만 서비스를 사용했을 때 얻을 수 있는 장점
파드에 대한 트래픽 Loadblancing

서비스 디스커버리와 클러스터 내부 DNS
- 디플로이먼트를 사용하면 여러 파드를 기동할 수 있는데 파드는 기동될 때마다 각각 다른 IP 주소를 할당받기 때문에 Loadbalancing 하는 구조를 자체적으로 구현하려면 각 파드의 IP를 매번 조회하거나 전송 대상의 목적지를 설정해야 합니다.
- 서비스를 사용하면 여러 파드에 대한 Loadbalancing을 자동으로 구성할 수 있으며 서비스를 EndPoint를 제공

2)ClusterIP Service
=>개요
- 쿠버네티스의 가장 기본이 되는 서비스
- type:ClusterIP 서비스를 생성하면 쿠버네티스 내부에서만 통신 가능한 Internel Network에 생성되는 가상 IP가 할당됨
- ClusterIP 와 통신은 각 노드 상에서 실행 중 인 시스템 구성 요소인 kube-proxy가 파드로 전송
- CluserIP는 쿠버네티스 클러스터 외부에서 트래픽을 수신할 필요가 없는 환경에서 클러스터 내부 LoadBalancer로 사용 
- 기본적으로 쿠버네티스 API에 접근하기 위해서 Kubernetes 서비스가 생성되어 있고 ClusterIP가 발급되어 있음
=>생성
type: ClusterIP를 설정
targetPort에 목적지 컨테이너 포트를 설정
port에는 외부에서 수신할 포트를 설정

=>가상 정적 IP 설정
- 애플리케이션 과 데이터베이스를 배포하는 경우 데이터베이스 서버를 클러스터 내부 DNS 레코드를 사용해서 지정하는 것이 바람직
- IP 주소로 하고자 하는 경우에는 spec.ClusterIP 란에 직접 고정 IP를 설정하는 것이 가능
- 가상 정적 IP를 설정하는 서비스 매니페스트 생성: sample-clusterip-vip.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-clusterip-vip
spec:
  type: ClusterIP
  clusterIP: 10.101.106.108
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
  selector:
    app: sample-app

- 배포: kubectl apply -f sample-clusterip-vip.yaml

- 도메인을 사용하지 않고 IP를 사용하는 이유
개발 과정이어서 도메인이 없는 경우 테스트
DNS를 거치지 않아도 되기 때문에 속도가 빠름

쿠버네티스에서는 IP를 사용하는 경우는 네트워크 연결을 확인하거나 장애를 분석할 때 사용

=>ClusterIP는 한 번 생성되면 변경이 불가능
- 수정하고자 하면 삭제하고 다시 만들어야 합니다.

3)ExternalIP Service
=>개요
- 특정 쿠버네티스 IP 주소:포트번호에서 수신한 트래픽을 컨테이너로 전송하는 형태로 외부와 통신할 수 있도록 하는 서비스

=>워커 노드의 IP를 확인
kubectl get nodes -o wide

192.168.0.201, 192.168.0.202

=>설정할 내용
- spec.externalIPs: 워커 노드의 IP 주소를 설정
- spec.ports[].port: ExternalIP 와 ClusterIP가 사용할 포트번호
- spec.ports[].targetPort: 목적지 컨테이너 포트
- type은 ClusterIP 입니다.

=>서비스 매니페스트 파일: sample-externalip.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-externalip
spec:
  type: ClusterIP
  externalIPs:
  - 192.168.0.201
  - 192.168.0.202
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
  selector:
    app: sample-app

=>노드의 컨테이너 안에서 테스트 해도 되지만 리눅스에서 curl -s http://노드의IP:8080 으로 접속이 가능

=>서비스 확인

4)NodePort Service
=>개요
- NodePort 서비스는 ExternalIP 서비스 와 유사
- ExternalIP는 지정한 쿠버네티스 노드의 IP주소:포트에서 수신한 트래픽을 컨테이너로 전송하는 형태로 외부와 통신을 하는데 NodePort는 모든 쿠버네티스 노드의 IP주소:포트에서 수신한 트래픽을 컨테이너에 전송하는 형태로 외부와 통신
- ExternalIP 서비스에서 전체 노드의 트래픽을 수신할 수 있는 설정과 비슷하지만 Listen할 때 0.0.0.0:포트를 사용해서 모든 IP 주소로 바인드 하는 형태
=>NodePort 설정
- type:NodePort 로 설정
- 별도로 IP를 설정하지 않음
- nodePort를 설정하는데 이 포트는 30000~32767 범위 내여야 하며 설정하지 않으면 임의로 설정됨 
=>서비스 작성: sample-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-nodeport
spec:
  type: NodePort
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
    nodePort: 30080
  selector:
    app: sample-app

=>서비스 배포: kubectl apply -f sample-nodeport.yaml

=>서비스 확인: kubectl get services

=>서비스 확인: curl -s 노드IP:30080
마스터 노드의 IP 와 워커 노드 IP 아무것으로나 통신이 가능

=>노드의 IP를 직접 사용하므로 IP 주소를 외부로 노출시켜야 합니다.

5)LoadBalancer
=>개요
- 로드밸런서 서비스는 서비스 환경에서 클러스터 외부로부터 트래픽을 수신할 때 사용하는 서비스
- 로드밸런서 서비스는 클러스터로 트래픽을 전달해주는 외부 LoadBalancer 와 함께 동작하며 레이블 셀렉터와 일치하는 파드로 트래픽을 전달하는 서비스
- 외부 로드밸런서를 사용할려면 쿠버네티스 클러스터가 구축된 인프라가 이 구조에 맞도록 설계되어 있어야 합니다.
- 현재는 Public Cloud 진영에서 로드밸런서를 제공하고 있고 직접 구축할 클러스터에서는 MetalLB를 이용해서 구현이 가능합니다.
- NodePort 나 ExternalIP는 결국 하나의 쿠버네티스 노드에 제공된 IP 주소로 통신을 하기 때문에 그 노드가 단일 장애점이 될 수 있지만 로드밸런서는 클러스터 외부에 만들어지기 때문에 노드에 장애가 발생해도 크게 문제가 없음
- NodePort를 생성하고 클러스터 외부의 로드밸런서에서 쿠버네티스 노드로 밸런싱을 하는 형태
- 쿠버네티스 노드에 장애가 발생한 경우에는 그 노드에 트래픽을 전송하지 않음으로써 자동으로 복구하게 되어 있지만 LoadBalancer가 노드 장애를 감지하고 목적지에서 제외 처리하기까지의 시간이 필요하므로 그동안 일시적으로 서비스 중단 현상이 발생 

=>로드밸런서 매니페스트 생성: sample-lb.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-lb
spec:
  type: LoadBalancer
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
    nodePort: 30080
  selector:
    app: sample-app

=>배포를 해보면 External IP가 계속 pending 상태
관리형 쿠버네티스가 아니라서 외부 IP가 설정되지 않아서 에러 상태가 됩니다.
해결책은 메탈LB 같은 도구를 이용해서 설정을 해야 합니다.
