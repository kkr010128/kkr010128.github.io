16) 이미지 용량 절감
=>apt를 이용한 패키지 업데이트 와 설치 시 남게 되는 캐시를 제거
- 캐시 관련 삭제 명령: apt clean, apt autoremove, rm -rfv 
- 운영체제 베이스 이미지를 사용한 후 apt를 사용한 경우 효과

- ubuntu base 이미지를 사용하는 웹 서버를 구축(apache2를 설치, /var/www/html 디렉토리에 웰컴 파일을 위치)

	<h1>Hello Docker</h1>

Dockerfile 작성
	FROM ubuntu:20.04

	RUN apt update
	RUN apt install -y tzdata
	RUN apt install -y php
	RUN apt install -y apache2
	
	WORKDIR /var/www/html

	ADD index.html .

	EXPOSE 80

	CMD apachectl -D FOREGROUND

이미지 생성
	docker build -t webapp:1.0 .


Dockerfile을 수정
	FROM ubuntu:20.04

	RUN apt update
	RUN apt install -y tzdata
	RUN apt install -y php
	RUN apt install -y apache2

	RUN apt clean -y
	RUN apt autoremove -y
	RUN rm -rfv /var/lib/apt/lists/* /tmp/* /var/tmp/*

	WORKDIR /var/www/html

	ADD index.html .

	EXPOSE 80

이미지 생성
	docker build -t webapp:2.0 .

- 작업
RUN apt clean -y: 설치에 사용한 패키지 라이브러리, 임시 파일, 오래된 파일을 삭제하는데 autoclean을 사용하면 더 이상 설치되어 있지 않은 패키지들의 .deb까지 삭제

RUN apt autoremove -y: 다른 패키지들의 종속성을 충족시키기 위해 자동으로 설치된 패키지를 삭제


RUN rm -rfv /var/lib/apt/lists/* /tmp/* /var/tmp/*: apt와 연관된 캐시 파일을 모두 삭제하는데 이미지의 시스템 소프트웨어를 다시 업데이트할 계획이 있다면 삭제하지 않는 것이 좋음

- 운영체제에서 많은 패키지를 설치하고 수행하면 디스크 용량이 줄어드는 효과가 있지만 도커 이미지에서는 실제 큰 효과는 없음

17)다단계 빌드
=>개요
- 빌드 단계를 여러 단계로 나누어 빌드하는 것
- 각 빌드 단계는 FROM 명령어로 시작하며 필요한 경우 빌드 단계에 AS 파라미터를 이용해서 이름을 붙일 수 있음
- 빌드가 여러 단계로 구성된 경우 최종 산출물은 마지막 단계의 내용을 담은 도커 이미지
- 각 빌드 단계는 독립적으로 실행되지만 앞선 단계에서 만들어진 디렉토리나 파일을 복사할 수 있음
- 멀티 스테이지 Dockerfile 스크립트를 통해 빌드 과정을 세밀하게 조정하면 최종 산출물인 이미지를 가능한 작게 유지할 수 있음

18)Dockerfile 작성 시 유의사항
=>이미지 크기 최소화
- 이미지가 무거우면 배포 속도가 느려지고 저장 공간을 많이 차지하게 됨
- 경량 베이스 이미지 사용: alpine 이나 slim 버전의 이미지 사용을 권장
- 레이어 수 줄이기
Dockerfile 명령어의 수와 도커 이미지 레이어 수는 동일한데 레이어 수가 많을수록 이미지를 생성하는 빌드 시간이 길어지고 파일 용량도 커짐

RUN 명령어를 여러 번 쓰기보다 &&를 사용해서 하나로 합치면 이미지 레이어 수가 줄어 용량이 최적화됨  

- 불필요한 파일을 삭제

=>빌드 캐시 활용
- 도커는 빌드 시 변경되지 않은 레이어를 재사용하므로 이 효율을 극대화
- 순서가 중요
자주 바뀌는 소스 코드 복사(COPY . .)는 나중에 
잘 바뀌지 않는 의존성 설치는 앞 부분에 배치
- .dockerignore 작성: git, 로그 파일, 로컬 노드 모듈 등 빌드에 필요없는 파일이 이미지에 포함되지 않도록 설정

=>보안 및 관리 설정
- root 계정 사용 지양: 보안을 위해 USER 명령을 사용하여 별도의 일반 사용자 계정으로 프로세스를 실행하는 것이 안전
- 명확한 태그 사용: latest 태그는 버전 관리가 어려우므로 v1.0.1 처럼 명확한 태그 사용을 권장
- 멀티 스테이지 빌드: 빌드 도구는 빌드 단계에서만 사용하고 최종 이미지에는 실행 파일만 남겨서 보안과 용량을 동시에 최적화

=>하나의 애플리케이션은 하나의 컨테이너로
- 하나의 컨테이너에 2개 이상의 애플리케이션을 설정하게 되면 애플리케이션의 결합성이 높아지게 되고 확장성을 저해
- 모놀리식 구성보다는 결합 해제된 애플리케이션(decoupling) 설계나 마이크로서비스 지향적 설계를 고려해야 장애가 발생하더라도 애플리케이션 자체가 유지될 수 있음

=> IaC 환경 개발은 디렉토리 단위로 수행
- 이미지를 빌드할 때 디렉토리의 모든 파일 과 디렉토리를  docker context에 저장한 뒤 작업을 수행
- 별도의 디렉토리를 만들어서 사용하는 것을 권장

=>서버리스 환경으로 개발
- Dockerfile을 통해 미리 설정된 환경을 서버리스 애플리케이션 환경이라고 하는데 이러한 환경은 사용자가 서버를 배포하거나 확장 및 관리를 할 필요가 없음
- 거의 모든 유형의 애플리케이션 또는 백엔드 서비스를 위해 서비리스 애플리케이션을 구축할 수 있으며 애플리케이션을 고가용성으로 확장하는데 필요한 모든 것을 자동으로 처리

9.docker compose
1)개요
=>분산 애플리케이션을 기준으로 보면 Dockerfile은 애플리케이션의 한 부분을 패키징하는 수단
=>Web Frontend, Backend API, Database를 갖춘 애플리케이션을 패키징하려면 각 컴포넌트에 하나씩 3개의 Dockerfile 파일이 필요하고 순서대로 각각의 컨테이너를 실행해야 하는데 이런 수동 프로세스는 오류를 발생시킬 가능성이 높음
=>공통의 목적을 갖는 애플리케이션 스택을 yaml 코드로 지정해서 한 번에 서비스를 올리고 관리할 수 있는 도구가 docker compose
=>docker compose 파일은 애플리케이션의 원하는 상태 즐 모든 컴포넌트가 실행 중일 때 어떤 상태여야 하는지를 기술하는 파일
=>docker container run 명령으로 컨테이너를 실행할 때 지정하는 모든 옵션을 한데 모아놓은 형식의 파일
=>docker compose 파일을 작성하면 docker compose 도구를 사용해서 애플리케이션을 실행
=>docker compose가 컨테이너, 네트워크, 볼륨 등 필요한 모든 docker 객체를 만들도록 docker API에 명령을 내림
=>docker compose로 실행된 컨테이너는 독립된 기능을 가지며 공통 네트워크로 구성되기 때문에 컨테이너 간 통신이 쉬움
=>docker compose는 테스트, 개발, 운영 등의 모든 환경에서 구성이 가능한 오케스트레이션 도구 중 하나이지만 다양한 관리 기능을 가지고 있지 않기 때문에 테스트와 개발환경에 적합
=>실제 운영환경은 많은 관리적 요소가 필요하기 때문에 도커 스웜이나 쿠버네티스와 같은 오케스트레이션 도구가 가지고 있는 자동 확장, 모니터리, 복구 등의 운영에 필요한 기능과 함께 사용되는 것을 권장
=>up 명령으로 한꺼번에 생성
=>down 명령으로 한꺼번에 정지 및 삭제

2)설치
=>Windows 나 Mac에서 Docker Desktop을 설치했으면 설치를 별도로 할 필요가 없음
=>리눅스에서만 별도로 설치
- 다운로드: sudo curl -SL https://github.com/docker/compose/releases/download/v5.5.0/docker-compose-linux-x86_64 -o /usr/local/bin/docker-compose

- 실행을 위해서 권한 변경: sudo chmod +x /usr/local/bin/docker-compose

- 심볼릭 링크 생성: sudo ln -s /usr/local/bin/docker-compose /usr/bin/docker-compose

- 소유자 변경:  /usr/local/bin/docker-compose

- 버전 확인: docker-compose --version

=>apache 웹 서버 컨테이너 생성

=>Maria DB 컨테이너
- 일반적인 컨테이너 생성 명령
docker run -d --name mariadb-server -p 3306:3306 -e MYSQL_ROOT_PASSWORD=your_password -v ~/mariadb/data:/var/lib/mysql --restart always mariadb:10.4.6

- docker-compose 활용
docker-compose.yaml 파일 작성

version: "3.8"
services:
  mariadb:
    image: mariadb:10.4.6
    container_name: mariadb-server
    restart: always
    ports:
      - "3307:3306"
    volumes:
      - ./data:/var/lib/mysql
    environment:
      MYSQL_ROOT_PASSWORD: your_password

docker-compose 컨테이너 생성: docker-compose up -d

docker-compose로 생성된 내용을 확인: docker-compose ps

docker network ls 명령을 수행해보면 docker-compose 가 만든 기본 네트워크를 확인할 수 있습니다.
동일한 네트워크로 만들어져있으면 IP 대신에 이름으로 통신이 가능
