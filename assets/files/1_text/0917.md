2)Action을 위한 yaml 파일을 수정
name: ci-test

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

jobs:
  run-test-code:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest
  build:
    needs: [run-test-code]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt

      - name: Image Build
        run: docker build -t <dockerhub-username>/flaskweb:latest .
      - name: Image Display
        run: docker images
      - name: Docker Hub Login
        uses: docker/login-action@v1
        with:
          username: <dockerhub-username>
          password: ${{ secrets.DOCKERHUB_TOKEN}}
      - name: Image Push
        run: docker push <dockerhub-username>/flaskweb:latest
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to EC2 via SSH
        uses: appleboy/ssh-action@v1.0.3
        env:
          DOCKER_USERNAME: <dockerhub-username>
          DOCKER_REPO: flaskweb
          DOCKER_TOKEN: ${{ secrets.DOCKERHUB_TOKEN}}
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ${{ secrets.EC2_USERNAME }}
          key: ${{ secrets.EC2_SSH_KEY }}
          envs: DOCKER_USERNAME, DOCKER_REPO, DOCKER_TOKEN
          debug: true
          timeout: 30s
          command_timeout: 5m
          request_pty: true
          use_insecure_cipher: true
          script: |
            echo "Successfully Connected"
            echo "Starting deployment for: $DOCKER_USERNAME/$DOCKER_REPO"
            echo "${DOCKER_TOKEN}" | sudo docker login -u "${DOCKER_USERNAME}" --password-stdin
            sudo docker pull $DOCKER_USERNAME/$DOCKER_REPO:latest
            sudo docker stop my-app-container 2>/dev/null || true
            sudo docker rm my-app-container 2>/dev/null || true
            sudo docker run -d --name my-app-container -p 5000:5000 --restart always $DOCKER_USERNAME/$DOCKER_REPO:latest
            sudo docker image prune -f

**Argo CD
1.GitOps
1)개요
=>Git 저장소를 단일 소스로 사용하여 인프라를 코드로 제공하는 방법론 및 관행
=>DevOps 문화가 이룩한 핵심 성과와 접근법을 실현하는 프레임워크를 제공
=>GitOps는 구현 방식에 열린 접근법으로 GitOps 프레임워크는 Git, 쿠버네티스 및 CI/CD 솔루션으로 구축할 수 있음
=>GitOps의 3가지 원칙
- Git을 신뢰할 수 있는 단일 소스로 취급
- 모든 것은 코드로 표현
- 작업은 Git Workflow를 통해 수행

2)GitOps 원칙
=>선언적 구성
- GitOps로 관리되는 시스템은 원하는 상태를 선언적으로 표현
- 명령어 형태로 컨테이너 3개를 만들어라 라고 하는 것이 아니라 애플리케이션은 3개의 컨테이너를 사용하겠다고 선언하면 에이전트가 3이라는 숫자를 맞춰주는 방식

=>버전이 제어되는 불변의 저장소
- 상태 관리에는 불변성 원칙 과 버전 관리 방법론을 적용하며 버전 변경 이력은 완벽하게 유지되어야 한다.

=>자동 반영
- 배포 환경에 설치된 소프트웨어 에이전트가 원하는 상태에 대한 선언적 표현을 Git 저장소에서 자동으로 끌어와야 함
- 변경 사항이 버전 제어 시스템에 반영되면 어떠한 수동 작업도 수행하지 말아야 한다는 것
- 지속적 조정

3)사용하는 이유
=>GitOps는 개발자에게 익숙한 보편적 Git 기반 워크플로를 사용해서 애플리케이션 개발부터 배포, 앱 수명 주기 관리 그리고 인프라 구성에 이르는 기존 프로세스를 확장
=>모든 변경 사항은 Git 저장소 기록을 통해 추적하고 감사하는데 이 접근법은 개발팀 과 운영팀 모두에게 문제를 신속하게 추적하고 재현할 수 있어서 편리하고 보안이 전반적으로 개선됨
=>이점
- 표준 워크플로
- 강화된 보안: 변경 사항을 미리 검토하고 예기치 않은 구성 변동을 감지하여 조취를 취함
- 가시성 및 감사: Git 저장소의 변경 이력을 통해 클러스터의 모든 변경 사항을 캡쳐하고 추적
- 멀티 클러스터 일관성: 많은 환경과 Kubernetes 클러스터들에 대한 배포를 안정적이고 일관되게 구성

4)Kubernetes CI/CD
=>개요
- 일반적인 CI/CD 파이프라인의 경우 CI 프로세스는 제출된 코드를 확인하고 CD 프로세스는 보안, IaC 또는 애플리케이션 프레임워크에 설정된 경계 등에 대한 요구 사항을 확인하고 적용
- 모든 코드 변경 사항을 추적하므로 업데이트가 쉬워지고 롤백이 필요한 경우에 대비해 버전 관리 기능도 제공
- CD는 GitOps의 도메인이며 CI와 연동해서 다양한 환경에 앱을 배포
- 쿠버네티스를 이용하면 클러스터 내부에 CI/CD 파이프라인을 쉽게 구현 가능
- CI 소프트웨어는 애플리케이션을 나타내는 컨테이너 이미지를 생성해서 컨테이너 이미지 레지스트리에 저장
- pull request와 같은 Git 워크플로를 통해 배포할 앱의 명세서 격인 매니페스트를 변경한 후 CD 동기화 루프를 개시

소스 Git 저장소 -> CI를 진행 -> 이미지 레지스트리

Git 저장소 -> CD를 수행 -> 쿠버네티스가 CD 작업 과정을 감시하다가 변경 사항이 발견되면 이미지 레지스트리에서 이미지를 다시 다운로드

=>Kubernetes에서 GitOps를 접목한 앱 배포 방법
- GitOps는 플랫폼에 구애받지 않는 열린 접근법이므로 그 애플리케이션 배포 모델은 쿠버네티스 클러스터 내부에 구축될 수 도 있고 여러 클러스터에 걸친 공통 플랫폼 형태로 구축될 수 있음
- 쿠버네티스 외부에 GitOps 도구를 구축하면 쿠버네티스는 앱 배포를 위한 플랫폼으로만 이용되고 클러스터 내부에 GitOps 도구를 구축하면 GitOps 엔진은 쿠버네티스 클러스터 안에서 실행되어 해당 클러스터에 앱을 스스로 동기화
- Git Ops 수명 주기
배포: Git에 저장된 매니페스트를 배포

모니터링: Git 저장소나 클러스터 상태를 모니터링

변화 감지: 현재 클러스터 구성 과 Git에 설명된 내용의 차이를 감지

2.Argo CD
1)개요
=>예전에는 개발, 테스트, staging, production 환경으로 구분해서 동작
=>kubernetes에서는 환경 별로 kubernetes 클러스터를 사용하던가 하나의 클러스터 안에 namespace로 구분
=>namespace를 분리하는 방식
- 별도의 namespace를 생성하고 애플리케이션을 구성하는데 필요한 모든 환경(ConfigMap, Secret, Ingress 등)을 추가해 나가는 방식
- 이 방식은 시간이 지나면서 구성 드리프트가 발생하는데 개발 환경 클러스터 namespace에만 최신 버전의 애플리케이션이 배포되거나 네트워크 정책같은 리소스를 수정하게 되면 나머지 다른 환경을 개발 환경과 동일하게 맞추기 위해서 다른 부분을 확인해서 수동으로 변경을 해야 하는데 이 부분을 단순화시키기 위해서 kustomize 나 helm 같은 패키지 매니저를 사용
- Helm을 사용하면 여러 버전을 만들고 각 환경에 맞는 원하는 버전을 배포할 수 있지만 이력을 추적하기 어렵고 관리의 복잡성이 증가
=>Argo CD는 선언전인 Kubernetes의 GitOps CD 도구
=>ArgoCD 안에 있는 애플리케이션 컨트롤러가 운영 중인 애플리케이션을 지속적으로 관찰하고 애플리케이션 상태 와 원천 소스인 Git Repository에 작성한 의도한 상태를 비교해서 변경 내용을 적용
=>사용 사례
- 배포 자동화: ArgoCD Controller는 자동으로 클러스터를 Git Repository에 의도한 상태로 푸시를 하게 되는데 Argo Event Framework 나 수동적인 요청을 통해서 가능
- 관찰 가능성: ArgoCD는 애플리케이션 상태가 깃에서 의도한 상태와 동기화되어 있는지 식별할 수 있는 UI 와 CLI를 제공하고 Argo CD Notification 엔진을 제공
- 멀티 테넌시: 여러 클러스터를 관리하고 배포 가능

3)핵심 개념
=>조정
- Git Repository에 담긴 의도한 상태를 현재 상태의 클러스터와 일치시켜야 하며 필요한 환경에 올바르게 전달을 해야 함
- Git Repository에 있는 helm 차트를 kubernetes yaml로 랜더링을 하고 클러스터의 의도한 상태와 비교하는 이를 동기화 상태(sync status)라고 하는데 이 때 다르다고 판단되면 자동 혹은 수동으로 kubectl apply 사용해서 적용
- Argo CD는 여러 템플릿 도구들을 지원하고 있는데 이런 도구들을 래퍼로 사용하는 것이 아니라 GitOps 원칙에 맞는 선언적 도구로 사용해서 원하는 상태를 배포하는데 목적을 두고 있음

5)Argo CD를 이용한 Application 배포
=>리소스 파일 생성: application.yaml
kind: Application
metadata:
  name: nginx-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.bitnami.com/bitnami
    chart: nginx
    targetRevision: 22.6.5
    helm:
      parameters:
        - name: "service.type"
          value: "NodePort"
        - name: "replicaCount"
          value: "2"
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-deploy
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

- 배포: kubectl apply -f application.yaml

argocd app sync nginx

7)Argo CD  Autopilot
=>개요
- Argo CD를 GitOps 방식으로 설치/운영하기 쉽게 만들어주는 툴
- Argo CD를 수동으로 설치하고 Application을 하나 하나 정의했지만 Autopilot은 ArgoCD 자체 설치 + 애플리케이션 관리 구조를 Git Repository 중심으로 자동화 함

=>기능
- GitOps를 사용해 부트스트랩 Argo CD 애플리케이션을 생성하고 관리할 수 있음
- GitHub Repository를 짜여진 구조로 세팅해 새로운 서비스를 추가하고 Argo CD의 수명 주기에 적용
- 각각 다른 환경에서 애플리케이션을 업데이트하고 승격할 수 있게 함
- 재배 복구를 대비할 수 있고 필요한 모든 유틸리티와 애플리케이션에 대한 장애 조치 클러스터를 부트스트랩
- Argo CD 애플리케이션에 시크릿에 대한 암호화도 지원

=>아키텍쳐
- 부트스트랩 단계에서 Argo CD를 배포할 때 오토파일럿은 Kubernetes 클러스터와 통신하고 그 후에는 더 이상 kubernetest 클러스터에 접근하지 않음
- 접근하는 것은 GitOps Repository 뿐
- 새로운 Argo CRD를 Kubenetes 클러스터에 추가할 때 오토파일럿은 Argo CD 서버에 접근함

=>설치
