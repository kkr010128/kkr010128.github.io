=>emptyDir
- 파드용 임시 디스크 영역으로 사용할 수 있는 종류로 파드가 종료되면 삭제됨
- 호스트(노드 컴퓨터)의 임의 영역을 마운트 할 수 없으며 호스트에 있는 파일을 참조할 수 도 없음
- emptyDir을 사용하는 파드 매니페스트: sample-emptydir.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-emptydir
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: /cache
      name: cache-volume
  volumes:
  - name: cache-volume
    emptyDir: {}

- 배포: cache 라는 디렉토리가 생성되고 파드와 연결: kubectl apply -f sample-emptydir.yaml

- 확인: kubectl exec -it sample-emptydir -- df -h | grep /cache

- 디스크 크기 제한을 128M로 하는 파드를 생성하는 매니페스트
apiVersion: v1
kind: Pod
metadata:
  name: sample-emptydir
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: /cache
      name: cache-volume
  volumes:
  - name: cache-volume
    emptyDir:
      sizeLimit: 128Mi

- 파드를 배포하기: kubectl apply -f sample-emptydir.yaml 

- 파드를 실시간으로 감시하기: kubectl get pods --watch

- 다른 터미널에서 파일을 더미로 만들기(1M 짜리 파일을 150개 만들기): kubectl exec -it sample-emptydir -- dd if=/dev/zero of=/cache/
dummy bs=1M count=150

- 파일의 크기가 디스크 제한을 넘어서서 파드가 종료됩니다.

- 디스크 대신 메모리를 사용하고자 하는 경우 설정
emptyDir:
  medium: Memory

=>hostPath
- 개요
쿠버네티스 노드 상의 영역을 컨테이너에 매핑하는 플러그인

호스트의 영역을 사용하기 때문에 어디에 매핑할 지 설정을 해주어야 합니다.

type에 Directory/DirectoryOrCreate/File/Socket/BlockDevice 등을 선택할 수 있음

일반적인 영구 저장용으로는 사용하지 않고 특수 환경에서 사용

- 사용하는 경우
노드 시스템 로그 수집 및 모니터링: Fluentd, Promtail, Filebeat 같은 로그 수집 에이전트가 호스트 노드의 /var/log 또는 /var/log/pods 디렉토리에 접근해야 할 때 사용

컨테이너 런타임 및 소켓 제어: Docker 도는 Containerd 소켓을 마운트하여 파드 내부에서 노드의 컨테이너 상태를 직접 조회/관리할 때 사용

노드 하드웨어/OS 커널 정보 수집: Node Exporter, cAdvisor 등의 메트릭 수집기가 호스트의 /sys, /proc 파일 시스템을 읽을  때 사용

단일 노드 테스트/개발 환경(Minikube 등): 클라우드 스토리지 없이 로컬 파일 시스템을 빠르게 파드와 연동할 때 사용

- 주의 사항 및 단점
파드 스케줄링 싱 데이터 불일치: 멀티 노드 환경에서 파드가 재시작되어 노드 A에서 노드 B로 재배치되면 노드 A에 남겨진 hostPath 데이터를 노드 B의 파드는 읽을 수 없음 - 일반 데이터베이스 나 상태 저장용으로 부적합

보안 취약점: 컨테이너가 루트 권한으로 호스트의 민감한 디렉토리(/etc, /root)를 쓰기 권한으로 마운트 하면 호스트 시스템 전체가 탈취될 수 있으므로 필요한 경우라면 readOnly: true로 지정하는 것이 안전 

- hostPath를 사용하는 파드 매니페스트: sample-hostpath.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-hostpath
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: /srv
      name: hostpath-sample
  volumes:
  - name: hostpath-sample
    hostPath:
      path: /etc
      type: DirectoryOrCreate

- 배포: kubectl apply -f sample-hostpath.yaml

- 파드 상세 정보에서 마운트 확인: kubectl describe pod sample-hostpath 

- 파일을 생성하고 노드를 확인: kubectl exec -it sample-hostpath -- sh -c "echo 'hostPath-test' > /srv/test.txt"


=>downwardAPI
- 개요
Downward API는 파드 내부에서 실행 중인 컨테이너 애플리케이션이 자신의 정보를 쿠버네티스 API 서버와 통신하지 않고도 환경 변수나 파일 형태로 주입받아 사용할 수 있게 해주는 기능

쿠버네티스 시스템에서 컨테이너 내부 애플리케이션으로 메타 데이터를 내려보낸다는 의미에서 Downward라는 이름을 붙임

- 사용하는 이유
쿠버네티스 API 클라이언트 종속성 제거(결합도 감소): 애플리케이션이 자신의 파드 이름이나 IP를 알기 위해 kubectl 바이너리를 설치하거나 k8s 클라이언트 SDK(프로그래밍 언어 별로 존재)를 코드에 포하시킬 필요가 없음

보안성 향상(RBAC 권한 최소화): 파드가 메타 데이터 조회를 위해 API Server 와 통신할 필요가 없으므로 해당 파드의 ServiceAccount에 불필요한 Pod 조회 권한을 부여하지 않아도 됨

순수 표준 인터페이스 사용(이식성 유지): 애플리케이션 코드는 환경 변수 나 파일 마운트를 읽는 표준 방식으로 동작하므로 쿠버네티스 전용으로 코드를 수정할 필요가 없음

- downward API를 사용하는 매니페스트(sample-downward-api.yaml)
apiVersion: v1
kind: Pod
metadata:
  name: sample-downward-api
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: /srv
      name: downward-api-volume
  volumes:
  - name: downward-api-volume
    downwardAPI:
      items:
      - path: "podname"
        fieldRef:
          fieldPath: metadata.name
      - path: "cpu-request"
        resourceFieldRef:
          containerName: nginx-container
          resource: requests.cpu

- 배포: kubectl apply -f sample-downward-api.yaml

- 확인: kubectl exec -it sample-downward-api -- ls /srv

=>영구 볼륨
- 개요
영구 볼륨은 영속성 영역으로 확보된 볼륨
볼륨은 파드 정의 안에 직접 지정하는 형태로 연결하지만 영구 볼륨은 개별 리소스로 생성한 후 사용
매니페스트를 사용하여 영구 볼륨 리소스를 생성
영구 볼륨은 Config & Storage Resource가 아닌 Cluster Resource로 분류 됨
영구 볼륨은 기본적으로 네트워크를 통해 디스크를 어태치하는 디스크 타입
단일 노드에서는 테스트용으로 hostPath가 제공되지만 영구 볼륨으로는 실용적이지 않음
영구 볼륨은 pluggable 한 구조

- 종류
Public Cloud의 디스크 서비스(AWS Elatic Block Store, GCE Persistent Disk, Azure File 등)

NFS(Network File System)

iSCSI(Internet Small Computer Systems Interface)

Ceph(RBD, 차세대 오픈소스 분산 스토리지 시스템)

OpenStack Cinder(오픈 스택 클라우드 환경의 블록 스토리지)

GlusterFS(분산 파일 시스템의 한 종류)

Container Storage Interface

- 컨테이너 스토리지의 흐름
Storage Class: 관리자가 어떤 종류의 스토리지를 사용할 지 정의

PersistentVolumeClaim(PVC): 개발자가 얼마큼의 디스크가 필요한 지 요청

CSI Driver: 요청을 받은 CSI 드라이버가 뒷단의 스토리에 명령을 내려 실제 볼륨을 생성

PersistentVolume(PV): 생성된 볼륨이 쿠버네티스 자원으로 등록되고 컨테이너에 연결

- 로컬 컴퓨터에 영구 볼륨 생성
현재 컴퓨터에 디렉토리 생성: mkdir -p /home/adam/data

PV 매니페스트 작성: pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv
spec:
  capacity:
    storage: 5Gi	#용량인데 나중에 pvc는 가장 비슷한 크기의 pv를 사용
  accessModes:
    - ReadWriteOnce	#RWO(단일 노드에서 읽고 쓰기 가능), ROX(여러 노드에서 Read 가능), RWX(여러 노드에서 Read/Write 가능)
  persistentVolumeReclaimPolicy: Retain #영구 볼륨 클레임이 사용된 후 삭제되었을 때 어떻게(Delete, Retain, Recycle-현재 Deprecated)
  storageClassName: manual
  hostPath:
    path: "/home/adam/data"

PV 배포: kubectl apply -f pv.yaml

PV 확인: kubectl get persistentvolumes

다른 종류의 스토리지를 사용할 때는 아래 부분을 변경
  hostPath:
    path: "/home/adam/data"

NFS를 사용하는 경우 변경
  nfs:
    server: 서버의 IP
    path: 마운트할 디렉토리

PV를 사용하는 PVC를 생성(pvc.yaml)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: manual

PVC 배포: kubectl apply -f pvc.yaml

PVC 확인: kubectl get persistentvolumeclaims
PVC 와 PV가 연결되었는지 확인

PVC를 사용할 pod 매니페스트(pod.yaml)
apiVersion: v1
kind: Pod
metadata:
  name: local-pod
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: "/usr/share/nginx/html"
      name: local-storage
  volumes:
    - name: local-storage
      persistentVolumeClaim:
        claimName: local-pvc

배포 - kubectl apply -f pod.yaml

파드 확인: kubectl get pods -o wide
배치된 노드를 확인 - worker1

배치된 노드(worker1)에서 파일을 생성: sudo nano /home/adam/data/test.txt

파드 확인(마운트 한 디렉토리 확인): kubectl exec -it local-pod -- cat /usr/share/nginx/html/test.txt


=>NFS 영구 볼륨 클레임
- NFS Server 생성
sudo apt update

패키지 설치: sudo apt install -y nfs-kernel-server

공유할 디렉토리 생성: sudo mkdir -p /nfs/k8s

접근 권한 변경: sudo chmod 777 /nfs/k8s

Export 설정 추가: /etc/exports 파일에 추가
/nfs/k8s *(rw,sync,no_subtree_check,no_root_squash)

변경한 설정 적용: sudo exportfs -ra

적용 확인: sudo exportfs -v

- 쿠버네티스 클러스터에 연결
nfs-server의 IP: 192.168.0.100

모든 노드에 nfs 클라이언트 설치: sudo apt install -y nfs-common

테스트를 위한 디렉토리 생성: sudo mkdir -p /mnt/nfs-test

마운트: sudo mount -t nfs 192.168.0.100:/nfs/k8s /mnt/nfs-test

확인: df -h
2개의 디렉토리가 연결되었는지 확인

언마운트: sudo umount /mnt/nfs-test

- nfs-server를 이용하는 PV-PVC 활용
pv를 위한 매니페스트 생성(nfs-pv.yaml)
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-storage
  nfs:
    server: 192.168.0.100
    path: /nfs/k8s

배포: kubectl apply -f nfs-pv.yaml

pvc를 위한 매니페스트(nfs-pvc.yaml)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nfs-pvc
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 5Gi
  storageClassName: nfs-storage

pvc 배포: kubectl apply -f nfs-pvc.yaml

pvc 확인: kubectl get pvc

pvc를 사용하는 파드 매니페스트(nfs-pod.yaml)
apiVersion: v1
kind: Pod
metadata:
  name: nfs-test-pod
spec:
  containers:
  - image: nginx:1.17
    name: nginx-container
    volumeMounts:
    - mountPath: "/usr/share/nginx/html"
      name: nfs-volume
  volumes:
    - name: nfs-volume
      persistentVolumeClaim:
        claimName: nfs-pvc

배포: kubectl apply -f nfs-pod.yaml

확인
pod에 접속: kubectl exec -it nfs-test-pod -- bash
파일 생성: echo "Hello kubernetes NFS" > /usr/share/nginx/html/index.html

NFS Server에서 확인: cat /nfs/k8s/index.html
