**Kubernetes
2.Kubernetes 기본
1)분리성 확보
=>namespace
- 가상적인 쿠버네티스 클러스터 분리 기능
- 완전한 분리 개념이 아니기 때문에 용도는 제한되지만 하나의 쿠버네티스 클러스터를 구분하고자 하는 경우 사용
- 기본적으로 제공되는 namespace
kube-system: 쿠버네티스 클러스터 구성 요소와 애드온이 배포될 네임스페이스

kube-public: 모든 사용자가 사용할 수 있는 ConfigMap 등을 배치하는 네임스페이스

kube-node-lease: 노드의 하트비트 정보를 저장하기 위한 Lease 리소스가 저장되는 네임스페이스

default: 기본 네임스페이스

=>namespace & RBAC
- RBAC(Role-Base Access Control)는 클러스터 조작에 대한 권한을 네임스페이스별로 구분할 수 있고 네트워크 정책과 함께 사용하여 네임스페이스 간의 통신을 제어할 수 있는 구조
- 네임스페이스만으로는 높은 분리성을 확보하기 어렵지만 RBAC나 네트워크 정책을 사용하면 분리성을 높일 수 있음

2)kubectl
=>개요
- 쿠버네티스의 클러스터 조작은 모두 쿠버네티스 마스터의 API를 통해 수행
- 직접 API에 요청을 보내거나 클라이언트 라이브러리를 사용하여 클러스터를 조작할 수 도 있지만 수동으로 조작하는 경우에는 CLI 도구인 kubectl을 사용하는 것이 일반적

=>인증 정보
- kubectl이 쿠버네티스 마스터와 통신을 할 때는 접속 대상의 서버 정보, 인증 정보가 필요
- kubectl은 kubeconfig(~./kube/config)에 쓰여 있는 정보를 사용하여 접속
- 일반적인 매니페스트와 동일한 형식으로 작성

=>컨텍스트 관련 명령
- 현재 컨텍스트 확인: kubectl config current-context
- 명령어를 지정할 때 특정 컨텍스트를 지정: kubectl get pods --context 컨텍스트이름

=>리소스 생성/삭제/갱신
- kubectl run
가장 간단하게 리소스를 생성

실행 커맨드에 각종 정보를 입력해서 생성

실행 시 입력한 정보가 남지 않기 때문에 재실행하기가 어렵고 문제가 발생했을 때 원인을 찾거나 해결 방법을 공유하는 것이 불편 

테스트나 간단한 pod를 생성할 때는 유용하지만 많은 configuration을 활용한다면 불펴

파드를 생성: kubectl run nginx --image=nginx

파드 확인: kubectl get pods

- kubectl create
종류를 지정해서 생성

deployment를 생성: kubectl create deployment dpy-nginx --image=nginx

확인
	kubectl get pods
	kubectl get deployments

리소스 파일 이용 가능

기존에 리소스가 존재하면 에러가 발생

리소스를 위한 yaml 파일 작성: sample-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  containers:
  - name: nginx-container
    image: nginx

생성: kubectl create -f sample-pod.yaml

삭제
	kubectl delete 종류 이름
	kubectl delete -f 파일명
	kubectl delete --all: 모든 리소스 삭제

삭제는 비동기로 처리되어 처리가 바로 완료되지 않음

--wait 옵션을 사용하면 리소스의 삭제 완료를 기다렸다가 명령어 실행을 종료할 수 있는데 실행이 완료될 때 까지 대기

리소스를 강제로 즉시 삭제하려면 정지까지 유예 기간을 0으로 하는 --grace-period 0 옵션과 강제로 삭제하는 --force 옵션을 사용

쿠버네티스 버전 1.8 이후 부터는 --force를 옵션을 설정하면 --grace-period 0 옵션도 자동으로 추가됩니다. 

삭제 완료 대기: kubectl delete -f sample-pod.yaml --wait

- 리소스 업데이트: kubectl apply
변경 부분이 있으면 적용하고 없으면 적용하지 않는데 리소스가 없으면 생성
적용: kubectl apply -f sample-pod.yaml

- 리소스 생성에도 kubectl apply를 사용하라고 하는 이유
생성 과 업데이트 시 다른 명령어를 사용하면 스크립트나 CI/CD 에 포함될 때 조건 분기를 이용해야 하기 때문입니다.

create 와 apply를 섞어서 사용하면 apply를 실행할 때 변경 사항을 검출하지 못하는 경우가 있습니다.

=>파드 재시작
- Deployment 등 의 리소스와 연결되어 있는 모든 파다를 재가동 - rollout restart
- 파드 기동 시 처리를 재실행하고 싶을 때나 시크릿 리소스에서 참조되는 환경 변수를 변경하고 싶을 때 사용
- 리소스와 연결되어 있지 않은 단독 파드에는 사용할 수 없음
- 리소스 파일 작성(sample-deployment.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx

- 리소스 생성: kubectl apply -f sample-deployment.yaml
- kubectl rollout restart deployment sample-deployment

=>generateName
- 개요
기본적으로 kubectl apply 명령어를 사용해서 리소스를 생성하는 것이 바람직한데 kubectl create를 이용하면 난수가 있는 이름의 리소스를 생성할 수 있음
metadata.name 대신 metadata.generateName을 지정하고 리소스를 생성하고 그 이름에 접두사를 붙여 이름이 자동으로 생성되도록 합니다.

- 리소스 매니페스트 파일(sample-generatename.yaml)
apiVersion: v1
kind: Pod
metadata:
  generateName: sample-generatename-
spec:
  containers:
  - name: nginx-container
    image: nginx

- 리소스 생성: kubectl create -f sample-generatename.yaml

=>리소스 상태와 체크
- kubectl 명령어를 연속적으로 실행하여 리소스를 조작할 때는 다음 명령어를 실행하기 전에 그때까지 작업한 리소스가 의도한 상태가 된 후 다음 명령어를 실행해야 하는 경우가 있는데 사용할 수 있는 것이 kubectl wait 명령어인데 실행하면 --for 옵션에 지정한 상태가 되기까지 최대 --timeout 옵션에 지정하는 시간까지 종료하지 않고 대기

- pod의 상태
Pending: 파드가 생성 요청되었으나 아직 하나 이상의 컨테이너가 생성되지 않았거나 노드에 스케쥴링 대기 중인 상태(이미지 다운로드 포함)

Running: 파드가 노드에 바인딩되었고 모든 컨테이너가 생성되었으며 최소 하나의 컨테이너가 실행 중이거나 시작/재시작 중인 상태

Completed(Succeeded): 파드 내의 모든 컨테이너가 생성되었으며 최소 하나의 컨테이너가 실행 중이거나 시작/재시작 중인 상태로 주로 Job 이나 CronJob에서 보여지는 결과

Failed: 파드 내 모든 컨테이너가 종료되었으나 최소 하나 이상의 컨테이너가 오류로 비정상 종료(0이 아닌 exit code)된 상태

Unknown: 노드 통신 오류 등으로 인해 파드의 상태를 API 서버가 확인할 수 없는 상태

CrashLoopBaskOff: 컨테이너가 시작된 직후 오류로 비정상 종료되어 쿠버네티스가 재시작을 반복하면 대기 시간을 늘리는 상태

ImagePullBackOff / ErrImagePull: 컨테이너 이미지를 다운로드 하지 못하는 상태

ContainerCreating: 노드에 볼륨을 마운트하거나 네트워크 인터페이스를 설정하는 등 컨테이너를 생성하는 중인 상태

OOMKilled: 메모리 부족

Terminating: 컨테이너가 정상 종료 절차를 진행 중인 상태

Init:0/N: 본 애플리케이션 컨테이너 실행 전 초기화 컨테이너가 동작중이거나 실패한 상태

- sample-pod가 정상적으로 기동할 때 가지 대기
kubectl apply -f sample-pod.yaml

kubectl wait --for=condition=Ready pod/sample-pod

- 모든 파드가 스케쥴링 될 때 까지 대기
kubectl wait --for=condition=PodScheduled pod --all

- 모든 파드가 삭제될 때 까지 파드마다 5초씩 대기
kubectl wait --for=delete pod --all --timeout=5s

- 모든 파드를 삭제한 후 곧바로 kubectl wait를 실행
kubectl delete pod --all --wait=false 

- 모든 파드가 삭제될 때 까지 대기
kubectl wait --for=delete pod --all

=>매니페스트 파일 설계
- 하나의 매니페스트 파일에 여러 리소스를 정의
매니페스트 파일은 여러 리소스를 한 개의 매니페스트 파일에 정의할 수 있기 때문에 어떤 서비스에서 사용할 여러 종류의 리소스를 한 개의 매니페스트 파일로 통합 가능

일반적인 사용 사례로는 파드를 기동하는 워크로드 API 카테고리의 리소스 와 외부에 공개하는 서비스 API 카테고리의 리소를 매니페스트에 통합하여 작성하는 방법을 고려

실행 순서를 정확히 지켜야 하거나 리소스 간의 결합도를 높이고 싶다면 한 개의 매니스페스를 사용하는 것이 좋지만 공통으로 사용하는 설정 파일이나 패스워드 등 은 여러 리소스스에서 사용되는 경우가 있기 때문에 공통으로 사용되는 리소스는 별도 매니페스트로 분리하는 것이 좋음

- 하나의 매니페스트에 여러 개의 리소스를 정의: sample-multi-resource-manifest.yaml
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order1-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.17
---
apiVersion: v1
kind: Service
metadata:
  name: order2-service
spec:
  type: LoadBalancer
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
  selector:
    app: sample-app

- 매니페스트 적용: kubectl apply -f sample-multi-resource-manifest.yaml

- 하나의 매니페스트에 여러 개의 리소스를 정의한 경우 앞에서부터 순차적으로 적용하기 때문에 앞에 내용에 문제가 있으면  뒤의 내용은 수행되지 않습니다.

- 여러 매니페스트 파일을 동시에 적용
여러 매니페스트 파일을 동시에 적용하려면 디렉토리 안에 적용하고 싶은 여러 매니페스트 파일을 배치해두고 kubectl apply 명령을 실행할 때 그 디렉토리를 지정

파일명 순으로 매니페스트 파일이 적용되기 때문에 순서를 제어하고 싶을 때는 파일명 앞에 연번의 인덱스 번호 등을 지정하여 사용 

디렉토리 안에 디렉토리가 존재하는 경우 kubectl apply -f ./ -R 옵션을 이용하면 재귀적으로 디렉토리 안에 존재하는 매니페스트 파일을 적용할 수 있음

- 매니페스트 파일을 저장할 디렉토리 생성: dir
- dir 디렉토리에 sample-pod1.yaml 파일 생성
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod1
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17

- dir 디렉토리에 sample-pod2.yaml 파일 생성
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod2
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17

- 매니페스트 설계 방침
아주 규모가 크지 않을 때는 시스템 전체를 구성하기 위한 모든 마이크로서비스의 매니페스트 파일을 하나의 디렉토리로 통합하여 사용

한 개의 디렉토리에 파일 통합이 어려울 정도로 거대한 시스템인 경우 분리가 가능하다면 서브 시스템이나 팀 별로 디렉토리를 나누어서 사용

마이크로서비스마다 디렉토리로 구분해서 리소스 종류 별로 파일을 생성할 수 있는데 가독성이 높아진다는 장점은 있지만 적용 순서 제어가 어렵다는 단점도 있음

=>어노테이션과 레이블
- 쿠버네티스에서는 각 리소스에 대해 어노테이션 과 레이블이라는 메타데이터를 부여할 수 있음
- 차이
Label: 리소스를 분류/검색하는 태그
Annotation: 추가적인 긴 설명/메타데이터 저장소

구분			Label						Annotation
목적			리소스 분류, 선택, 검색에 이용		리소스에 추가 설명/메타데이터 저장
검색/Selector지원	지원						지원 안함(Selector로 사용 못함)

=>Prune을 이용한 리소스 삭제
- 매니페스트 관리와 자동 적용
쿠버네티스를 운용할 때 수동으로 kubectl 명령어를 실행하는 일은 거의 없는데 수동으로 운영하는 것은 휴먼 에러가 발생하기 쉽고 사람이 파악하고 관리할 수 있는 리소스 수에 한계가 있기 때문에 권장하지 않고 이에 대한 해결책의 하나로 매니페스트를 Git 저장소에서 관리하고 변경이 있을 때만 kubectl apply 명령어를 사용하여 자동으로 매니페스트를 적용시키는 방법을 사용

매니페스트에서 삭제된 리소스를 삭제하는 데 필요한 kubectl delete 명령어를 자동으로 실행하려면 매니페스트에서 삭제된 리소스를 감지할 수 있는 구조를 만들어야 함

kubectl apply에서 --prune 옵션을 이용

업데이트 된 매니페스트에 대해서 kubectl apply --prune 명령을 실행하면 매니페스트에서 삭제된 리소스도 자동으로 삭제

디렉토리 생성: prune

  labels:

  containers:
  - name: nginx-container
    image: nginx:1.17

디렉토리를 적용: kubectl apply -f ./prune
