**CI/CD
1.CI/CD
1)일반적인 개발 워크플로
=>로컬에서 단위 테스트 실행
- 중앙 레포지토리에서 최신 코드를 로컬로 가져온 후 요구 사항을 구현
- 요구사항을 구현할 때 TDD(테스트 주도 개발)를 많이 사용
- 구현된 코드는 단위 테스트를 통과할 때 까지 반복적으로 수정

=>중앙 레포지토리로 코드 푸시 및 병합

=>병합 후 코드 컴파일
- 구현을 완료한 코드가 메인 브랜치에 병합되면 코드 컴파일을 수행
- 새로 병합된 코드로 인해 기존에 없던 컴파일 오류가 발생할 수 있음

=>컴파일된 코드에서 테스트 실행
- 단위 테스트 와 통합 테스트를 실행해 회귀 테스트를 수행해해서 결함이 있는지를 확인
- 정적 분석(코딩 표준 준수 및 불필요한 코드의 존재 여부를 확인하는 과정) 같은 작업을 수행하기도 함

=>아티팩트 배포
- 병합된 코드의 단계별 품질 점검을 끝내면 모든 코드를 패키징하고 최종 사용자가 사용할 수 있도록 서버에 배포
- 아티팩트는 일반적으로 하나의 압축된 파일

2)CI/CD 개요
=>기본 개념은 지속적인 통합(Continuous Integration), 지속적인 서비스 제공(Continuous Delivery), 지속적인 배포(Continuous Deployment)
=>애플리케이션 워크플로를 자동화해서 애플리케이션을 보다 짧은 주기로 고객에게 제공하는 방법
=>자동화해서 개발 및 운영 팀에서 발생하는 문제(Integration Hell)를 해결하기 위한 방법
=>지속적인 서비스 제공이 지속적인 배포를 포함하기도 합니다.
=>CI/CD는 파이프라인으로 표현되는 실제 프로세스를 의미하고 애플리케이션 개발에 지속적인 자동화 및 지속적인 모니터링을 추가하는 것을 의미

3)CI - 지속적인 통합
=>개발 팀이 작은 변경 사항을 구현하고 코드를 버전 제어 레포지토리에 자주 체크인하도록 하는 코딩 철학이자 일련의 관행
=>폴리 글랏의 문제: 애플리케이션은 다양한 플랫폼과 도구에서 코드를 개발해야 하기 때문에 팀은 작은 변경 사항을 통합하고 검증하기 위한 매커니즘이 필요
=>기술 목표는 애플리케이션을 빌드, 패키지, 테스트 하나는 일관되고 자동화된 방법을 설정하는 것 
=>통합 프로세스의 일관성을 유지하면 팀이 코드 변경을 더 자주 커밋할 가능성이 높아져 공동 작업과 소프트웨어 품질이 향상
=>모든 개발을 완료한 후에 품질 관리를 적용하는 고전적인 방법을 대체하는 방법으로 소프트웨어의 질적 향상과 소프트웨어를 배포하는데 걸리는 시간을 줄이는데 초점을 맞춤

4)CD
=>지속적인 서비스 제공(Continuous Delivery)
- 개발자들이 애플리케이션에 적용한 변경 사항이 버그 테스트를 거쳐 레포지토리(이미지 저장소 또는 컨테이너 레지스트리)에 자동으로 업로드하는 것
- 운영팀은 이 레포지토리에서 애플리케이션을 실시간 프로덕션 환경으로 배포
- 최소한의 노력으로 새로운 코드를 배포하는 것

=>지속적인 배포(Continuous Deployment)
- 변경 사항을 레포지토리에서 고객이 사용 가능한 프로덕션 환경까지 자동으로 릴리스하는 과정
- 애플리케이션 제공 속도를 저해하는 수동 프로세스로 인한 운영 팀의 프로세스 과부하 문제를 해결

5)지속적 인도
=>전통적 인도 서비스의 문제점
- 느린 인도 기간
- 느린 피드백 주기
- 자동화 미비
- 위험한 핫픽스: 간단한 테스트만 수행하거나 테스트 생략
- 스트레스
- 의사 소통 부족
- 책임의 분산
- 낮은 업무 만족도

=>지속적 인도
- 장점
빠른 제품 인도
빠른 피드백 주기
위험도가 낮은 릴리스
유연한 릴리스 가능

6)자동 배포 파이프라인
코드 변경 -> 지속적 통합 -> 자동 인수 테스트 -> 구성 관리 변경 -> 배포

7)컨테이너 인프라 환경에서의 CI/CD
=>개발자가 소스를 commit 하고 push 하면 CI 단계로 진입
=>CI 단계에서는 애플리케이션이 자동 빌드되고 테스트를 거쳐 배포할 수 있는 애플리케이션인지 확인
=>테스트를 통과하면 신뢰할 수 있는 애플리케이션으로 간주하고 CD 단계로 넘김
=>CD 단계에서는 애플리케이션을 컨테이너 이미지로 만들고 파드, 디플로이먼트, 스테이트 풀셋 등 다양한 오브젝트 조건에 맞춰 미리 설정한 파일을 통해 배포

2.Git Hub Action
1)개요
=>End To End Git Hub 중심 소프트웨어 개발 생명주기 프로세스
=>소프트웨어 개발에 필요한 작업 주기를 자동화하는 도구
=>이벤트 기반으로 동작하는데 특정 이벤트가 발생했을 때 Workflow가 Trigger 되고 Workflow가 지정하는 Runner라는 시스템에서 Job을 자동으로 실행시키는 형태
=>요금은 레포지토리가 public 이거나 액션을 실행하는 시스템이 직접 호스팅 경우는 무료
=>Starter Workflow
- 예시를 제공: https://github.com/actions/starter-workflows
- 액션을 공유: https://github.com/marketplace?type=actions

2)구성 요소
=>Event: 정의된 Git Hub Action 작업을 실행시키는 특정 활동
- 외부 트리거(Git Hub 외부에서 발생한 사건)의 발동
- Git Hub 저장소에서 무언가를 수행(push, merge, pr 등)
- 특정 시간 혹은 간격마다 수행
- 사용자가 직접 워크플로를 실행

=>Step
- Git Hub Action의 최소 실행 단위
- uses 절을 통해 가져오고 run 절에 의해서 실행

=>Runner
- 워크플로 코드가 실행되는 물리/가상 서버 및 컨테이너
- 기본적으로는 Git Hub이 제공하는 시스템을 러너로 사용

=>Job
- 스텝을 모아두고 어떤 러너에서 실행할 지 정의하는 컴포넌트
- 전체 워크플로의 중하위 목료를 완수하게끔 설계
- CI/CD 파이프라인의 경우 빌드, 테스트, 패키징을 각각 하나의 잡으로 구성
- 잡의 실행 결과를 깃허브 액션 인터페이스를 통해서 확인하지만 성공 혹은 실패는 잡 단위로 표기될 뿐 스텝 어디에서 이상이 있는지는 나오지 않으므로 각 잡을 만들 대 어느 스텝에서 에러가 났는지 파악할려면 깊게 들어가지 않고도 확인이 가능한 편한 크기로 만들기를 권장

=>jobs
- 실행할 작업을 정의
- 하나의 작업 내의 명령들은 같은 환경에서 실행
- runs-on: 잡이 실행되는 환경으로 linux, mac os, windows를 지원
- steps: 실제 동작을 정의
name: 이름
uses: 작업을 가져와서 사용하는 경
run: 명령어 입력

jobs:
  runs-on: ubuntu-latest
  steps:
  - name: Install tree
    run: |
      sudo apt update
      sudo apt install tree

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository Code
        uses: actions/checkout@v4
      - name: One-Line Print
        run: echo 'Hello Git Hub Action'
      - name: Set Up Python
        uses: actions/setup-python@v5
        with:

      - name: Display Python version
        run: python --version

=>원격 레포지토리에 푸시
- .gitignore를 만들어서 node_modules를 푸시에서 제외하기

- git 초기화: git init

- 스테이지 영역으로 이동: git add .

- 로컬 레포지토리로 이동: git commit -m "nodejs push"

- 원격 레포지토리 연결: git remote add origin https://github.com/itstudy001/nodetest.git

- 푸시: git push -u origin main

=>git hub에서 push가 발생할 때 마다 테스트를 수행하는 action을 생성: .github/workflows/nodetest.yaml
name: Node.js CI
on:
  push:
    branches: [ main ]
jobs:
  build:
    runs-on: ubuntu-latest

    strategy:
      matrix:
        node-version: [20.x]

    steps:
      - uses: actions/checkout@v4 #레포지토리에서 코드를 가져오기

      - name: Set UP Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}

      - run: npm install
      - run: npm run build --if-present
      - run: npm test

- 테스트 수행: pytest

=>git hub action을 이용해서 테스트
- 패키지 정보를 내보내기: pip list --format=freeze > requirements.txt

- 프로젝트에 .github/workflows 디렉토리를 생성하고 yaml 파일을 추가하고 작성: ci-test.yaml
name: ci-test
on:
  push:
    branches:
      - main
jobs:
  run-test-code:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest

- 코드를 원격 레포지토리에 push
actions 탭에서 성공 여부를 확인
