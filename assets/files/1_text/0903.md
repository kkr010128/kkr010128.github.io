8. 리소스 관리 와 오토 스케일링
1)리소스 제한
=>개요
- 쿠버네티스트에서는 컨테이너 단위로 리소스 제한 설정이 가능
- 제한이 가능한 리소스는 CPU, Memory, Ephemeral Storage 이지만 Device Plugin을 이용하면 GPU 등 의 다른 리소스에 대해서도 제한 설정을 할 수 있음 

=>CPU/Memory 리소스 제한
- CPU는 클럭 수로 지정하지 않고 1vCPU(가상 CPU)를 1000m(millicores) 단위로 지정하는데 3GHZ CPU 라도 1vCPU로 지정하면 1000m
- 리소스 제한은 파드 정의 내부의 각 컨테이너 정의 부분에 포함되고 spec.containers[].resources의 requrests.cpu/requests.memory 또는 limits.cpu/limits.memory를 지정하는 형태로 제한
- CPU 와 Memory를 제한하는 디플로이먼트 매니페스트: sample-resource.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-resource
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.17
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "1024Mi"
            cpu: "1000m"

- 배포

=>requests 와 limits
- requests는 사용하는 리소스의 최솟값을 지정하는데 requests로 지정한 양의 리소스가 존재하지 않으면 스케쥴링 되지 않음
- limits는 사용할 리솟스의 최대값

=>requests 만 지정
- limits는 자동으로 설정되지 않고 호스트 측의 부하가 최대로 상승할 때 까지 리소스를 계속 소비하려고 하기 때문에 파드가 많이 기동하는 노드에서 뺏기가 발생하고 메모리의 경우 OOM(Out Of Memory)으로 프로세스가 정지 될 수 있음 
- requests 만 설정하는 매니페스트: sample-resource-only-request.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-resource-only-requests
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.17
        resources:
          requests:
            memory: "256Mi"
            cpu: "200m"

- 배포

- 조회: kubectl get pod sample-resource-only-requests -o json | jq ".spec.containers[].resources"

=>limits 만 지정한 경우
- requests 값이 limits 와 동일하게 설정
- 오버커밋이 될 수 있으므로 되도록이면 requests도 지정
- requests 만 설정하는 매니페스트: sample-resource-only-limits.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-resource-only-limits
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17
    resources:
      limits:
        memory: "256Mi"
        cpu: "200m"

- 조회: kubectl get pod sample-resource-only-limits -o json | jq ".spec.containers[].resources"

=>Ephemeral Storage 리소스 제어
- 개요
일반적으로 스토리지는 용량 문제나 영속성 제어 관점에서 영구 볼륨을 사용하여 그 곳에 데이터를 쓰는 것이 바람직하지만 컨테이너 재기동 시 삭제되어도 좋은 데이터의 경우에는 컨테이너 내부의 디스크 영역을 사용할 수 도 있음

애플리케이션이 로그 데이터를 대량으로 출력하는 경우에도 예상치 못하게 쿠버네티스 노드의 디스크 영역을 많이 차지하는 경우가 있는데 이 때 사용하는 것이 Ephemeral 리소스 제한 

쿠버네티스 노드에서 기동 중인 시스템 구성 요소의 kubelet이 디스크 사용 현황을 정기적으로 모니터링 하고 초과하는 경우는 파드는 Evict(축출) 되게 되어 있음

Ephemeral Storage 용량으로 계산되는 것
	컨테이너가 출력하는 로그
	emptyDir에 기록된 데이터
	컨테이너의 쓰기 가능한 레이어에 기록된 데이터

CPU 나 Memory와 동일한 방법으로 설정

- 실습

스토리지 제한을 가하는 매니페스트(sample-ephemeral-storage.yaml)
apiVersion: v1
kind: Pod
metadata:
  name: sample-ephemeral-storage
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17
    resources:
      limits:
        ephemeral-storage: "2048Mi"
      requests:
        ephemeral-storage: "1024Mi"

배포

리소스 제한을 초과하는 파일을 생성: kubectl exec -it sample-ephemeral-storage -- dd if=/dev/zero of=/dummy bs=1M count=2048

리소스 제한을 초과하기 때문에 Evict 됩니다.

- emptyDir은 파드에서 공유하고 사용할 수 있기 때문에 여러 파드의 설정된 limits의 합계를 초과한 경우 Evict
하나의 파드에 여러 개의 컨테이너가 존재하면 limits * 컨테이너의 개수로 제한이 설정됨

=>시스템에 할당된 리소스와 Eviction 매니저
- CPU/Memory/Ephemeral Storage의 일반적인 리소스는 완전히 고갈되면 쿠버네티스 자체가 동작하지 않거나 그 노드 전체에 영향을 미칠 수 있기 때문에 각 노드에 kube-reserved, system-reserved 라는 두 가지 리소스가 시스템용으로 확보되어 있음
- kube-reserved는 쿠버네티스 시스템 구성 요소나 컨테이너 런타임에 확보된 리소스
- system-reserved는 OS에 깊이 관련된 데몬 등에 확보된 리소스
- 실제 파드에 할당 가능한 리소스는 쿠버네티스 노드에 존재하는 리소스 총량에서 2개의 리소스를 제외한 양
- 쿠버네티스 내부에는 Eviction 메니저라는 구성 요소가 동작하며 시스템 전체가 과부하되지 않도록 관리
- Eviction 메니저는 실제로 사용하는 리소스 합계가 한계치에 도달하지 않았는지 정기적으로 확인하고 초과한 경우 파드를 evict 하고 이를 통해서 노드의 리소스를 100% 사용하지 못하도록 합니다.
- 메모리의 경우는 100% 가까이 사용하게 되면 OOM이 많이 발생하므로 이를 일정하게 제어를 해야 함
- Eviction Threshold는 soft 와 hard 두 가지가 있는데 soft 제한에 걸리면 SIGTERM 신호를 보내 파드를 정지하려고 하는데 이 때 terminationGracePeriodSeconds는 파드에 설정되어 있는 값이고 kubelet에 지정되어 있는 --eviction-soft-grace-period 옵션 값 중 짧은 쪽이 선택되는데 그래서 파드에 긴 terminationGracePeriodSeconds를 설정했더라도 더 빨리 정지되는 경우가 있음
- hard 제한이 걸리면 바로 SIGKILL이 보내져 파드가 정지됨
- Eviction 매니저가 Evict하는 파드는 우선 순위에 따라 결정
requests에 할당된 양보다 초과하여 리소스를 소비하는 것
PodPriority가 더 낮은 것
requests에 할당된 양보다 초과하여 소비하고 있는 리소스 양이 더 많은 것

=>여러 컨테이너 사용 시 리소스 할당
- 파드에는 여러 컨테이너 와 여러 초기화 컨테이너가 포함되어 있을 수 있는데 스케쥴링 될 때는 파드 단위로 수행되어 필요한 리소스는 이러한 여러 컨테이너를 기반으로 계산이 이루어짐
- 파드에 필요한 리소스 양은 모든 컨테이너의 리소스 합계 또는 모든 초기화 컨테이너의 리소스 최댓값 중 큰 것을 그 파드의 리소스 값으로 설정

2)Cluster Autoscaler
=>개요
- 쿠버네티스 클러스터 자체의 오토 스케일링을 의미하며 수요에 따라 쿠버네티스 노드를 자옹으로 추가하는 기능
- 클러스터 전체나 각 노드의 부하 평균이 높아졌을 때 확장하는 것처럼 보이지만 실제로는 Pending 상태의 파드가 생기는 타이밍에 동작하는데 requests 나 limits를 설정하지 않은 상태에서는 실제 노드의 부하 평균이 낮은 상황에서도 스케일 아웃이 되거나 부하 평균이 높은 상황에서도 스케일 아웃이 되지 않는 상황이 발생
- requests를 기준으로 이루어지기 때문에 requests를 초과해서 할당한 경우에는 최소 리소스 요청만으로 리소스가 꽉 차버려서 신규 노드를 추가해야만 하는데 이 때 실제 컨테이너 프로세스가 사용하는 리소스 사용량은 고려되지 않음
- requests를 낮게 설정하면 실제 리소스 사용량이 높더라도 스케쥴링이 가능하다고 판단해서 클러스터 스케일 아웃을 하지 않는 상황이 발생할 수 있음
- 기본 정책으로 requests 와  limits에 너무 큰 차이를 주지 않아야 하고 requests를 너무 크게 설정하지 않을 것을 권장
- 실제 값을 정할 때 requests 와 limits를 낮게 설정하고 성능 테스트를 하면서 올려가는 것이 좋음
- 메모리의 경우 낮게 설정하면 부하 테스트에서 OOM으로 프로세스가 kill 되기 때문에 OOM 발생하지 않을 정도의 리소스 할당을 하나의 지표로 생각

=>Cluster Autoscaler 구축
- Cluster Autoscaler는 Node가 부족하다는 것을 판단하고 실제 Node를 생성할 수 있는 인프라(Node Group)와 연동해야 하는데 kubeadm 환경에서는 새 서버가 만들어진 뒤 자동으로 kubeadm join까지 실행되는 구조가 필요

- 구축 방법
AWS에서 구축하는 경우
	Cluster AutoScaler가 Auto Scaling Group의 Desired Capacity를 변경
	AWS에서는 Auto Scaling Group을 태그를 기반으로 자동 발견하도록 구성할 수 있음

OnPremise 인 경우
	Ubuntu VM을 만들어 kubeadm으로 Worker Node를 추가하는 방식이라면 Cluster API(CAPI)를 사용하는 방법이 Kubernetes 표준에 가까운 방식

3)LimitRange를 사용할 리소스 제한
=>개요
- LimitRange를 사용하면 파드 등에 대해 CPU나 Memory 리소스의 최솟값과 최댓값, 기본값 등을 설정할 수 있음
- LimitRange가 네임스페이스에 제한을 두려면 네임스페이스마다 설정이 필요
- LimitRange는 신규로 파드를 생성할 때 적용되므로 기존 파드에는 영향을 주지 않음
- 제한 가능한 항목
default: 기본 limits
defaultRequest: 기본 requests
max: 최대 리소스
min: 최소 리소스
maxLimitRequestRatio: limits/requests의 비율
- LimitRange를 설정할 수 있는 리소스  와 설정 항목
Container는 전부 설정 가능
Pod는 default 와 defaultRequest를 설정할 수 없음
PersistentVolumeClaim은 max 와 min 만 설정 가능

=>기본으로 생성되는 LimitRange
- 파드나 컨테이너에 대해 리소스 제한을 전혀 하지 않을 경우 실제 노드 부하와 관계없이 계속 파드를 스케쥴링
- 스케쥴러는 requests에서 지정한 리소스를 확보할 수 있을 지에 따라 스케쥴링 여부를 판단하기 때문에 모든 파드에 requests를 지정하지 않았을 경우 스케쥴러는 계속 그 노드에 스케쥴링을 하게 됨
- 리소스 소비가 과도하게 많아지면 메모리는 OOM Killer에 의해 프로세스가 정지되지만 CPU는 전체 동작이 느려져 최악의 경우 운영체제가 동작을 하지 않게 됨

=>Container에 대한 LimitRange
- type:Container의 LimitRange로 설정
- 개별적으로 컨테이너에 대해 리소스 제한을 정의하지 않고 기본 설정을 정의할 수 도 있으며 컨테이너에 허용하는 최대/최소 리소스 제한을 설정할 수 도 있음 
- maxLimitRequestRatio를 설정하면 requests 와 limits의 차이에 따른 과도한 오버커밋도 피할 수 있음

- Container에 제한을 가하는 LimitRange 매니페스트: sample-limitrange-container.yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: sample-limitrange-container
  namespace: default
spec:
  limits:
  - type: Container
    default:
      memory: 512Mi
      cpu: 500m
    defaultRequest:
      memory: 256Mi
      cpu: 250m
    max:
      memory: 1025Mi
      cpu: 1000m
    min:
      memory: 128Mi
      cpu: 125m
    maxLimitRequestRatio:
      memory: 2
      cpu: 2

- 배포

- 최저 CPU requests 보다 낮은 파드를 생성하는 매니페스트: sample-pod-overrequest.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod-overrequest
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17
    resources:
      requests:
        cpu: 100m
      limits:
        cpu: 100m

배포해보면 실패:  forbidden: minimum cpu usage per Container is 125m, but request is 100m

- requests 와 limits의 차이가 4배인 파드를 생성하는 매니페스트: sample-pod-overrequest.yaml
apiVersion: v1

4)Resource Quota
=>개요
- 각 네임스페이스마다 사용 가능한 리소스 제한 기능
- 이미 생성된 리소스에는 적용되지 않음
- 생성 가능한 리소스 수 제한 과 리소스 사용량 제한으로 나눔

=>생성할 수 있는 ConfigMap 제한
- ResourceQuota 생성(sample-resourcequota.yaml)
apiVersion: v1
kind: ResourceQuota
metadata:
  name: sample-resourcequota
  namespace: default
spec:
  hard:
    count/configmaps: 10

배포

확인: kubectl describe resourcequota sample-resourcequota

configmap 11개 생성: for i in `seq 1 11`; do kubectl create configmap conf-$i --from-literal=key1=val1; done


=>최근의 방식
apiVersion: v1

    count/cronjobs.batch: 10

5)Horizontal Pod Autoscaler
=>개요
- HPA는 디플로이먼트/레플리카셋/레플리케이션컨트롤러의 레플리카 수를 CPU 부하 등에 따라 자동으로 스케일하는 리소스
- 부하가 높아지면 스케일 아웃하고 부하가 낮아지면 스케일 인 됨
- 파드에 resource requets가 설정되어 있지 않을 경우에는 동작하지 않음
- HPA는 30초에 한 번 꼴로 오토 스케일 여부를 확인
- 필요한 레플리카수 = ceil(sum(파드의 현재의  CPU 사용률) / targetAverageUtilization)
현재 2개의 파드가 배포 중인데 100% 와 90% CPU를 사용하고 있고 50%까지만 사용하도록 허락
